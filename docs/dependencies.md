# Package dependency graph

Generated by inspection of each package's `package.json` `dependencies` on
other `@awb/*` workspace packages. No circular dependencies exist; if you add
one, that's a design smell — split the shared bit into a lower-level package
instead of reaching sideways.

```
@awb/domain            (no @awb deps — pure types/schemas, imported by nearly everything)
@awb/config             → domain
@awb/evidence           → domain
@awb/database           → domain, config
@awb/repository         → domain, database
@awb/repository-map     → domain
@awb/repository-memory  → domain, database
@awb/workflow           → domain   (+ @temporalio/* — no other @awb deps: Workflow code
                                     must stay deterministic and cannot reach into
                                     database/repository/etc directly; Activities do that)
@awb/temporal-worker     → domain, workflow  (+ @temporalio/worker, @temporalio/activity)
@awb/workspace           → domain, config, repository (reuses repository's runGit helper)
@awb/execution           → domain
@awb/agent-gateway       → domain
@awb/capability-broker   → domain
@awb/planning            → domain, agent-gateway, capability-broker, workflow
@awb/verification        → domain, evidence, execution
@awb/qa                  → domain, evidence, execution, playwright
@awb/review              → domain, agent-gateway, capability-broker, evidence
@awb/github              → domain, evidence  (Milestone 9)
@awb/observability        → domain            (Milestone 10)
@awb/policy               → domain            (Milestone 3/6)

apps/cli       → config, database, domain, repository (+ more as milestones land)
apps/daemon    → nearly all packages (it's the composition root)
apps/web       → nothing from packages/ directly — talks to apps/daemon over HTTP/WS only
```

## Why this shape

- **`@awb/domain` has zero `@awb/*` dependencies.** Every other package can
  depend on it without risk of a cycle. If you find yourself wanting to import
  from `@awb/database` *into* `@awb/domain`, the type you're adding probably
  belongs in the consuming package instead.
- **`@awb/workflow` only depends on `@awb/domain`.** This is a deliberate
  determinism boundary (see `docs/temporal-workflows.md`) — Workflow code
  cannot import `@awb/database`, `@awb/repository`, or any I/O-performing
  package directly. Activities (in `workers/temporal-worker`) sit between the
  Workflow and those packages.
- **`apps/web` has no package dependencies at all.** The browser talks to
  `apps/daemon` over `/api` (HTTP + WebSocket) only — never imports a
  `packages/*` module directly, per the "browser never touches the
  filesystem, git, or a shell" invariant.
- **`apps/daemon` is the composition root.** It's expected to depend on most
  packages, since it's the one process that owns SQLite, the artifact store,
  the Temporal client, and GitHub credentials.

This file is maintained by hand at each milestone boundary rather than
generated, since the package count is small enough (≈20) for manual upkeep to
stay accurate — if that stops being true, prefer a small script that greps
each `package.json` over letting this document silently drift.
