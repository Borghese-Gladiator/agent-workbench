# Token-efficiency findings — summary

_Companion to the longer audit at `agent-workbench-live/runs/2026-05-22-token-efficiency-tracking/audit-token-efficiency.md` and the queued work plan in `docs/TODO.md` §4._

## Top-line

The §3 token-efficiency-tracking run shipped per-run metrics tracking. It works — `metrics.jsonl` is being produced — but it answers only ~0.003% of the cost question on a realistic run. Concrete numbers from the §3 dogfood run itself (`runs/2026-05-22-token-efficiency-tracking/metrics.jsonl`):

| Bucket | Tokens | Share of total | Bucketed by current system? |
|---|---:|---:|:---:|
| fresh input | 2,934 | 0.0024% | yes |
| output | 425,478 | 0.34% | n/a |
| cache_creation | 1,178,364 | 0.95% | **no** |
| cache_read | **121,786,040** | **98.7%** | **no** |
| **total** | **123,392,816** | 100% | |
| **cost** | **$236.73** | | |

The bucketer in `lib/metrics/buckets.py:127-135` attributes `input_tokens` only. The renderer at `lib/cli/cmd_metrics.py:88` literally prints "cache_read not bucketed." Both lines are explicit acknowledgements that the gap exists.

A second bug surfaced incidentally: **100% of 621 turns on this run landed in `stage=other, command=""`** — the slash-command correlator silently failed. Even if buckets were fixed, the per-phase cost split wouldn't work today.

## Why `cache_read` is so big

Same tokens, billed once per turn. The session's prefix (system prompt + tool defs + CLAUDE.md + AGENTS.md + every prior user message + every prior assistant reply + every prior tool result) grows monotonically. On this run, the prefix peaked around **295k tokens**; the average across 621 turns was **~196k**. Multiply: 196k × 621 ≈ 121.7M. That's the metric.

In one sentence: **`cache_read` is the cost of keeping the conversation alive, multiplied by every step you took inside it.**

The top 5 turns on the run all show the signature pattern:

| input | cache_creation | cache_read | output |
|---:|---:|---:|---:|
| 1 | 564 | 295,443 | 290 |
| 1 | 564 | 295,443 | 290 |
| 1 | 1,693 | 293,750 | 273 |
| 1 | 1,693 | 293,750 | 273 |
| 1 | 299 | 293,451 | 1,564 |

Tiny fresh input. Tiny output. ~290k re-read prefix every time.

## Does TODO §4 fully solve this?

**No.** §4 is the right next step, but it stops short of the deepest mitigations. Honest accounting:

### What §4 does solve

- **Visibility into where the cache is going.** §4 buckets `cache_read` and `cache_creation` the same way fresh input is bucketed today, so a future run can answer "is the 121.8M mostly assistant_history, or mostly tool_results, or mostly system_prompt?" Without this, every other decision is guessing.
- **The 100%-`other` correlation bug.** §4 includes the regression test and the targeted fix in `transcript.py`. After it lands, per-phase tables actually work.
- **One large structural mitigation: compact validate context.** §4 introduces `validate-context.md` (auto-generated by `validate --init`, no LLM call) and rewires `.claude/commands/validate.md` to read it instead of brief + plan + build + diff separately. This avoids the validator independently re-reading those files in the same session that already has a 295k prefix.
- **Pre-computed blast radius.** Today `templates/review.md` instructs the model to run `git diff --name-only` + `git grep -n <symbol>` up to depth 3. §4 moves those into the CLI so the model reads one file instead of running N tool calls whose outputs accumulate.
- **Cache-miss visibility.** §4 surfaces the count of turns where `cache_creation > 1000` (i.e., 5-minute TTL expirations), so long pauses are diagnosable.
- **A better efficiency metric.** §4 adds `billable_net_per_passing_build = (input + output + cache_creation) / approves` — excludes `cache_read` so the metric tracks *agent* efficiency, not *session length*.

Expected impact, rough order: 30-60% reduction in `cache_read` *during the validate phase specifically*, on runs that adopt the new validate-context flow. The build phase is mostly untouched.

### What §4 doesn't solve

- **Fresh-session enforcement.** §4 only prints a hint when transcript turns > 100. The hint is correct, but it relies on the human reading and acting on it. The biggest single lever — actually starting `/validate` in a new Claude Code session — is voluntary. A run that does build + validate in one session still pays the full long-prefix tax.
- **The build phase's own cache_read.** On the §3 run, the build session itself was long enough that build-phase turns were also re-reading large prefixes. §4 doesn't touch this. Mitigations would need to be either (a) compact between sub-steps of build, which Claude Code doesn't currently expose a hook for, or (b) more aggressive subagent use during build so file-reading happens in a subagent's own context.
- **CLAUDE.md + AGENTS.md weight.** Both load on every turn. §4 doesn't audit or shrink them. On a 621-turn session, even 5k tokens of CLAUDE.md content = 3.1M cache_read tokens billed over the session. Worth a separate review.
- **Claude Code's auto-compaction.** Claude Code does compact at high context fill, but the timing isn't aligned to the lifecycle (build/validate boundaries). §4 doesn't change this — only Anthropic can.
- **Cross-session cache reuse.** When you exit Claude Code and re-launch, the cache for the new session starts cold. There's no way to inherit cached portions across session boundaries today.
- **Per-turn cost throttling.** Some turns on the §3 run charged $0.40+ for tiny outputs. §4 reports this but doesn't throttle. Throttling would mean either (a) the model voluntarily summarizing its own session, or (b) hard limits in the harness — both out of scope for the workbench.

### What's missing from §4 entirely

These would be follow-on runs after §4:

1. **A repo-instructions audit pass.** Read `~/.claude/CLAUDE.md`, `agent-workbench-live/AGENTS.md`, repo-root `AGENTS.md`. Identify content that's redundant, optional, or stage-specific. Move stage-specific guidance into the slash-command bodies (loaded once on invocation) rather than CLAUDE.md (loaded every turn). Expected impact: 10-30% on long-session cache_read.
2. **Subagent-first read strategy.** The current `/build` and `/validate` workflows have the master session reading files directly. Each Read tool result sticks in the prefix forever. Routing all "reads more than N files" work through `Explore` subagents would keep the master session prefix small. Would need updates to `.claude/commands/build.md` and `validate.md` plus AGENTS.md guidance.
3. **Build-mid compaction.** A `/build` that lasts 200+ turns probably has 100 turns of debugging that aren't load-bearing for validate. A `agent-workbench build --checkpoint` command could prompt the model to write a compact `build-progress.md` and recommend a session refresh mid-build. Speculative; would need design first.
4. **Tool-call output budgets.** A single `git log` or large file Read can dump 5-10k tokens into the prefix. Adding a soft budget per tool call (e.g., truncate Read outputs > 2k tokens, instruct the model to use `head` / `tail` for the rest) would compound across long sessions.

## Practical answers to "what should I do now?"

In priority order, by effort:

1. **Right now, before §4 lands:** at the end of `/build`, exit Claude Code and re-launch in the worktree before running `/validate`. This alone would have saved most of the $186 cache-read on the §3 run.
2. **Watch for "auto-compact" notices in Claude Code.** When you see one, it means you've already paid for a lot of prefix. Either let it compact and continue, or proactively exit and restart with a clean state.
3. **Don't reuse a session across unrelated runs.** Each `/new-run` for an independent task = exit + relaunch first.
4. **Run §4 next.** It unblocks measurement and lands the cheapest structural fix (compact validate context).
5. **Follow §4 with the repo-instructions audit.** Easiest of the four missing pieces and likely 10-30% on long sessions.

## Bottom line

§4 takes the 121.8M from "unexplained" to "explained, with one phase materially reduced." It does not take it to "small." The 295k-prefix-per-turn pattern is inherent to staying in one long Claude Code session, and the workbench can't change that — what it CAN do is surface the cost, make the validator stop carrying the build's history, and tell the human when it's time to restart. §4 does the first two and prints a hint for the third. To go further, the next runs need to address CLAUDE.md weight, subagent routing, and tool-output discipline.
