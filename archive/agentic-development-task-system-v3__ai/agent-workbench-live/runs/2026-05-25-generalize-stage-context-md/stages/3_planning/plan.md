# Implementation plan

## Current repo understanding

This is a self-modifying run: the workbench's source code is the target. The pattern to mirror is `validate-context.md`, generated by `lib/validate_context.py` and written by `cmd_validate.py:_write_validate_context_artifacts`. That builder is **path-based, not pure-string** (see DR-001) — it accepts pathlib paths and reads files internally via a defensive `_read()` helper that returns `""` on missing. The brief's "pure function takes strings" framing was Assumption A in the raw idea; planning confirmed it does not match `validate_context.build`'s actual shape, so this plan follows the existing pattern.

Two facts from `cmd_start.py` and `metadata.py` that simplify the implementation:

1. **`rd = metadata.run_dir(cfg, run_id)`** at `cmd_start.py:32` already returns the worktree-side run dir for self-modifying runs. `metadata.run_dir` reads `target.worktree.path` from metadata and delegates to `runs.resolve_run_dir_for_meta`. No new path-resolution logic is required to land `build-context.md` inside the worktree.
2. **There is no `/build` slash command.** Today the building stage entry point is `/handoff` only at the *human_review* stage; the agent enters `building` by virtue of being inside the worktree after `/start`. So the wiring target for "read `build-context.md` first" is the `/start` command's output (which already prints `worktree:` and is the last thing the human sees before the agent starts coding) and `AGENTS.md`'s session-discipline section. There is no slash-command-step-1 to edit because there is no slash command.

The staged-vs-flat distinction matters: for staged runs, brief lives in `stages/2_shaping/brief.md` and plan in `stages/3_planning/plan.md`; for flat runs, both live at the run root. `_write_validate_context_artifacts` already branches on `staged` for this. The new `_write_build_context_artifacts` must do the same.

The convenience-artifact-swallow-on-exception contract is established in `cmd_validate.py:46–84` (the entire body of `_write_validate_context_artifacts` is wrapped in `try: ... except Exception: pass`). The new write-call in `cmd_start.py` follows the same pattern.

## Proposed changes

### Change 1 — New file `lib/build_context.py`

Mirrors `lib/validate_context.py`'s shape. Single public entry point:

```python
def build(
    *,
    brief_path: pathlib.Path,
    plan_path: pathlib.Path,
    meta: dict,
    build_template_path: pathlib.Path,
) -> str:
    """Return the rendered build-context.md body."""
```

Note: takes `meta` dict (not `worktree_path` + `base_ref` scalars) because the build context surfaces three metadata fields together (worktree path, branch name, base_ref_sha) rather than the single field validate-context needs. Passing the dict is cleaner than three positional params. `meta` is the loaded metadata.yaml.

`build_template_path` is the path to `templates/build.md`; the builder inlines its skeleton into the curated context (so the agent doesn't context-switch into `templates/`).

Body structure (top-level `##` sections, in order):

1. `# build-context.md` + generation comment
2. `## Acceptance criteria` — lifted from `brief.md#acceptance-criteria` (fallback: `(none in brief.md)`)
3. `## Non-goals` — lifted from `brief.md#non-goals` (fallback: `(none in brief.md)`)
4. `## Proposed changes` — lifted from `plan.md#proposed-changes` (fallback: `(none in plan.md)`)
5. `## Files likely to change` — lifted from `plan.md#files-likely-to-change` (fallback: `(none in plan.md)`)
6. `## Test plan` — lifted from `plan.md#test-plan` (fallback)
7. `## Definition of done` — lifted from `plan.md#definition-of-done` (fallback)
8. `## Decisions & assumptions (filtered)` — lifted from `plan.md#decisions--assumptions` (use the existing `_filtered_plan_blocks`-style approach, but here we have no `build.md` to filter against yet, so include all DR-NNN / ASM-NNN blocks; the filter against `build.md` is meaningful only at validate-time, not at building-entry)
9. `## Worktree` — three lines: `Path: <worktree path>`, `Branch: <branch name>`, `Base ref SHA: <sha>` — all read from `meta`
10. `## build.md template skeleton` — inlines the contents of `templates/build.md` so the builder agent sees the section headings to fill in without reading the template dir
11. `## Rules` — load-bearing one-liner: "Stay bounded by the brief. Record deviations from plan in `build.md`. Do not read `brief.md` or `plan.md` unless this file's pointers send you there."

Helper functions duplicated from `validate_context.py` (do not refactor into a shared module — see DR-003):
- `_read(path)` → returns `path.read_text()` or `""` on missing
- `_section(body, name)` → regex-based heading extraction, returns `""` if missing
- `_HEADING_RE` constant

ASM-NNN / DR-NNN block extraction: reuse the regex shape from `validate_context._collect_id_blocks` but **without** the `build.md` filter (we include all blocks at building-entry time). This is a small variant; copy the relevant regex constant and a simplified function rather than importing from validate_context (per DR-003).

### Change 2 — Modify `lib/cli/cmd_start.py`

Add a helper `_write_build_context_artifacts(cfg, run_id, rd, staged, meta)` mirroring `_write_validate_context_artifacts` in `cmd_validate.py`. Its body is wrapped in `try: ... except Exception: pass`. Inside, it:

1. Resolves `brief_path` and `plan_path`: for staged, `lifecycle.stage_dir(cfg, run_id, "shaping") / "brief.md"` and `lifecycle.stage_dir(cfg, run_id, "planning") / "plan.md"`; for flat, `rd / "brief.md"` and `rd / "plan.md"`.
2. Resolves `build_template_path`: `cfg.root / "templates" / "build.md"`. (Confirmed during planning that the template exists.)
3. Resolves `target_dir`: for staged runs, `lifecycle.stage_dir(cfg, run_id, "building")`; for flat, `rd`. Mirror `_write_validate_context_artifacts`'s pattern.
4. Calls `build_context.build(brief_path=…, plan_path=…, meta=meta, build_template_path=…)`.
5. Writes the result to `target_dir / "build-context.md"`.

Insertion point: between line 88 (metadata update finishes) and line 91 (start of the transition block). The call must happen **after** the worktree exists (so `target_dir` resolves correctly inside the worktree-side run dir via `metadata.run_dir`) and **before** the transition (so the file is in place when the human reads the `/start` output).

Important: `rd` was captured at line 32 (before worktree creation for non-self-modifying runs). For runs where the worktree was just created (`already_created == False`), `rd` may still point to master's runs dir; for self-modifying runs (`already_created == True`), it already points to the worktree-side run dir. The helper must re-resolve `rd` via `metadata.run_dir(cfg, run_id)` immediately before computing `target_dir`, to capture the post-creation truth. (See ASM-001.)

Also reload `meta` after the `metadata.update` at line 88, so the `base_ref_sha` is visible to the builder. The simplest path is `meta = metadata.load(cfg, run_id)` at the top of the helper.

## Risks

- **Builder template-path discovery.** `cfg.root / "templates" / "build.md"` assumes the template exists. If not present in the worktree (it should be — it's tracked source), the builder writes a fallback note in the inline section. Test case explicitly covers missing template behavior.
- **`metadata.update` doesn't re-load `meta` in cmd_start.** After line 88's `metadata.update`, the local `meta` variable is stale (the in-memory dict was passed in for mutation but `base_ref_sha` was set inside the closure on the disk file, not on the in-memory variable). The helper must `meta = metadata.load(cfg, run_id)` itself rather than trusting the caller's `meta`. Recorded as ASM-001.
- **Self-modifying vs. non-self-modifying paths diverge.** For self-modifying runs (`already_created`), the worktree exists at new-run time and `rd` points to the worktree-side run dir from line 32. For non-self-modifying runs, the worktree is created at line 79; `rd` was captured at line 32 before creation, and we need to re-resolve via `metadata.run_dir(cfg, run_id)` after line 88. The helper does the re-resolution unconditionally so both paths converge on truth.
- **Staged vs. flat layout divergence.** The helper branches on `staged = lifecycle.is_staged_run(cfg, run_id)` to decide `target_dir` and source paths. Mirrors the existing pattern in `_write_validate_context_artifacts`; the bug surface here is "did I get the stage directory naming right?" Mitigated by reading the existing helper's pattern verbatim.
- **Test fixtures are wide.** A real E2E test of `/start` requires a real git repo + worktree + temp workbench. `tests/test_validate_context.py` keeps its tests narrow (just the builder, fed synthetic strings — no real git). The pure-builder unit tests are easy; the E2E coverage may need a different test class. If E2E fixtures are heavy, prefer keeping unit-test coverage strong and adding only one minimal E2E test that exercises the wrapping in `cmd_start.py`.
- **Doc drift in lifecycle.md.** If the `building` stage's table structure differs from what the subagent reported, the row format needs adjustment. Mitigated by re-reading the actual file before editing.

## Decisions & assumptions

### DR-001
- **Decision**: `build_context.build` takes `pathlib.Path` arguments and reads files internally, matching `validate_context.build`'s signature shape. Not a pure string-in function.
- **Rationale**: Consistency with the existing curated-context builder. The brief's "pure function takes strings" framing was an assumption in the raw idea; `validate_context.build` is explicitly path-in, and `_read()` is the load-bearing defensive helper. Mirroring keeps cognitive overhead minimal and avoids the question "why does this builder take strings when the other takes paths?"
- **Alternatives considered**: (a) Pure string-in (raw idea's framing); (b) Mixed — paths for big artifacts, strings for `meta`.
- **Why not the alternatives**: (a) Introduces an inconsistency that hurts the next person reading both files. (b) is what this plan adopts for `meta` specifically — it's a dict, not a file — so the "mixed" critique evaporates; the substantive choice is "paths for the markdown artifacts," which matches `validate_context`.

### DR-002
- **Decision**: Write `build-context.md` from `cmd_start.py`, not from a hypothetical `/build` slash command's `--init` step or from a building-stage entry hook.
- **Rationale**: The raw idea floated both options. The brief committed to `/start`. Validating that choice during planning: there is no `/build` slash command at all (subagent investigation confirmed). The building stage is entered passively by the agent operating inside the worktree after `/start`. So `/start` is the only deterministic write point upstream of building.
- **Alternatives considered**: Write it on first agent-side action (e.g. lazy generation when the agent first reads the file); add a new `/build --init` slash command to symmetrize with `/shape --init` / `/plan --init` / `/validate --init`.
- **Why not the alternatives**: Lazy generation moves a deterministic step into the agent's responsibility — exactly what curated-context exists to prevent. Adding a new slash command is scope creep against the brief's non-goal list and adds friction for the human (one more command to remember).

### DR-003
- **Decision**: Duplicate the helper functions `_read`, `_section`, `_HEADING_RE` (and a small variant of the DR/ASM block extractor) into `lib/build_context.py` rather than importing from `lib/validate_context.py` or extracting a shared `lib/context_helpers.py`.
- **Rationale**: The two builders may diverge later (different sources, different filters, different output structures — followups-context.md, plan-context.md, shape-context.md will each have their own quirks). A shared base prematurely couples them. The bad-examples block in the brief explicitly flags "edits to validate_context.py itself" as a bad outcome; duplicating instead of refactoring honors that. The functions are 5–10 lines each; the duplication cost is trivial.
- **Alternatives considered**: Extract a shared `lib/markdown_sections.py` with `read`, `section`, `heading_re` exported; import from validate_context directly.
- **Why not the alternatives**: Extracting now means a third file to read and a shared API surface to maintain; the extraction is cheaper *after* the third builder lands (when the right shape is visible). Importing from validate_context creates a sibling-import cycle in a flat lib/ layout for what should be a small, self-contained file.

### DR-004
- **Decision**: Include all DR-NNN / ASM-NNN blocks from `plan.md` in `build-context.md#decisions--assumptions`, without filtering against `build.md` (which doesn't yet exist at building-entry time).
- **Rationale**: At validate-time, `_filtered_plan_blocks` filters DR/ASM blocks against `build.md` so the reviewer sees only the decisions actually referenced. At building-entry there's no `build.md` yet, so there's nothing to filter against; the agent needs the full list to keep itself bounded. The "filtered" label in the brief was a copy-paste error; corrected here to "all relevant" in the actual heading.
- **Alternatives considered**: Filter against `brief.md` (which decisions does the brief mention?); leave the section empty and tell the agent to read `plan.md` if they want decisions.
- **Why not the alternatives**: Filtering against brief is noise — briefs typically don't mention DR-NNN IDs because the brief is code-blind. Leaving empty defeats the cache-discipline goal (agent still has to read plan.md).

### ASM-001
- **Text**: `meta` passed into `cmd_start.run` is stale after `metadata.update` on line 88 (the closure mutates the on-disk file but the local dict isn't refreshed). `_write_build_context_artifacts` must reload meta via `metadata.load(cfg, run_id)` if it needs the `base_ref_sha`.
- **Reason**: Reading `cmd_start.py`, the `_m` closure at line 84 mutates a dict argument passed to `metadata.update`. Standard `metadata.update` patterns I've seen elsewhere in this codebase read-modify-write the file; whether they also mutate the caller's `meta` reference depends on `metadata.update`'s implementation. Safer to reload than to trust.
- **Impact**: low. Worst case: `base_ref_sha` is missing from `build-context.md#worktree` for the first run that hits the helper. Easy to spot and fix.

### ASM-002
- **Text**: Running `python -m pytest` from `agent-workbench-live/` works without a virtualenv shim or `bin/pytest` invocation. If a shim is required (analogous to `bin/pytest` patterns elsewhere in this repo family), the builder discovers it during the build stage and records the actual command in `build.md`.
- **Reason**: The user's CLAUDE.md mentions `bin/pytest` for the `app` (Django) repo. This is a different repo (no Django). The standard pattern for `agent-workbench-live` is bare `python -m pytest`; confirming during build.
- **Impact**: medium. Wrong invocation means the test suite isn't actually validated. Easy to catch (commands log will show the failure).

### ASM-003
- **Text**: `templates/build.md` exists at `agent-workbench-live/templates/build.md` with sensible section headings that can be inlined verbatim into `build-context.md`.
- **Reason**: The subagent listed `templates/build.md` in its summary as a real file. The exact contents weren't quoted, but the file's existence is enough to plan against. If the contents turn out to be unsuitable (e.g. heavy boilerplate that bloats `build-context.md`), the build stage either trims at inline time or files a follow-up.
- **Impact**: low. Worst case: `build-context.md` has a verbose inline template section; cheap to iterate.

### ASM-004
- **Text**: `docs/lifecycle.md`'s `building` stage table has a structure compatible with adding a new `build-context.md` row alongside existing rows (Reads, Produces, etc.). The subagent reported a table-with-named-rows shape; this assumption holds unless the file has changed since.
- **Reason**: Lifecycle docs are slow-changing; the subagent read the file during planning.
- **Impact**: low. If the table shape is different, the builder adjusts in-place; the change is small.
