# Agentic Development Task System — Implementation Phases (v0.0.3)

## Tech Stack

- **Frontend:** React 18 + TypeScript + Vite
- **Backend:** Node.js + Express (or Fastify)
- **Database:** SQLite via `better-sqlite3`
- **Terminal:** xterm.js + node-pty
- **Styling:** CSS Modules or Tailwind CSS
- **State:** React Query for server state, zustand for UI state
- **File watching:** chokidar

## Phase 1: Storage and Ingest Foundation

### Goal
Stand up project scaffolding, SQLite database, migration system, and the JSON ingest pipeline.

### Steps

1. **Project structure**
   - Initialize monorepo-style layout:
     ```
     src/
       server/
         db/
           migrations/
           connection.ts
           schema.ts
         ingest/
           watcher.ts
           validator.ts
           processor.ts
         routes/
         index.ts
       shared/
         types.ts
         constants.ts
       client/
         (placeholder)
     ```
   - Set up `package.json`, `tsconfig.json`, Vite config
   - Install dependencies: `better-sqlite3`, `chokidar`, `uuid`, `express`, `zod`

2. **SQLite database + migrations**
   - Create `schema.sql` with the exact DDL from the spec (all 12 tables + indexes)
   - Write a migration runner that applies `schema.sql` on first boot
   - Database file location: `<app-data>/db/taskboard.sqlite`
   - Enable `PRAGMA foreign_keys = ON` on every connection
   - Enable WAL mode for concurrency

3. **Shared types**
   - Define all TypeScript types from the spec in `shared/types.ts`
   - Define Zod schemas for ingest envelope validation in `shared/schemas.ts`

4. **Ingest watcher**
   - Watch `<repo>/.taskboard/inbox/` using chokidar
   - On new `.json` file:
     1. Read and parse JSON
     2. Validate against Zod envelope schema (`event_id`, `event_type`, `occurred_at`, `payload`)
     3. Compute SHA-256 of file content
     4. Check `ingest_files` for duplicate by `file_path` or `sha256`
     5. If invalid → move to `.taskboard/rejected/`, insert `ingest_files` with `rejection_reason`
     6. If duplicate → ignore silently (or log)
     7. If valid → dispatch to event processor

5. **Event processor — `plan.proposed`**
   - Insert into `plans` table (status = `draft`)
   - Insert each task draft into `plan_task_drafts`
   - Insert `activity_events` for plan proposed
   - Insert `ingest_files` record
   - Move file to `.taskboard/processed/`

6. **Event processor — other events (stubs)**
   - `task.created`, `task.updated`, `task.status_changed`, `task.assigned`, `task.session_linked`
   - `session.declared`, `review.requested`, `review.completed`, `artifact.attached`
   - Implement as validated stubs that insert activity events and ingest records
   - Full behavior for each wired up in later phases

7. **Repo directory bootstrapping**
   - On startup (or on config), ensure `.taskboard/inbox/`, `.taskboard/processed/`, `.taskboard/rejected/`, `.taskboard/attachments/` exist
   - Ensure `<app-data>/db/`, `<app-data>/sessions/`, `<app-data>/logs/`, `<app-data>/cache/` exist

### Acceptance Criteria
- Valid `plan.proposed` JSON in inbox → plan + drafts in DB, file moved to `processed/`
- Invalid JSON → file moved to `rejected/`, `ingest_files` row with rejection reason
- Duplicate file (same sha256) → safely ignored
- Plans and drafts queryable via direct DB access
- Activity events recorded for every successful ingest

### Files Created
- `package.json`, `tsconfig.json`, `vite.config.ts`
- `src/server/db/connection.ts`, `src/server/db/schema.sql`, `src/server/db/migrate.ts`
- `src/shared/types.ts`, `src/shared/schemas.ts`, `src/shared/constants.ts`
- `src/server/ingest/watcher.ts`, `src/server/ingest/validator.ts`, `src/server/ingest/processor.ts`
- `src/server/index.ts`
- Test fixtures: `tests/fixtures/plan-proposed-valid.json`, `tests/fixtures/plan-proposed-invalid.json`
- Unit tests for validator, processor, and DB operations

## Phase 2: Plans and Approval Flow

### Goal
Build the plan inbox UI, plan detail view, and the approve/reject actions with task materialization.

### Steps

1. **API routes for plans**
   - `GET /api/plans` — list plans (filter by status)
   - `GET /api/plans/:id` — plan detail with task drafts
   - `POST /api/plans/:id/approve` — approve plan
   - `POST /api/plans/:id/reject` — reject plan

2. **Plan approval logic**
   - Set `plans.status = 'approved'`, `approved_at`, `approved_by`
   - For each `plan_task_drafts` row:
     - Create flat `tasks` row (status = `ready` or `backlog`)
     - Set `source_plan_id`, `source_plan_task_draft_id`
     - Copy repo/directory/worktree/agent context from draft
     - Parse `tags_json` and insert `task_tags`
   - Insert `activity_events` for plan approval + each task creation

3. **Plan rejection logic**
   - Set `plans.status = 'rejected'`, `rejected_at`, `rejected_by`
   - Insert activity event
   - No tasks materialized

4. **Client: Plan Inbox view**
   - React page listing draft plans
   - Each card: title, goal, planner agent, repo context, count of proposed tasks
   - Click to expand/view proposed task drafts
   - Approve / Reject buttons per plan

5. **Client: Plan Detail view**
   - Full plan information
   - Ordered list of task drafts with titles, contents, acceptance criteria, tags
   - Approve / Reject actions
   - After approval: link to created tasks

6. **Client shell and routing**
   - Set up React Router with basic layout (sidebar nav)
   - Routes: `/plans`, `/plans/:id`, `/tasks` (placeholder), `/activity` (placeholder)

### Acceptance Criteria
- Ingested plan visible in Plan Inbox
- Approving a plan creates flat tasks with correct provenance
- Rejecting a plan creates no tasks
- Tasks carry repo/worktree/tag/agent context from drafts
- Activity events logged for approval and each task creation
- Plan detail shows task drafts before approval, created tasks after

### Files Created/Changed
- `src/server/routes/plans.ts`
- `src/server/domain/plans.ts` (approval/rejection logic)
- `src/client/App.tsx`, `src/client/router.tsx`
- `src/client/pages/PlanInbox.tsx`, `src/client/pages/PlanDetail.tsx`
- `src/client/components/PlanCard.tsx`, `src/client/components/TaskDraftList.tsx`
- `src/client/api/plans.ts` (React Query hooks)

## Phase 3: Task Board and Task Detail

### Goal
Build the Kanban task board with filtering, task detail page with full context, and status transition actions.

### Steps

1. **API routes for tasks**
   - `GET /api/tasks` — list tasks (filter by status, agent, repo, directory, worktree, tags)
   - `GET /api/tasks/:id` — task detail with related data
   - `PATCH /api/tasks/:id` — update task fields (status, assigned agent, etc.)
   - `POST /api/tasks/:id/transition` — explicit status change with validation
   - `GET /api/tasks/:id/activity` — activity events for this task
   - `GET /api/tasks/:id/reviews` — reviews for this task
   - `GET /api/tasks/:id/sessions` — linked sessions for this task
   - `GET /api/tasks/:id/artifacts` — artifacts for this task

2. **Task status transition validation**
   - Define allowed transitions (e.g., `backlog→ready`, `ready→assigned`, `assigned→running`, etc.)
   - Reject invalid transitions with clear error messages
   - Every transition creates an `activity_events` row

3. **API routes for agents**
   - `GET /api/agents` — list agents
   - `POST /api/agents` — create agent
   - Agent assignment to tasks

4. **Client: Kanban Board**
   - Columns for key status groups (e.g., Backlog, Ready, In Progress, Review, Done, Archived)
   - Map multiple statuses to columns (e.g., `assigned` + `running` + `waiting` + `blocked` → "In Progress")
   - Task cards showing: title, agent, tags, repo/dir, last updated, session count, review badge
   - Filter bar: status, agent, repo, directory, worktree, tag
   - Click card → navigate to task detail

5. **Client: Task Detail page**
   - Full task information display
   - Status transition controls (buttons for valid next states)
   - Agent assignment dropdown
   - Acceptance criteria display
   - Activity timeline (chronological events)
   - Linked sessions list (placeholder — populated in Phase 4)
   - Reviews section (placeholder — populated in Phase 7)
   - Artifacts section (placeholder — populated in Phase 8)
   - Source plan provenance link

6. **Task creation from UI**
   - `POST /api/tasks` — create a standalone task (not from plan)
   - Simple form: title, contents, status, agent, repo path, tags

### Acceptance Criteria
- Tasks visible on Kanban board grouped by status
- Filters narrow displayed tasks correctly
- Status transitions validated; invalid transitions rejected
- Every status change creates an activity event
- Task detail shows full context: provenance, criteria, timeline
- Standalone task creation works from UI

### Files Created/Changed
- `src/server/routes/tasks.ts`, `src/server/routes/agents.ts`
- `src/server/domain/tasks.ts` (transition logic)
- `src/client/pages/TaskBoard.tsx`, `src/client/pages/TaskDetail.tsx`
- `src/client/components/KanbanColumn.tsx`, `src/client/components/TaskCard.tsx`

## Phase 4: Terminal Session Foundation

### Goal
Implement terminal session persistence, declaration via ingest, session-to-task linking, and display in the UI.

### Steps

1. **API routes for sessions**
   - `GET /api/sessions` — list sessions (filter by state, task)
   - `GET /api/sessions/:id` — session detail
   - `POST /api/sessions` — create/declare session
   - `PATCH /api/sessions/:id` — update session state/metadata
   - `POST /api/sessions/:id/link` — link session to task
   - `GET /api/sessions/:id/tasks` — tasks linked to this session

2. **Session ingest handler — `session.declared`**
   - Wire up the `session.declared` event processor
   - Insert into `terminal_sessions` table
   - If `primary_task_id` set, also create `task_session_links` row with role `primary`
   - Insert activity event

3. **Task-session link ingest — `task.session_linked`**
   - Wire up the `task.session_linked` event processor
   - Insert `task_session_links` row
   - Enforce unique constraint on (task_id, session_id)
   - Insert activity event

4. **Session persistence**
   - Session metadata stored in SQLite (not just UI state)
   - On app reload, sessions are queryable from DB
   - Session state transitions: starting → running → exited/disconnected → archived
   - `last_seen_at` updated on heartbeat/activity

5. **UI: Session list on Task Detail**
   - Task detail page shows linked sessions with role badges
   - Session cards: title, state, shell, cwd, branch, last seen
   - Click to navigate to session (workspace view — Phase 5)

6. **UI: Session count on Task Cards**
   - Kanban task cards show linked session count badge

### Acceptance Criteria
- Sessions created and persisted in SQLite
- Session declaration via ingest works
- Sessions persist across app refresh
- Task can have multiple linked sessions with different roles
- Task detail shows all linked sessions
- Task cards show session count

## Phase 5: Browser Terminal Workspace

> **Status (2026-04-07):** Deferred indefinitely. This phase was deprioritized as lowest ROI during v0.0.3 implementation. The v0.0.5 plan proposes replacing the xterm.js/node-pty approach entirely with tmux sessions + a WebSocket bridge, making this phase obsolete. Skip to v0.0.4 (issue editing + DnD) instead.

### Goal
Build the tabbed terminal workspace with xterm.js, allowing users to open, switch, and restore terminal sessions.

### Steps

1. **Server: PTY management**
   - Install `node-pty`
   - `POST /api/sessions/:id/spawn` — spawn a PTY process for a session
   - WebSocket endpoint for terminal I/O (`/ws/terminal/:sessionId`)
   - Handle PTY output → WebSocket → xterm.js
   - Handle xterm.js input → WebSocket → PTY stdin
   - Track PTY lifecycle, update session state accordingly

2. **Server: Session reconnection**
   - On disconnect, session moves to `disconnected` state
   - On reconnect, reattach to existing PTY if still alive
   - `reconnect_token` generated on session creation for secure reattach
   - If PTY exited while disconnected, update to `exited` state

3. **Optional scrollback persistence**
   - Write scrollback to `<app-data>/sessions/<session-id>/scrollback.log`
   - On reconnect, serve last N lines of scrollback for context
   - `meta.json` stores session metadata snapshot

4. **Client: Terminal Workspace page**
   - Route: `/terminal` or `/workspace`
   - Tabbed interface: each tab = one terminal session
   - Tab shows: session title, linked task badge, state indicator
   - Active tab renders xterm.js terminal
   - Tab bar controls: new session, close tab, reorder

5. **Client: xterm.js integration**
   - Install `xterm`, `xterm-addon-fit`, `xterm-addon-web-links`
   - Connect xterm instance to WebSocket
   - Handle resize events → PTY resize
   - Handle disconnect/reconnect gracefully

6. **Client: Open session from Task Detail**
   - "Open Terminal" button on task detail
   - Creates or opens a session linked to the task
   - Navigates to workspace with that session's tab active

7. **Client: Session metadata panel**
   - Sidebar or panel showing session details: cwd, branch, shell, state, linked task, started at
   - Toggleable from workspace

### Acceptance Criteria
- User can open multiple terminal tabs
- Terminal sessions survive page refresh (session records persist; PTY reconnect if alive)
- Task-linked sessions openable from task detail
- Session state (running/disconnected/exited) accurately reflected
- Terminal I/O works over WebSocket
- Session metadata visible in workspace

### Files Created/Changed
- `src/server/terminal/pty-manager.ts`
- `src/server/terminal/ws-handler.ts`
- `src/server/routes/sessions.ts` (add spawn endpoint)
- `src/client/pages/TerminalWorkspace.tsx`
- `src/client/components/TerminalTab.tsx`, `src/client/components/TerminalTabBar.tsx`
- `src/client/components/XTerminal.tsx`
- `src/client/components/SessionMetadataPanel.tsx`

## Phase 7: Review Flow

### Goal
Implement the review lifecycle: requesting review, recording outcomes, and task state transitions based on review results.

### Steps

1. **API routes for reviews**
   - `POST /api/tasks/:id/reviews` — create a review
   - `GET /api/tasks/:id/reviews` — list reviews for a task
   - `GET /api/reviews/:id` — review detail

2. **Review ingest handlers**
   - `review.requested` → set task status to `needs_review`, set `reviewer_agent_id`
   - `review.completed` → insert `reviews` row, apply outcome:
     - `approved` → transition task to `succeeded`
     - `changes_requested` → transition task to `ready` or `blocked`
     - `blocked` → transition task to `blocked`

3. **Review outcome transitions**
   - Task must be in `needs_review` to receive a review
   - Review outcome determines next task state
   - Multiple reviews per task allowed (e.g., re-review after changes)
   - `review_outcome` field on task updated to latest

4. **Client: Review section on Task Detail**
   - List of reviews with: reviewer, type (standard/adversarial/human), outcome, summary, date
   - Expandable details (findings, etc.)
   - Current review state badge on task

5. **Client: Review actions**
   - "Request Review" button on eligible tasks (status = `running` or `waiting`)
   - Manual review submission form (for human reviews)

6. **Activity logging**
   - Review requested → activity event
   - Review completed → activity event
   - Task transition from review → activity event

### Acceptance Criteria
- Task can enter `needs_review` state
- Review results stored and displayed on task detail
- `changes_requested` moves task back to `ready` or `blocked`
- `approved` moves task to `succeeded`
- Multiple reviews per task supported
- Review activity logged

### Files Created/Changed

- `src/server/domain/reviews.ts`
- `src/server/ingest/processor.ts` (wire up review events)
- `src/client/pages/TaskDetail.tsx` (add reviews section)
- `src/client/components/ReviewCard.tsx`, `src/client/components/ReviewForm.tsx`
