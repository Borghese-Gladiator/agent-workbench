# v0.0.5 Implementation Plan — Projects, Workflows, and Conversational UI

## Brief

Bridge the current task-management dashboard (v0.0.1–v0.0.4) toward the full ticket-to-PR workflow described in the v0.0.5 vision doc. This plan adds the **project model**, **workflow orchestration**, **conversational interface**, and **git worktree management** — the foundational layers that everything else (spec-kit, Agent Teams, adversarial review) will plug into.

Scope is deliberately limited to what can be built on the existing Express + SQLite + React stack without introducing spec-kit (which is not yet stable enough to depend on). The orchestrator is designed so spec-kit can slot in later as a phase executor.

### What's NOT in v0.0.5
- Spec-kit integration (deferred to v0.0.7+ when spec-kit is stable)
- tmux / Agent Teams integration (deferred — requires terminal infra from Phase 5)
- Playwright MCP validation (deferred — nice-to-have, not foundational)
- Retrospective / meta-learning (deferred — polish)

### Prerequisites
- v0.0.4 Section 2 (Create Issues via UI) should be finished or skipped
- v0.0.4 Section 3 (Approve with Edits) and Section 4 (DnD) are partially implemented; this plan does not depend on them

## Phase 1: Projects Model

### Goal
Add projects as a first-class entity that groups issues, tasks, and workflows. Projects have a filesystem presence and a DB record.

### Schema

```sql
-- migration: 001_projects.sql
CREATE TABLE IF NOT EXISTS projects (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  slug TEXT NOT NULL UNIQUE,
  repo_path TEXT,
  description TEXT,
  status TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active', 'archived')),
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE INDEX idx_projects_slug ON projects(slug);
CREATE INDEX idx_projects_status ON projects(status);

-- Add project_id FK to existing tables
ALTER TABLE issues ADD COLUMN project_id TEXT REFERENCES projects(id);
ALTER TABLE tasks ADD COLUMN project_id TEXT REFERENCES projects(id);

CREATE INDEX idx_issues_project_id ON issues(project_id);
CREATE INDEX idx_tasks_project_id ON tasks(project_id);
```

## Phase 2: Workflow Runs (Orchestration Foundation)

### Goal
Add workflow runs — the entity that tracks a full "conversation → plan → tasks → execute → review → PR" pipeline. This phase builds the state machine and persistence; actual execution (launching agents, creating worktrees) comes in Phase 3–4.

### Schema

```sql
-- migration: 002_workflow_runs.sql
CREATE TABLE IF NOT EXISTS workflow_runs (
  id TEXT PRIMARY KEY,
  project_id TEXT REFERENCES projects(id),
  title TEXT NOT NULL,
  description TEXT,
  status TEXT NOT NULL DEFAULT 'pending' CHECK (
    status IN (
      'pending',          -- created, not started
      'specifying',       -- generating spec from input
      'planning',         -- generating plan from spec
      'awaiting_approval',-- plan ready, waiting for user
      'tasking',          -- breaking plan into tasks
      'executing',        -- agents working on tasks
      'reviewing',        -- adversarial review in progress
      'submitting',       -- creating PR
      'completed',        -- PR created or work done
      'failed',           -- step failed, can retry
      'canceled'          -- user canceled
    )
  ),
  current_step TEXT,      -- which step failed or is active
  input_text TEXT,        -- original user input / conversation
  spec_markdown TEXT,     -- generated specification
  plan_markdown TEXT,     -- generated plan
  error_message TEXT,     -- last error (for failed status)
  retry_count INTEGER NOT NULL DEFAULT 0,
  issue_id TEXT REFERENCES issues(id),       -- linked issue (created during tasking)
  pr_url TEXT,            -- draft PR URL when submitted
  created_by TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  started_at TEXT,
  completed_at TEXT
);

CREATE INDEX idx_workflow_runs_project_id ON workflow_runs(project_id);
CREATE INDEX idx_workflow_runs_status ON workflow_runs(status);
CREATE INDEX idx_workflow_runs_issue_id ON workflow_runs(issue_id);
```

### API

| Method | Route | Description |
|--------|-------|-------------|
| `GET /api/workflows` | List workflow runs | Filter: `?status=`, `?project_id=` |
| `POST /api/workflows` | Create workflow run | Body: `{ project_id?, title, input_text }` |
| `GET /api/workflows/:id` | Get workflow run detail | Includes linked issue, tasks |
| `PATCH /api/workflows/:id` | Update workflow fields | For manual spec/plan editing |
| `POST /api/workflows/:id/advance` | Advance to next step | Triggers the next phase of the pipeline |
| `POST /api/workflows/:id/approve` | Approve plan and advance | User approves the generated plan |
| `POST /api/workflows/:id/retry` | Retry from failed step | Re-attempts the current_step |
| `POST /api/workflows/:id/cancel` | Cancel the workflow | Sets status to canceled |

### State Machine

```
pending → specifying → planning → awaiting_approval → tasking → executing → reviewing → submitting → completed
                                                                    ↑                        |
                                                                    └── (changes_requested) ──┘
Any state → failed (on error)
Any state → canceled (user action)
failed → (retry from current_step)
```

### Domain Logic

`src/server/domain/workflow.ts` — thin orchestrator:

```typescript
// Advance the workflow to the next step
async function advanceWorkflow(workflowId: string): Promise<void> {
  const workflow = getWorkflow(workflowId);
  switch (workflow.status) {
    case 'pending':
      // Move to specifying — in v0.0.5, this is a no-op (user provides spec directly)
      // In v0.0.7+ with spec-kit, this calls speckit.specify()
      updateWorkflow(workflowId, { status: 'specifying' });
      break;
    case 'specifying':
      // Spec is ready (user edited it or it was auto-generated)
      updateWorkflow(workflowId, { status: 'planning' });
      break;
    case 'planning':
      // Plan is ready, wait for approval
      updateWorkflow(workflowId, { status: 'awaiting_approval' });
      break;
    case 'awaiting_approval':
      // User approved — break into tasks
      updateWorkflow(workflowId, { status: 'tasking' });
      // Create issue + task drafts from plan
      break;
    case 'tasking':
      // Tasks created — begin execution
      updateWorkflow(workflowId, { status: 'executing' });
      break;
    case 'executing':
      // All tasks done — trigger review
      updateWorkflow(workflowId, { status: 'reviewing' });
      break;
    case 'reviewing':
      // Review passed — submit PR
      updateWorkflow(workflowId, { status: 'submitting' });
      break;
    case 'submitting':
      updateWorkflow(workflowId, { status: 'completed' });
      break;
  }
}
```

## Phase 3: Git Worktree Management

### Goal
Manage git worktrees for task execution. Each task that enters `running` status gets an isolated worktree with its own branch.

### Design

- Worktrees live at `<repo>/.worktrees/<task-slug>/`
- Branch naming: `task/<task-id-short>/<slugified-title>` (e.g., `task/a1b2/add-auth-middleware`)
- Worktree lifecycle:
  - **Created** when task transitions to `running` (if repo_path is set)
  - **Kept** while task is active (running, waiting, blocked, needs_review)
  - **Cleaned up** on user request or when task is archived
- Worktree path is stored on the `tasks.worktree_path` field (already exists in schema)

### API

| Method | Route | Description |
|--------|-------|-------------|
| `GET /api/worktrees` | List active worktrees | Shows all worktrees with linked task/branch |
| `POST /api/tasks/:id/worktree` | Create worktree for task | Creates branch + worktree, updates task |
| `DELETE /api/tasks/:id/worktree` | Remove worktree | Cleans up worktree dir, nulls task field |
| `GET /api/worktrees/status` | Health check | Lists worktrees, flags orphaned ones |

### Domain Logic

`src/server/domain/worktrees.ts`:

```typescript
import { execSync } from 'child_process';

function createWorktree(repoPath: string, taskId: string, taskTitle: string): string {
  const slug = slugify(taskTitle);
  const shortId = taskId.slice(0, 8);
  const branchName = `task/${shortId}/${slug}`;
  const worktreePath = path.join(repoPath, '.worktrees', `${shortId}-${slug}`);
  
  // Create branch and worktree
  execSync(`git worktree add "${worktreePath}" -b "${branchName}"`, { cwd: repoPath });
  
  return worktreePath;
}

function removeWorktree(repoPath: string, worktreePath: string): void {
  execSync(`git worktree remove "${worktreePath}" --force`, { cwd: repoPath });
}

function listWorktrees(repoPath: string): WorktreeInfo[] {
  const output = execSync('git worktree list --porcelain', { cwd: repoPath });
  // Parse porcelain output
}
```

### Auto-creation hook

When a task transitions to `running` via `POST /api/tasks/:id/transition`:
1. If `task.repo_path` is set and `task.worktree_path` is null:
2. Create worktree automatically
3. Update `task.worktree_path` and `task.branch_name`
4. Log activity event

### UI

- **Worktree badge** on task cards (small icon showing worktree exists)
- **Worktree section** on task detail page: path, branch, creation date, cleanup button
- **Worktrees admin page** (`/worktrees`) — list all worktrees, orphan detection, bulk cleanup

## Phase 4: Conversational Interface

### Goal
Add a chat-based interface as the primary way to interact with the system. The user types naturally; the system interprets intent and creates the right entities.

### Design

For v0.0.5, this is a **simulated conversation** — the chat UI sends messages to the server, which stores them and presents a structured response. Actual AI-powered intent extraction (calling Claude to interpret messages) is wired in but behind a flag, since it requires an API key and adds latency.

Without AI: the chat is a structured command interface with shortcuts:
- `/create project <name>` → creates a project
- `/create issue <title>` → creates an issue
- `/status` → shows active workflows and tasks
- `/workflow <project> <description>` → starts a workflow

With AI (when `ANTHROPIC_API_KEY` is set): the chat sends the message to Claude for intent extraction, and Claude returns structured actions.

### Schema

```sql
-- migration: 003_conversations.sql
CREATE TABLE IF NOT EXISTS conversations (
  id TEXT PRIMARY KEY,
  title TEXT,
  project_id TEXT REFERENCES projects(id),
  workflow_run_id TEXT REFERENCES workflow_runs(id),
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE INDEX idx_conversations_project_id ON conversations(project_id);

CREATE TABLE IF NOT EXISTS conversation_messages (
  id TEXT PRIMARY KEY,
  conversation_id TEXT NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
  role TEXT NOT NULL CHECK (role IN ('user', 'assistant', 'system')),
  content TEXT NOT NULL,
  entities_created_json TEXT,   -- JSON array of { type, id } for entities created by this message
  metadata_json TEXT,           -- extra context (spec-kit phase, error info, etc.)
  created_at TEXT NOT NULL
);

CREATE INDEX idx_conversation_messages_conversation_id ON conversation_messages(conversation_id);
```

### API

## Phase 6: Agent Status Dashboard

### Goal
Real-time view of what each agent is doing. Agents already exist in the DB; this phase adds computed status and a dashboard.

### Design

Agent status is derived, not stored:
- **Idle**: no tasks in `assigned` or `running` status for this agent
- **Working**: has a task in `running` status
- **Assigned**: has tasks in `assigned` but none `running`
- **Reviewing**: has a task in `needs_review` where they are `reviewer_agent_id`

### API

| Method | Route | Description |
|--------|-------|-------------|
| `GET /api/agents/dashboard` | Agent status overview | Each agent with computed status, current task, recent activity |

### UI

- **Agent dashboard page** (`/agents`) — grid of agent cards
- Each card shows: name, kind, computed status, current task title (linked), last activity timestamp
- Status indicator: colored dot (green=working, yellow=assigned, blue=reviewing, gray=idle)

### Files

**Server:**
- `src/server/routes/agents.ts` — add `/dashboard` endpoint with computed status

**Client:**
- `src/client/pages/AgentDashboardPage.tsx`

### Acceptance Criteria
- [ ] Agent dashboard shows all agents with computed status
- [ ] Status updates when tasks transition
- [ ] Clicking agent card links to their active task
- [ ] Dashboard auto-refreshes (polling every 10s)

## Open Questions

1. **Migration runner**: Should we use a library (e.g., `umzug`) or write a simple one? **Recommendation**: Write a simple one — just read `.sql` files and track applied names in a `schema_migrations` table. Under 50 lines of code.

2. **Chat AI mode**: Should the Anthropic API key be configured in the UI or only via env var? **Recommendation**: Env var only for v0.0.5. UI config for API keys introduces security concerns.

3. **Worktree auto-creation**: Should it be opt-in (explicit API call) or automatic on `running` transition? **Recommendation**: Automatic when `repo_path` is set, with a way to disable per-task.

4. **Project slug generation**: Auto-generate from name (kebab-case) or let user specify? **Recommendation**: Auto-generate with option to override on creation.
