# Phase 9: Issue Editing, CLI Creation, Approve-with-Edits, and Drag-and-Drop (v0.0.4)

## Overview

This phase adds four capabilities that are missing from the current workflow:

1. **Edit issues** — modify draft issues (title, goal, task drafts) before or instead of approving
2. **Create issues via CLI** — a command-line tool to author issues without manually writing JSON
3. **Approve with edits** — approve an issue while simultaneously modifying its task drafts
4. **Drag and drop on the task board** — reorder and move tasks between Kanban columns

These are user-facing workflow improvements that build on the existing Phase 2 (Issues + Approval) and Phase 3 (Task Board) foundations.

---

## 1. Edit Issues (UI)

### Problem
Issues arrive via ingest as drafts, but the only actions are approve or reject. There is no way to fix a typo in a task title, adjust acceptance criteria, remove a bad draft, reorder tasks, or change the issue goal before approving.

### Design

**Issue-level edits (draft issues only):**
- Edit `title` and `goal` inline on the issue detail page
- Issue must be in `draft` status to be editable

**Task draft edits:**
- Edit `title`, `contents`, `acceptance_criteria`, `suggested_agent_id`, `tags_json` on each draft
- Reorder drafts (change `ordinal`)
- Delete individual drafts
- Add new drafts to an existing issue

**Activity logging:**
- Every edit creates an `issue.updated` or `draft.updated` activity event with a diff of changed fields

### API

| Method | Route | Description |
|--------|-------|-------------|
| `PATCH /api/issues/:id` | Update issue title/goal | Only when status=draft |
| `PATCH /api/issues/:id/drafts/:draftId` | Update a single task draft | Fields: title, contents, acceptance_criteria, suggested_agent_id, tags_json |
| `DELETE /api/issues/:id/drafts/:draftId` | Remove a draft from an issue | Recomputes ordinals |
| `POST /api/issues/:id/drafts` | Add a new draft to an issue | Generates draft_id, appends to end |
| `PUT /api/issues/:id/drafts/reorder` | Reorder drafts | Accepts `[{ draft_id, ordinal }]` |

### Editor: Monaco (`@monaco-editor/react`)

For editing longer text fields (goal, task descriptions, acceptance criteria), use Monaco Editor — the same editor engine as VS Code.

**Why Monaco over alternatives:**

| Option | Bundle | Shortcuts | Markdown | Verdict |
|--------|--------|-----------|----------|---------|
| **@monaco-editor/react** | ~40MB (async CDN load, no build impact) | Full VS Code keybindings: multi-cursor, find/replace, Ctrl+Z, etc. | Syntax highlighting built-in | **Recommended** |
| CodeMirror 6 | ~150KB | Standard editing; multi-cursor/find via extensions | Good via `@codemirror/lang-markdown` | Good lightweight alternative, but more assembly required |
| Tiptap (ProseMirror) | ~200KB | Rich-text shortcuts (Ctrl+B), not code-editor shortcuts | WYSIWYG, not source editing | Wrong paradigm — we want markdown source |
| Plain textarea | 0 | OS-native only (no multi-cursor, no find/replace) | None | Too basic for editing task descriptions |

**Why bundle size doesn't matter here:** This is a local dev tool, not a shipped production app. Monaco loads asynchronously from CDN by default — zero build-time impact. Even self-hosted, it's a single developer's machine.

**Usage pattern:**
- Short fields (issue title, task title): plain `<input>` — Monaco is overkill
- Long fields (goal, contents, acceptance_criteria): `<Editor language="markdown" />` with config:
  - `minimap: { enabled: false }`
  - `lineNumbers: "off"`
  - `wordWrap: "on"`
  - `scrollBeyondLastLine: false`
  - Height: auto-grow with content, min 80px, max 400px

### UI

- Issue detail page gets an "Edit" mode toggle (pencil icon) when status=draft
- In edit mode: short fields become editable inputs, long fields become Monaco editors
- Task drafts become a sortable list (drag handles for reorder)
- Each draft row has a delete button (with confirmation)
- "Add Task" button at bottom of draft list
- Save button persists all changes, Cancel discards
- Optimistic UI updates with React Query invalidation on save

### Future improvement: single-textarea draft editing

The current UI has separate title/contents/acceptance_criteria textareas per draft. A better UX would be a single markdown textarea per draft where the user writes everything in one place, with a convention like:

```
# Task title

Task description goes here...

## Acceptance Criteria
- criterion 1
- criterion 2
```

The system would parse this on save to extract the structured fields. This avoids forcing users to context-switch between multiple small textareas.

### Acceptance Criteria
- [x] Can edit issue title and goal on a draft issue
- [x] Can edit any field on a task draft
- [x] Can delete a task draft (with confirmation)
- [x] Can add a new task draft to an existing issue
- [x] Can reorder task drafts via drag or explicit controls
- [x] Edits are blocked on non-draft issues (approved/rejected/archived)
- [x] Activity events logged for every edit
- [x] Cmd+Enter saves, Esc cancels in edit mode

### Files

**Server:**
- `src/server/routes/issues.ts` — add PATCH, DELETE, POST, PUT endpoints
- `src/server/db/repositories/issues.ts` — add `updateIssue()` 
- `src/server/db/repositories/issue-task-drafts.ts` — add `updateDraft()`, `deleteDraft()`, `insertDraft()`, `reorderDrafts()`

**Client:**

## 2. Create Issues via UI and CLI

> **Status (2026-04-07):** Not yet implemented. This is the next feature to build.

### Problem
Issues currently can only be created by dropping a valid JSON envelope into `.taskboard/inbox/`. There is no "Create Issue" button in the UI and no CLI tool. Writing JSON by hand is tedious and error-prone.

### UI: "New Issue" button on Issues page
- Add a "New Issue" button to the IssuesPage (matching the "+ New Task" pattern on TasksPage)
- Form fields: title, goal, and one or more task drafts
- Requires `POST /api/issues` endpoint (below)
- Created issues arrive in `draft` status, ready for editing/approval

### CLI

### Design

A Node.js CLI script (`bin/taskboard`) that supports issue creation:

```bash
# Interactive mode — prompts for title, goal, then tasks one at a time
npx taskboard issue create

# One-shot with args
npx taskboard issue create \
  --title "Implement auth" \
  --goal "Add JWT-based authentication" \
  --task "Create JWT middleware" \
  --task "Add login endpoint" \
  --task "Add token refresh"

# From a markdown file (simple format: h1=title, blockquote=goal, checklist=tasks)
npx taskboard issue create --from issue.md

# From stdin (pipe from another tool)
echo '{"title":"...", "goal":"...", "tasks":[...]}' | npx taskboard issue create --json
```

**Output options:**
- `--ingest` (default): writes the `issue.proposed` JSON to `.taskboard/inbox/` for the watcher to pick up
- `--api`: POSTs directly to `POST /api/issues` (new endpoint, creates issue+drafts without ingest)
- `--dry-run`: prints the JSON envelope to stdout without writing

**Markdown format** (`--from`):
```markdown
# Issue Title

> Issue goal description here

- [ ] First task title — task description
- [ ] Second task title — acceptance: criteria here
- [ ] Third task title @agent-id #tag1 #tag2
```

### API (new)

| Method | Route | Description |
|--------|-------|-------------|
| `POST /api/issues` | Create an issue + drafts directly | Bypasses ingest, same result as `issue.proposed` event |

### Implementation

- `bin/taskboard.ts` — CLI entry point using `commander` (or `yargs`)
- `bin/commands/issue-create.ts` — issue creation logic
- `bin/lib/markdown-parser.ts` — parse the simple markdown format into issue+tasks
- `bin/lib/envelope-writer.ts` — generate valid ingest JSON envelopes
- `package.json` — add `"bin": { "taskboard": "./bin/taskboard.ts" }` and `tsx` for execution

### Acceptance Criteria
- [ ] `npx taskboard issue create` with interactive prompts creates a valid issue
- [ ] `--task` flags create the correct number of drafts
- [ ] `--from issue.md` parses markdown into issue+drafts correctly
- [ ] `--ingest` writes to `.taskboard/inbox/` and watcher processes it
- [ ] `--api` posts directly to the server
- [ ] `--dry-run` outputs JSON without side effects
- [ ] Invalid input produces clear error messages

### Files
- `bin/taskboard.ts`
- `bin/commands/plan-create.ts`
- `bin/lib/markdown-parser.ts`
- `bin/lib/envelope-writer.ts`

## 3. Approve with Edits

### Problem
Currently approval materializes tasks exactly as drafted. If one draft has a bad title or missing criteria, you must either: (a) reject the whole issue, or (b) approve and then manually edit the created tasks. There should be a way to approve and apply edits atomically.

### Design

The approve endpoint accepts an optional `edits` payload — a map of draft IDs to field overrides. These overrides are applied to drafts in-memory before materialization. The original drafts in the DB are **not modified** (preserving the original proposal for audit), but the materialized tasks reflect the edits.

```json
POST /api/issues/:id/approve
{
  "approved_by": "user-1",
  "edits": {
    "<draft-id-1>": {
      "title": "Corrected title",
      "acceptance_criteria": "Updated criteria"
    },
    "<draft-id-2>": null  // null = skip this draft (don't materialize)
  }
}
```

**Rules:**
- Edits are optional — omitting `edits` or passing `{}` behaves exactly like today
- Setting a draft to `null` excludes it from materialization (soft-delete at approval time)
- Editable fields: `title`, `contents`, `acceptance_criteria`, `suggested_agent_id`, `tags_json`
- Ordinal and draft ID are not editable via this mechanism (use the edit issue APIs for that)
- Activity event for `issue.approved` includes the edits payload for audit

### UI

- On the issue detail page, when clicking "Approve", a modal/panel appears with each draft as an editable row
- User can inline-edit any field, or toggle a draft off (exclude from materialization)
- "Approve as-is" button skips the edit step (current behavior)
- "Approve with edits" button submits the edits payload

### Acceptance Criteria
- [ ] Approve with no edits works exactly as before (backwards compatible)
- [ ] Approve with field edits materializes tasks with the overridden values
- [ ] Approve with a draft set to `null` skips that draft
- [ ] Original drafts in DB remain unmodified
- [ ] Activity event records the edits applied
- [ ] UI provides an inline editing experience during approval

### Files

**Server:**
- `src/server/routes/issues.ts` — modify `POST /:id/approve` to accept and apply `edits`

**Client:**
- `src/client/pages/IssueDetailPage.tsx` — approval modal with editable drafts
- `src/client/components/ApproveWithEditsModal.tsx` — the approval editing UI

## 4. Drag and Drop on Task Board

### Problem
The Kanban board displays tasks in columns by status, but there is no way to move tasks between columns visually. Users must open the task detail and change the status manually. Drag and drop is the standard Kanban interaction.

### Design

**Drag between columns:**
- Dragging a task card from one column to another triggers a status transition
- The target column determines the new status:
  - If the column maps to a single status (Backlog→`backlog`, Ready→`ready`, Review→`needs_review`, Done→`succeeded`), use that status
  - If the column maps to multiple statuses (In Progress→`assigned`/`running`/`waiting`/`blocked`), default to `assigned` on drop (user can refine from task detail)
- Invalid transitions (per `ALLOWED_TASK_TRANSITIONS`) show an error toast — the card snaps back
- Successful transitions call `POST /api/tasks/:id/transition`

**Drag within a column (reorder):**
- Tasks within a column can be reordered by drag
- Requires a new `sort_order` field on the `tasks` table (integer, nullable, default null)
- Reorder calls a new `PUT /api/tasks/reorder` endpoint

### Library: `@dnd-kit/core` + `@dnd-kit/sortable` (recommended)

| Library | Bundle | Maintenance | Kanban Fit | Gotchas |
|---------|--------|-------------|------------|---------|
| **@dnd-kit/core + sortable** | ~12-15 kB gzip | Active, community-maintained | **Excellent** — `SortableContext` for within-column, `DndContext` + droppables for cross-column | Original author stepped back mid-2024; community maintains. Manual drop indicators needed. |
| @hello-pangea/dnd | ~30 kB gzip | Active (maintained fork of react-beautiful-dnd) | Good — fixes React 18 strict mode issues from the original | Larger bundle. API frozen to rbd's design, less flexible for custom behaviors. |
| pragmatic-drag-and-drop (Atlassian) | ~5-8 kB gzip | Active (powers Trello/Jira internally) | Good potential | Framework-agnostic — requires more React glue code. No built-in sortable abstraction. Docs still maturing. |
| react-beautiful-dnd | ~30 kB gzip | **Deprecated** (archived 2024) | Was the gold standard | React 18 strict mode broken. Do not use for new projects. |
| Native HTML5 DnD | 0 | N/A | **Poor** | No keyboard accessibility without massive custom work. Inconsistent cross-browser ghost images. Touch broken. |

**Recommendation: @dnd-kit.** Best balance of bundle size, Kanban-specific abstractions (`useSortable` + `useDroppable` map directly to the column/card model), built-in keyboard accessibility, and active maintenance. pragmatic-drag-and-drop is worth watching (smallest bundle, Atlassian backing) but requires more boilerplate for sortable lists today.

### API (new/modified)

| Method | Route | Description |
|--------|-------|-------------|
| `PUT /api/tasks/reorder` | Set sort order for tasks within a column | Accepts `[{ task_id, sort_order }]` |

Existing `POST /api/tasks/:id/transition` handles cross-column moves (already exists).

### Schema Change

```sql
ALTER TABLE tasks ADD COLUMN sort_order INTEGER DEFAULT NULL;
CREATE INDEX idx_tasks_sort_order ON tasks(sort_order);
```

### UI

- Wrap the Kanban board with `<DndContext>` from `@dnd-kit/core`
- Each column is a `<SortableContext>` (droppable)
- Each task card is a `<useSortable>` draggable
- Visual feedback: drag overlay (ghost card), drop indicator line, column highlight on hover
- Error state: toast notification on invalid transition, card animates back to original position
- Loading state: optimistic move, revert on API failure

### Acceptance Criteria
- [ ] Can drag a task card from one column to another
- [ ] Drop triggers the correct status transition via API
- [ ] Invalid transitions show an error and snap back
- [ ] Can reorder tasks within a column by dragging
- [ ] Drag shows a ghost card overlay
- [ ] Drop targets highlight on hover
- [ ] Works with filtered views (filters remain applied after drag)
- [ ] Keyboard accessible (dnd-kit provides this)

### Files

**Server:**
- `src/server/db/schema.sql` — add migration for `sort_order` column
- `src/server/routes/tasks.ts` — add `PUT /reorder` endpoint

**Client:**
- `src/client/pages/TasksPage.tsx` — wrap with DndContext, handle drag events
