# v0.3.4 — Trim Adversarial Review Comment to Task-Specific Content

## Brief

The system comment auto-generated on the `in_review` transition (shipped in v0.3.3) currently uses a rigid template with placeholders (`[risk area 1]`, `[constraint 1]`, `Working directory: <fill in worktree path>`, etc.). In practice those placeholders are never filled — the user just edits or deletes them before sending. Every comment ends up looking identical.

v0.3.4 replaces the template with a **barebones, task-specific comment**: the invocation line, the task title, and the task's acceptance criteria when present. No placeholder scaffolding, no fabricated focus areas, no `<fill in worktree path>`, no hand-wavy "Constraints / Prefer" buckets.

The comment is meant to *seed* the review — it should contain only the things that are genuinely specific to this task. Anything the reviewer model would invent anyway (edge cases, ship-blockers, simpler alternatives) is left to the slash command itself.

### Motivation

- The current template is boilerplate that repeats verbatim on every task. It adds visual noise without adding information.
- The "Focus on" and "Constraints" sections are *pretending* to be task-specific but are actually `[risk area 1]` placeholders. That's worse than omitting them — it implies the system knew something it didn't.
- The `Working directory: <fill in worktree path>` line is always the literal placeholder string, because v0.3.3 explicitly decided not to infer a path. Shipping a literal `<fill in worktree path>` is worse than omitting the line.
- Keeping the comment short makes the "Send to terminal" path cleaner: what gets pasted is exactly what the user wants to run, minus their own edits.

### Non-goals

- No change to the transition trigger, the comment author (`adversarial-review-bot`), the Copy / Send-to-terminal buttons, or the `POST /api/sessions/:id/paste` endpoint.
- No smart risk-area inference (that would require model calls — out of scope).
- No change to the `reviews` table or the review outcome flow.
- No change to other system-authored comments (none exist today; this is just scoping).

## Design

### New template

Exact output for a work item with acceptance criteria:

```
/codex:adversarial-review --base main challenge whether this was the right approach for <title>.

Acceptance criteria:
<acceptance_criteria>
```

Exact output when `acceptance_criteria` is null or blank:

```
/codex:adversarial-review --base main challenge whether this was the right approach for <title>.
```

That's the whole thing. No task description dump (the slash command has the branch and the reviewer will look at the diff — we don't need to echo the body into a prompt). No branch line (it's embedded in the worktree the reviewer is running in). No working-directory placeholder. No focus/constraints/prefer buckets.

**Substitution rules (unchanged from v0.3.3 where applicable):**

- `title`: trim, collapse internal `\r?\n` runs to a single space before substitution (it lives on the first line).
- `acceptance_criteria`: trim; when null or empty-after-trim, omit the entire `Acceptance criteria:` block **including the blank line that separates it from the invocation line**. The output ends at the invocation line's `.`.
- `--base main` stays a literal — no derivation from task data.
- The function signature (`ReviewPromptWorkItem`) stays the same for API stability, but `body` and `branch_name` become unused fields. Keep them in the type for now — removing them is a ripple into the call site in `work-items.ts`, and the next person to touch this module can drop them if they stay unused. (Alternatively: drop them now; see "Open question" below.)

### Why drop the body?

The task body is already visible one scroll up in the comment list (it's the top of the drawer / detail page). Re-pasting it into the review prompt means the reviewer model sees it twice and the user reads it twice. The `/codex:adversarial-review` slash command operates on a branch, not on prose — the body doesn't change what it inspects.

If the body turns out to matter, it can be added back trivially. Starting lean is the cheap direction.

### Why keep acceptance criteria?

Acceptance criteria *do* shape what "right" means for this task — they're the reviewer's success rubric. They're also typically short (1–3 lines) and explicitly task-specific, so they earn their place in the prompt.

### Why drop the branch line?

The v0.3.3 implementation emits `Branch: fix/login` or `Branch: (none — uncommitted work)`. In practice the `/codex:adversarial-review` command runs from a worktree that's *already* on the branch being reviewed — the reviewer doesn't need to be told the branch name, and the `(none — uncommitted work)` fallback is information-free noise.

### Why drop the "Focus on / Constraints / Prefer" buckets?

Each of those sections was a single real bullet (`correctness under edge cases`, `safer simpler alternatives`, `ship-blocking issues first`, `concrete examples of how the current approach could fail`) padded with `[risk area N]` and `[constraint N]` placeholders the user was expected to fill in.

In practice:
- The one-sentence `/codex:adversarial-review` slash command definition already encodes "look for ship-blockers, edge cases, simpler alternatives" — we don't need to re-teach the model those priors in every invocation.
- The user never fills in `[risk area 1]` — they either delete the placeholders or send the prompt as-is. Either way the buckets add no signal.

If a specific task truly needs focus steering, the user can type it after the invocation line before sending. The default comment stays clean.

### Template module shape

**File:** `src/server/domain/review-prompts.ts` (existing)

```ts
export interface ReviewPromptWorkItem {
  id: string;
  title: string;
  body: string;            // now unused; kept for API stability
  acceptance_criteria: string | null;
  branch_name: string | null; // now unused; kept for API stability
}

export function renderAdversarialReviewPrompt(workItem: ReviewPromptWorkItem): string {
  const title = workItem.title.replace(/[\r\n]+/g, " ").trim();
  const criteria = (workItem.acceptance_criteria ?? "").trim();

  const invocation = `/codex:adversarial-review --base main challenge whether this was the right approach for ${title}.`;

  if (!criteria) return invocation;

  return `${invocation}

Acceptance criteria:
${criteria}`;
}
```

No other files need logic changes. The call site in `src/server/routes/work-items.ts` already passes the full `ReviewPromptWorkItem` and doesn't care that two of the fields stop being consulted.

### Open question — drop unused fields?

Option A (recommended): leave `body` and `branch_name` on `ReviewPromptWorkItem`. One call site, negligible cost, preserves a clean re-introduction path if we ever want them back.

Option B: remove them from the type and from the call site's argument object. Tighter, but burns churn in `work-items.ts:168–174` for no immediate gain.

Proceeding with **Option A** unless instructed otherwise during implementation.

## Changes

### 1. `src/server/domain/review-prompts.ts`

- Replace the current template body of `renderAdversarialReviewPrompt` with the logic above.
- Leave `ReviewPromptWorkItem` exported shape unchanged.

### 2. `src/server/domain/review-prompts.test.ts`

Rewrite the test cases to match the new template. Parametrized-style (simple `for…of` over a table) is preferred since there's only one rendering function. Cases:

| label | input overrides | expected output |
|---|---|---|
| populated with criteria | (baseItem) | invocation + blank line + `Acceptance criteria:` + criteria |
| null criteria | `acceptance_criteria: null` | invocation only (no blank line, no criteria section) |
| blank criteria | `acceptance_criteria: "   "` | invocation only |
| criteria with surrounding whitespace | `acceptance_criteria: "\n\n  Works.\n"` | criteria trimmed to `Works.` |
| title with embedded newlines | `title: "Fix\nlogin\r\nbug"` | first line reads `… approach for Fix login bug.` |
| title with surrounding whitespace | `title: "  Fix bug  "` | first line reads `… approach for Fix bug.` |

Drop the v0.3.3 assertions that looked for `Task description:`, `Working directory:`, `Branch:`, `Focus on:`, `Constraints:`, `Prefer:` — those strings must no longer appear in the output. Add a negative assertion verifying none of those substrings are present in the "populated" case.

Keep the test harness (manual `assertEqual` / `assertIncludes` with exit code) — there's no test framework in this repo and that matches the rest of the existing tests.

Add one `assertNotIncludes` helper (or inline the negative check) to assert the absence of `[risk area`, `[constraint`, `<fill in worktree path>`, `Task description:`, `Branch:` in the populated output.

### 3. `package.json`

- Bump `version` from `0.3.3` to `0.3.4`.

### 4. No other code changes

- `src/server/routes/work-items.ts` — unchanged; it already passes all four fields to `renderAdversarialReviewPrompt` and the function signature is preserved.
- `src/shared/constants.ts` — unchanged; `ADVERSARIAL_REVIEW_BOT_ID` still matters for the UI gating.
- Client components — unchanged. The Copy / Send-to-terminal buttons don't inspect the comment body shape.
- DB schema, migrations, API routes — unchanged.

### 5. Existing comments in the DB

Any comments already persisted from the v0.3.3 template stay as-is. Rewriting historical comments would be surprising (they're edit-capable by the user and may already carry their edits). The cutover is forward-looking: the next `in_review` transition produces the new shorter form.

### Manual (browser)

1. Start dev server (`npm run dev`).
2. Create a task **with** acceptance criteria. Drag to Review. Open drawer. Verify the new system comment body is exactly:
   ```
   /codex:adversarial-review --base main challenge whether this was the right approach for <title>.

   Acceptance criteria:
   <criteria>
   ```
   — no `Task description`, no `Working directory`, no `Branch`, no `Focus on`, no `Constraints`, no `Prefer`, no `[risk area]`, no `[constraint]`.
3. Create a task **without** acceptance criteria. Drag to Review. Open drawer. Verify the comment body is a single line:
   ```
   /codex:adversarial-review --base main challenge whether this was the right approach for <title>.
   ```
4. Task with acceptance criteria containing leading/trailing whitespace → rendered trimmed.
5. Task title with an embedded newline (paste one into the editor) → rendered with the newline collapsed to a space.
6. Click **Copy** on the new comment → clipboard contains exactly the rendered body (verify by pasting into a text editor — no trailing whitespace, no extra blank lines).
7. On a task with a linked running session, click **Send to terminal** → terminal receives the same exact string, Enter still not auto-pressed. Cursor lands at end of the last line.
8. Move task `in_review → in_progress → in_review` → a second short comment is created (v0.3.3 re-entry behavior still works).
9. Existing (pre-0.3.4) comments in the DB remain visible and unchanged.

## Risks

- **Template regression on copy/paste.** If the rendered string accidentally ends with an extra newline or leading space, the Send-to-terminal paste will look wrong. The unit tests pin exact strings — keep those snapshots.
- **Callers relying on deprecated fields.** None outside `work-items.ts`, and that one just forwards them. Grep confirms no other importers of `renderAdversarialReviewPrompt` before shipping.
- **User muscle memory.** Anyone who had internalized the v0.3.3 template shape may briefly be confused by the shorter comment. Mitigation: changelog entry / plan doc (this file) is the record.
