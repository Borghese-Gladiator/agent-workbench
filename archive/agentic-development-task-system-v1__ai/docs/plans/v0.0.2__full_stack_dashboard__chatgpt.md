# Agentic Development Task System (v0.0.2)

## Phased Full Implementation Plan

## 0. Product intent

Build a fully local, browser-based development task dashboard for Claude Code workflows.

The system should support:

* planner-generated plans
* dashboard approval of plans
* materialization of approved plan items into flat tasks
* task tracking in a Kanban-style board
* long-lived terminal sessions
* reconnectable terminal tabs
* multiple terminal tabs per task
* association between tasks and Claude/terminal sessions
* local JSON ingest from repo directories
* activity history and review flow
* adversarial review as a skill-driven task transition, not as workflow-engine infrastructure

The system is explicitly **not** a general workflow engine and should avoid retry logic, distributed execution, or DAG orchestration.

---

# 1. Core product decisions

## 1.1 Key principles

* Fully local-first
* Browser UI backed by a local service
* JSON ingest is the canonical input mechanism
* Plans are separate from tasks
* Tasks remain flat
* Terminal sessions are first-class and reconnectable
* A task may reference multiple terminal sessions
* Approved plans materialize tasks
* Review is implemented as a task transition plus stored review data
* Activity log is immutable and append-only

## 1.2 Scope boundaries

Include:

* plan ingest and approval
* task board
* task detail
* terminal workspace
* session/task linkage
* local event ingest
* review state transitions
* SQLite persistence

Exclude:

* retries
* distributed execution
* remote multi-user sync
* background queue orchestration
* workflow graph builder
* subtask hierarchy
* cloud storage
* generalized plugin marketplace

# 3. Lifecycle model

## 3.1 Plan lifecycle

States:

* `draft`
* `approved`
* `rejected`
* `archived`

Flow:

1. planner emits a proposed plan via JSON ingest
2. system stores the plan and proposed task drafts
3. dashboard displays the plan for approval
4. user approves or rejects
5. if approved, proposed task drafts are materialized into flat tasks
6. plan remains as provenance for created tasks

## 3.2 Task lifecycle

States:

* `backlog`
* `ready`
* `assigned`
* `running`
* `waiting`
* `blocked`
* `needs_review`
* `succeeded`
* `failed`
* `canceled`
* `archived`

Transitions should be explicit and persisted as events.

## 3.3 Terminal session lifecycle

States:

* `starting`
* `running`
* `exited`
* `disconnected`
* `archived`

Behavior:

* sessions are long-lived
* sessions can be reattached after page reload
* multiple sessions may be linked to one task
* a session may optionally have a “primary task”
* a task detail page should display all linked sessions

# 6. Local ingest directory structure

The system should support repo-local ingest and app-local storage.

## 6.1 Repo-local ingest structure

For each tracked repo:

```text
<repo>/
  .taskboard/
    inbox/
    processed/
    rejected/
    attachments/
```

### Semantics

* `inbox/`: new JSON files waiting for ingest
* `processed/`: accepted JSON files moved here after successful ingest
* `rejected/`: invalid JSON files moved here after failed validation or ingest
* `attachments/`: optional task/plan-related artifacts referenced by ingest events

## 6.2 App-local storage structure

```text
<app-data>/
  db/
    taskboard.sqlite
  sessions/
    <session-id>/
      meta.json
      scrollback.log
  logs/
  cache/
```

### Semantics

* `db/`: SQLite database
* `sessions/`: per-terminal-session metadata and optional persisted scrollback
* `logs/`: local service logs
* `cache/`: temporary derived data

## 6.3 File naming conventions

Use timestamped plus UUID naming:

```text
2026-03-31T21-10-44Z__plan-proposed__<uuid>.json
2026-03-31T21-15-10Z__task-updated__<uuid>.json
2026-03-31T21-17-02Z__review-completed__<uuid>.json
```

This improves manual inspection and ordering.

# 8. Plan approval and task materialization flow

## 8.1 Plan ingestion

1. ingest service watches all configured repo `.taskboard/inbox/` directories
2. when a new file appears, it validates schema
3. if valid and not previously processed, insert:

   * `plans`
   * `plan_task_drafts`
   * `activity_events`
   * `ingest_files`
4. move file to `.taskboard/processed/`

## 8.2 Plan approval

When a user approves a plan in the dashboard:

1. update `plans.status = 'approved'`
2. set `approved_at`, `approved_by`
3. for each `plan_task_drafts` row, create one flat `tasks` row
4. insert associated `task_tags`
5. insert one `activity_events` row for:

   * plan approved
   * each task created
6. dashboard refreshes task board

## 8.3 Plan rejection

When rejected:

1. update `plans.status = 'rejected'`
2. set `rejected_at`, `rejected_by`
3. create an activity event
4. no tasks are materialized

# 9. Terminal and session design

## 9.1 Requirements

* browser UI should show terminal tabs
* sessions must be reconnectable
* multiple tabs per task
* a task detail page should show all associated sessions
* the system should store Claude session identity when available
* session linkage should survive page reloads
* session metadata should be queryable from SQLite

## 9.2 Session ownership model

A session is independent from the task, but may be linked to one or more tasks.
A session may also declare a `primary_task_id`.

This supports:

* one task with several execution tabs
* one task with an execution tab and a review tab
* one task with exploration sessions
* reattaching the UI to known sessions later

## 9.3 Reconnect behavior

On app start:

1. load active terminal sessions from `terminal_sessions`
2. determine which are reconnectable
3. restore them to the UI model
4. task pages show linked sessions even before the user opens the tab again

If the underlying Claude session has a resumable ID, persist it in `claude_session_id`.

## 9.4 Scrollback persistence

For v1, persist metadata and optional scrollback log by session:

* store session metadata in SQLite
* optionally store terminal scrollback under app-local `sessions/<session-id>/scrollback.log`

# 11. Phased implementation plan

## Phase 1: repository, storage, and ingest foundation

### Goals

* establish local storage
* establish schema
* establish JSON ingest pipeline

### Deliverables

* initialize project structure
* create SQLite database and migrations
* implement the tables listed above
* implement ingest directory discovery for configured repos
* implement JSON validation pipeline
* implement processed/rejected file movement
* implement `ingest_files` deduping by file path and content hash
* implement `activity_events` creation for every accepted ingest event

### Acceptance criteria

* a valid `plan.proposed` file in `.taskboard/inbox/` becomes a stored plan
* invalid files move to `rejected/`

# 12. Query requirements

The system should support these common queries:

* all draft plans awaiting approval
* all tasks by status
* all tasks for a repo/worktree
* all tasks assigned to an agent
* all tasks created from a specific plan
* all sessions linked to a task
* all tasks linked to a session
* most recent activity events
* all reviews for a task
* all rejected ingest files

Example SQL patterns:

```sql
SELECT * FROM plans WHERE status = 'draft' ORDER BY created_at DESC;
```

```sql
SELECT * FROM tasks WHERE status = 'needs_review' ORDER BY updated_at DESC;
```

```sql
SELECT s.*
FROM terminal_sessions s
JOIN task_session_links l ON l.session_id = s.id
WHERE l.task_id = ?;
```

```sql
SELECT t.*
FROM tasks t
WHERE t.source_plan_id = ?
ORDER BY created_at ASC;
```

# 13. Validation rules

## 13.1 Ingest rules

* every ingest file must contain `event_id`, `event_type`, `occurred_at`, `payload`
* every `event_id` should be globally unique
* every file should be validated before any database write
* invalid files must be moved to `rejected/`
* accepted files must be moved to `processed/`
* duplicate content should not be ingested twice

## 13.2 Task rules

* tasks remain flat
* no parent-child task hierarchy
* `status` must be one of the allowed states
* tags stored both relationally and derivable from payload
* task provenance to a source plan is optional but should be preserved when present

## 13.3 Session rules

* a session may exist before linking to a task
* a task may have zero, one, or many sessions
* a session may declare a primary task
* a task/session link must be unique per pair
