# v0.3.6 — Mass task ingestion via a single CLI command

## Brief

Creating an epic's worth of tasks today means repeating `npm run ingest -- task --title "..." --epic-id $EPIC_ID --tags "..." --acceptance-criteria "..."` 10–15 times in a row. Every line repeats the same boilerplate (`npm run ingest -- task`, `--kind task`, the same `--epic-id`, the same actor/source), forces acceptance criteria onto one physical line, and — worst — leaves the inbox in a half-populated state if any single line errors.

v0.3.6 adds one new subcommand, `batch`, to the existing ingest CLI. It takes a **single JSON string** argument that describes the epic (optionally) and the list of tasks, and fans that into the same envelopes the per-task path already writes. The whole thing happens in one shell invocation that Claude Code assembles and runs. No files, no interactive prompts, no new server code.

### User stories

1. **As a user asking Claude to "break this epic into phase-A-through-E tasks"**, Claude runs a single `npm run ingest -- batch '<json>'` command and all 15 tasks (+ optional epic) land in the inbox atomically.
2. **As a user adding tasks under an existing epic**, Claude uses the same command with `"epic_id": "<uuid>"` at the top level and omits the `"epic"` block.
3. **As a user whose JSON had a typo in row 7**, the CLI validates every row *before* writing anything. It exits 1, prints all row-indexed errors at once, and the inbox is untouched.
4. **As a caller who prefers to pipe**, I can pass `-` as the JSON argument (or omit it) and the CLI reads the JSON payload from stdin.

### Non-goals

- **No file format.** The batch argument is JSON on the command line (or stdin), full stop. No YAML, no `.yaml` / `.json` path, no `drafts/` dir.
- **No new event types.** `batch` fans out into existing `work_item.created` / `epic.created` envelopes — one file per row in `data/ingest/inbox/`.
- **No bulk update / delete.** Create-only.
- **No inter-task dependencies.** No `depends_on`, no parent/child sugar.
- **No new arg-parsing or schema library.** Stays in `zod` + the existing hand-rolled parser.

## Design

### Why JSON-on-the-command-line (and not a file)

The file-based version of this plan was rejected — and it should be. The use case is "Claude Code has a structured breakdown in its head and needs to commit it to the board." A file is an extra artifact the user has to review, save, and clean up; it's also a second surface (skill-writes-file, CLI-reads-file) that can drift. A single CLI call is:

- **Directly invokable by Claude.** The Bash tool takes a command; a structured JSON string fits there cleanly. No Write+Bash pair.
- **Visible in the transcript.** The exact payload shows up in Claude's tool-use log and in the user's shell history. No "what was in that draft file again?" lookup.
- **Stateless.** Nothing to clean up after.
- **Reusable.** A human can also run it from a heredoc: `npm run ingest -- batch "$(cat <<'JSON' ... JSON)"` — but that's a convenience, not the primary path.

### Command shape

```
npm run ingest -- batch '<json-payload>'
npm run ingest -- batch -              # read JSON from stdin
npm run ingest -- batch                # also read from stdin (no positional arg)
```

Under the hood: `npx tsx src/cli/ingest.main.ts batch '<json-payload>'`.

The JSON argument is a **single positional argument** — not a `--flag` value. Rationale: the existing arg parser treats the first non-flag token after the subcommand as a positional. Adding a `--payload` flag would work too but buys nothing.

### Payload shape

```json
{
  "defaults": {
    "kind": "task",
    "tags": ["setup"],
    "actor_id": "claude-code",
    "actor_type": "agent",
    "source": "claude-skill"
  },
  "epic": {
    "title": "Poker game scaffold",
    "description": "Multi-phase breakdown for the poker-game repo.",
    "initiative_id": null
  },
  "tasks": [
    {
      "title": "Scaffold poker repo (client + server workspaces)",
      "tags": ["setup", "backend", "frontend"],
      "acceptance_criteria": "New repo poker-game/ with /server (Node+TS+Express+ws) and /client (Vite+React+TS). `npm run dev` starts both."
    },
    {
      "title": "Pick and install core deps",
      "tags": ["setup"],
      "acceptance_criteria": "Server: express, ws, zod, uuid, tsx.\nClient: react, react-router, zustand.\nShared: pokersolver for hand evaluation."
    }
  ]
}
```

**Top-level keys (all optional except `tasks`):**

| Key        | Type     | Notes                                                                                             |
| ---------- | -------- | ------------------------------------------------------------------------------------------------- |
| `defaults` | object   | Applied to every task row unless the row overrides. Keys match the row schema below.              |
| `epic`     | object   | If present, an epic envelope is built first; its generated `epic_id` becomes the default for rows. |
| `epic_id`  | string   | Shortcut: attach every task to an existing epic. Ignored if `epic:` is also present.              |
| `tasks`    | array    | Required, non-empty. Each row is a task / bug description.                                         |

**Row schema (`tasks[]`):**

| Key                   | Type            | Maps to CLI flag           | Notes                                       |
| --------------------- | --------------- | -------------------------- | ------------------------------------------- |
| `title`               | string          | `--title`                  | required                                    |
| `body`                | string          | `--body`                   |                                             |
| `kind`                | "task" / "bug"  | `--kind`                   | default `task`                              |
| `status`              | string          | `--status`                 | default `triage`                            |
| `epic_id`             | string (uuid)   | `--epic-id`                | overrides defaults and auto-generated epic  |
| `parent_id`           | string (uuid)   | `--parent-id`              |                                             |
| `tags`                | string[]        | `--tags`                   | merged with `defaults.tags` (row wins dupes) |
| `acceptance_criteria` | string          | `--acceptance-criteria`    | multi-line OK (it's JSON — embed `\n`)      |
| `branch_name`         | string          | `--branch-name`            |                                             |
| `assigned_agent_id`   | string          | `--assigned-agent-id`      |                                             |
| `actor_id`            | string          | `--actor-id`               |                                             |
| `actor_type`          | string          | `--actor-type`             |                                             |
| `source`              | string          | `--source`                 |                                             |

**Precedence for the task `epic_id`** (lowest → highest): `defaults.epic_id` < top-level `epic_id` < `epic.*`-generated UUID < row-level `epic_id`.

**Strict keys.** The zod schema is `.strict()` at every level — an unknown top-level or row-level key is a validation error. This catches silly typos (`"acceptanceCriteria"`) loudly. Exception: any row key starting with `_` is permitted and discarded, so callers can annotate rows (`"_phase": "A — skeleton"`) without a schema change.

### Ordering and atomicity

- **Epic first.** If `epic:` is present, its envelope is built, validated, and written before any task. If epic validation fails, no tasks are written.
- **All-or-nothing validation.** All task envelopes are built and zod-validated in memory *before* any write. Any error aborts the run with a single aggregated error message. **No half-written inbox.**
- **Input-order writes.** After validation passes, files are written in input order.
- **No rollback on disk error.** A filesystem write failure (disk full, permission) after validation is fatal. The CLI reports what was written and what wasn't and exits 1.

### Output

stdout: JSON, pretty-printed (matches today's CLI). New aggregate shape for `batch`:

```json
{
  "epic": {
    "file": "data/ingest/inbox/epic-poker-game-scaffold-4a1b2c3d.json",
    "entity_id": "4a1b2c3d-...",
    "event_type": "epic.created"
  },
  "tasks": [
    { "file": "...", "entity_id": "...", "event_type": "work_item.created" },
    { "file": "...", "entity_id": "...", "event_type": "work_item.created" }
  ],
  "summary": { "epics": 1, "tasks": 15 }
}
```

When `epic:` is omitted, `"epic": null`. Other subcommands (`task`, `epic`, `comment`) keep their existing `IngestResult` return shape — only `batch` returns the aggregate.

### Error reporting

```
Batch validation failed (3 errors):
  epic.title: Required
  tasks[2].title: Required
  tasks[7].acceptance_criteria: Expected string, received array

No files written. Fix the errors and re-run.
```

Row errors are indexed by **0-based** position to match the input array. A two-pass approach (validate all, then write all) is what enables this.

### Payload size and shell limits

macOS `ARG_MAX` is ~1 MB; Linux is ~2 MB. A 50-task payload with generous acceptance criteria comes in well under 20 KB, so inline JSON is fine for realistic use. The **stdin mode** (`batch -` or `batch` with no positional) is the escape hatch for degenerate sizes or when shell escaping gets hairy — it's also the mode power-users will prefer with heredocs.

## Changes

### Phase 1: `batch` subcommand in `src/cli/ingest.ts`

**Files touched:** `src/cli/ingest.ts`, `src/cli/ingest.main.ts`, `src/cli/ingest.test.ts`.

**Arg parser update (`parseArgs`)**. The existing parser expects `subcommand` followed by `--flag value` pairs only. Extend it minimally: after the subcommand, collect any leading *non-flag* tokens into a `positional: string[]` array on the returned `ParsedArgs`. Flag parsing stays as-is. This is a tiny change (~5 lines) and unlocks `batch '<json>'` without special-casing.

**New zod schema `BatchPayloadSchema`** in `ingest.ts`:

- `z.object({ defaults, epic, epic_id, tasks }).strict()` at top level.
- `defaults` and each `tasks[]` entry are `.strict()` too, with a `.passthrough()`-style exception only for keys matching `/^_/`.
- `tasks` is `z.array(...).min(1)`.
- `epic` validation just needs `title`; `description` / `initiative_id` are optional.

**New exported function `runBatch(payload: unknown, rootDir: string): BatchIngestResult`:**

1. Parse `payload` through `BatchPayloadSchema`. Collect all zod issues into a single formatted error if parsing fails.
2. If `epic:` present → call existing `buildEpicEnvelope` with the epic's fields merged with `defaults` (only `actor_id` / `actor_type` / `source` apply to epics). Keep its UUID.
3. Determine effective `epic_id` for tasks: `epic.*`-generated UUID if present, else top-level `epic_id`, else `defaults.epic_id`, else null. Row-level `epic_id` still wins per row.
4. For each task row: flatten `defaults` + row into a flat `flags` record (keys converted to kebab-case to match the existing `buildTaskEnvelope` flag names), then call `buildTaskEnvelope`. Collect every result.
5. Run `validateEnvelope` on every built envelope. Accumulate errors with `tasks[i].<field>` paths. If any, throw a single aggregated `Error` with the full message. **No writes yet.**
6. Zero errors → `writeToInbox` for the epic (if any), then each task in order. Each `writeToInbox` re-validates cheaply — fine, keeps the single-envelope path honest.
7. Return `BatchIngestResult`.

**New exported helper `readJsonFromStdin(): unknown`** — for `batch -` / empty-positional mode. Synchronous read via `fs.readFileSync(0, "utf-8")` so the rest of the CLI stays sync. Parse with `JSON.parse`; surface a single clean error on parse failure.

**Dispatch update (`run`):**

```ts
case "batch": {
  const rawJson = positional[0] ?? "-";
  const jsonString = rawJson === "-" ? readJsonFromStdin() : rawJson;
  const payload = JSON.parse(jsonString);  // wrap with a clean error message
  return runBatch(payload, rootDir);
}
```

### Phase 2: `ingest.main.ts` usage banner

Update the file header comment to include:

npx tsx src/cli/ingest.main.ts batch -              # read JSON from stdin

### Phase 3: New Claude Code skill — `taskboard-mass-ingest`

**New file:** `.claude/skills/taskboard-mass-ingest.md`. Same shape as `taskboard-create-task.md`.

```markdown
---
name: taskboard-mass-ingest
description: Create an epic and a batch of tasks on the Agent Task System taskboard in one CLI call. Use when the user asks for a multi-task breakdown, a "phase A/B/C" scaffold, or >3 tasks at once.
---

Create an epic and/or multiple tasks in a single command.

## When to use
- User asks to create more than ~3 tasks at once.
- User asks for a phased / multi-step breakdown of an initiative.
- User provides a bulleted list of tasks and says "add these."

## Steps
1. Gather (from the conversation or by asking):
   - Whether to create a new epic or attach to an existing one (get its uuid).
   - The task list with title + tags + acceptance_criteria for each.
2. Assemble the JSON payload (see schema below). Put shared fields — `epic_id`, actor, source, common tags — in `defaults`.
3. Show the assembled JSON to the user in a fenced code block and ask for confirmation. Do NOT run the CLI before confirmation.
4. After confirmation, run:
   ```bash
   npm run ingest -- batch '<json-payload>'
   ```
   For payloads with tricky escaping, pipe via stdin instead:
   ```bash
   cat <<'JSON' | npm run ingest -- batch -
   { ... }
   JSON
   ```
5. Report the returned epic id (if any) and task count.

## Payload schema
- Top level: `{ defaults?, epic?, epic_id?, tasks: [...] }` — tasks required, non-empty.
- Task row: `{ title (required), body?, kind?, tags?, acceptance_criteria?, epic_id?, parent_id?, branch_name?, ... }`.
- `epic` block: `{ title (required), description?, initiative_id? }` — its generated UUID is used for every task below unless a row overrides.
- Row-level `epic_id` wins over `epic:`-generated UUID wins over top-level `epic_id` wins over `defaults.epic_id`.

## Defaults
- kind: task unless the user explicitly says bug
- status: triage (the CLI default)
- actor_id: claude-code
- source: claude-skill

## Guardrails
- Never run the CLI without showing the JSON first.
- If the batch would create >30 items, ask before proceeding.
- Do not mix `task` and `bug` kinds in one batch unless the user explicitly asks for it.
```

The skill is responsible for the *conversational* loop. The CLI stays mechanical.

### Phase 4: Tests

**Unit tests (`src/cli/ingest.test.ts`), new section `── runBatch ──`:**

- `runBatch` with just `tasks:` (no epic) → writes N files to tmp inbox, returns `epic: null`.
- `runBatch` with `epic:` + tasks → writes epic first; tasks' `epic_id` equals the generated epic UUID.
- `runBatch` with top-level `epic_id` and no `epic:` block → tasks get that `epic_id`.
- `runBatch` with row-level `epic_id` overriding `defaults.epic_id` → row wins.
- `defaults.tags` merged with row `tags` → union, preserving order.
- `runBatch` rejects empty `tasks: []`.
- `runBatch` rejects unknown top-level keys (e.g. `taks:`) with a helpful message.
- Row keys starting with `_` (e.g. `_phase`) are accepted and discarded.
- **Atomicity:** payload with one invalid row (missing `title`) → zero files written to the tmp inbox. Assert `fs.readdirSync` length is 0.
- Error aggregation: payload with three invalid rows → thrown error message mentions all three `tasks[i]` indices.
- `parseArgs` now returns a `positional` array — verify on simple and mixed inputs.
- `run(["batch", "<valid-json>"], tmpDir)` end-to-end → returns `BatchIngestResult`, files on disk.

**Manual tests:**

- [ ] Run `npm run ingest -- batch '<poker-payload>'` (from the issue example, ported to JSON) with dev server running → epic + all ~15 tasks appear on the board under Triage, linked to the new epic.
- [ ] Introduce a typo in one row's `title` (remove it) → CLI exits 1, prints all errors, and `ls data/ingest/inbox/` shows no new files.
- [ ] Run with `-` and a heredoc → same behavior as inline JSON.
- [ ] Run with no positional arg and no stdin → CLI exits 1 with a usage error (not hang).
- [ ] Invoke the `taskboard-mass-ingest` skill in Claude Code on a fresh "break down an auth overhaul into 6 tasks" prompt → skill shows the JSON, waits for confirmation, runs the CLI, reports the epic id and count.
- [ ] Re-run the same payload → a *new* epic (new UUID) with a *new* set of tasks is created. Document in the skill: batch is create-only, not idempotent.

## Data flow

```
Claude Code / user assembles JSON payload
                │
                ▼
   npm run ingest -- batch '<json>'   (or stdin via `batch -`)
                │
                ▼
      JSON.parse → zod BatchPayloadSchema
                │
                ▼
  build epic (optional) + build every task envelope (in memory)
                │
                ▼
  validateEnvelope ×N  (all-or-nothing, aggregated errors)
                │
         any errors? ─── yes ──► exit 1, print all errors
                │
                ▼ all valid
  writeToInbox: epic first, then tasks in input order
                │
                ▼
  existing chokidar watcher picks up each file, processes via
  validator.ts → processor.ts → SQLite → board UI refresh
```

## Out of scope

- A file-based mode (`batch --file plan.yaml`). Explicitly rejected — the whole point is a single command.
- Bulk update (`work_item.updated`) or bulk delete.
- Inter-task dependencies (`depends_on`) or implicit parent/child from structural nesting.
- `--dry-run`. The all-or-nothing validate step already gives the user "would this run cleanly?" — a separate flag is a second code path for marginal gain.
- Importing from external formats (GitHub issues, Linear exports, etc.). Separate feature.
- A TUI / interactive wizard.

## Addendum (post-implementation) — skill layout fix and rename

After the initial v0.3.6 implementation shipped, the user reported that typing `/` did not surface any of the taskboard skills — `taskboard-create-task`, `taskboard-create-epic`, or the new `taskboard-mass-ingest`. The user also asked why no *delete* skills existed, and requested a rename of the mass-ingest skill.

### Root cause

Claude Code's project-level skill loader requires each skill to be a **directory** at `.claude/skills/<skill-name>/` containing a `SKILL.md` entrypoint. Loose markdown files at `.claude/skills/*.md` — which is what this project was using — are not picked up, so none of the taskboard skills appeared in the `/` slash-command menu or in the loaded-skills system reminder.

The v0.3.0 plan that originally introduced these skills called for `.claude/skills/create-task.md` (loose), and v0.3.6 followed the same (broken) pattern for `taskboard-mass-ingest.md`. This addendum corrects the layout for all taskboard skills.

### Changes in this addendum

1. **Rename** `taskboard-mass-ingest` → `bulk-create`. Shorter, no redundant `taskboard-` prefix on the marquee skill for this project.
2. **Restructure** each skill as a directory with `SKILL.md`:
   - `.claude/skills/bulk-create/SKILL.md` (content of the former `taskboard-mass-ingest.md`, updated references)
   - `.claude/skills/taskboard-create-task/SKILL.md`
   - `.claude/skills/taskboard-create-epic/SKILL.md`
3. **Add delete skills** (thin wrappers over the existing `delete-task` / `delete-epic` CLI subcommands that shipped earlier):
   - `.claude/skills/taskboard-delete-task/SKILL.md`
   - `.claude/skills/taskboard-delete-epic/SKILL.md`
4. **Remove the old loose `.md` files** at `.claude/skills/` root once the directory versions are verified. (Subject to confirmation — see cleanup note below.)
5. **Cross-link** `taskboard-create-task` → `bulk-create` and `taskboard-create-epic` → `bulk-create` in each skill's "When to use" so Claude routes batch requests to the right skill.

### Delete-skill scope

Intentionally minimal — each is a 30-line wrapper: *gather the UUID, confirm with the user, run the CLI, report the result*. Key guardrails:

- **`taskboard-delete-task`** — ask for confirmation showing the UUID + title before running `delete-task --work-item-id <uuid>`. If the user asks to delete multiple, surface the "one at a time" limitation rather than silently looping.
- **`taskboard-delete-epic`** — additionally warn about orphaning tasks that still reference the epic, and offer to delete those separately.

Neither skill does cascade deletion. That would be a v0.3.7+ CLI feature (`delete-epic --cascade`), not a skill-side concern.

### Verification

After writing each `SKILL.md`, Claude Code's loaded-skills list (surfaced in the system-reminder that follows any file write under `.claude/skills/`) confirmed each skill registered by name. The loose `.md` versions never appeared in that list, confirming they were dead weight.

### Follow-up rename: drop the `taskboard-` prefix

After the first addendum shipped with names like `taskboard-create-task`, `taskboard-create-epic`, `taskboard-delete-task`, `taskboard-delete-epic`, the user pointed out the prefix was redundant: this repo's `.claude/skills/` is already scoped to the taskboard project, so prefixing every skill with `taskboard-` just lengthens every invocation without adding signal. `bulk-create` already set the shorter-name precedent.

Renamed to the short forms:

| Before                      | After          |
| --------------------------- | -------------- |
| `taskboard-create-task`     | `create-task`  |
| `taskboard-create-epic`     | `create-epic`  |
| `taskboard-delete-task`     | `delete-task`  |
| `taskboard-delete-epic`     | `delete-epic`  |
| `bulk-create` *(unchanged)* | `bulk-create`  |

Changes applied:
- Directory renames (`git mv`) so history is preserved for each SKILL.md.
- `name:` field in each frontmatter updated to match the new directory name.
- Cross-references inside SKILL.md bodies updated (`/taskboard-create-task` → `/create-task`, `/taskboard-delete-task` → `/delete-task`).
- Historical sections earlier in this plan (Phase 3 and the first addendum body) intentionally left with the old names — they document what was shipped at the time.

### Lesson for future v0.x.y plans

Any new project-level skill added in this repo (or any docs pointing to one) must use the directory + `SKILL.md` layout. Loose markdown files in `.claude/skills/` do not register with Claude Code's skill loader. The prior convention from v0.3.0 was a bug, fixed here.

Secondary lesson from the follow-up rename: in a single-purpose project skills directory, **don't prefix skill names with the project domain** — the directory scopes that already. `create-task` is clearer than `taskboard-create-task` when the user types `/`.
