# v0.3.8 — Board ergonomics: inline edit, keyboard nav, command palette, awaiting-input badges

## Brief

Today the board is a *viewer*. Every edit, creation, or navigation round-trips through either a terminal (`npm run ingest -- …`) or a modal-less drawer that only reads. The UI has the data, React Query is already wired, and the server already exposes `POST /api/work-items`, `PATCH /api/work-items/:id`, `POST /api/work-items/:id/transition`, `POST /api/epics`, etc. — the plumbing is there; the surface isn't.

v0.3.8 adds the four highest-ROI ergonomics improvements against that existing plumbing:

1. **Inline editing on the board + drawer** — click a card's title, tags, or status chip; edit in place; save via existing `PATCH /api/work-items/:id`.
2. **Keyboard navigation with arrow keys + Enter to edit** — `j/k/↑/↓` moves between cards in a column, `h/l/←/→` moves between columns, `Enter` enters edit mode on the selected card's title, `Escape` exits.
3. **Command palette (`⌘K` / `Ctrl+K`)** — a global modal, triggered by a new navbar button *and* the keyboard shortcut, that lets the user search for and jump to any work item / epic, or fire "New task" / "New epic" actions that POST directly. Replaces the mandatory terminal round-trip.
4. **Awaiting-input notification on tasks** — a persistent badge and board-wide counter when a terminal session backing a task is idle waiting on Claude prompting the user. Wires the already-present `work_items.awaiting_input` column (currently 0 for everything, consumed by no one) to a real path: Claude Code (via the existing ingest pipeline) writes the flag on; the UI pulses the card; clicking clears it.

### User stories

1. **As a user with a typo in a task title**, I click the title on the card, type the fix, press Enter, and it saves. No drawer, no dialog, no terminal.
2. **As a user driving the board without the mouse**, I press `j`/`k` to move down/up a column, `h`/`l` to switch columns, `Enter` to edit the current card's title, `n` to create a new task, `e` to create a new epic, `⌘K` to open the palette, `?` to see the shortcut list.
3. **As a user who can't remember what I was working on**, I press `⌘K`, type two words from the title, arrow-down to the match, hit Enter, and land on that task's detail view.
4. **As a user creating a one-off task**, I click the new `⌘K` button at the top-right of the navbar, pick "New task", fill the inline form (title + epic + tags), and the task appears in Triage without opening a terminal.
5. **As a user who left Claude Code running inside a task session and stepped away**, I see a pulsing dot on the card (and a count in the navbar) the instant Claude blocks on a question. I click in, answer Claude, the dot clears.

### Non-goals

- **No UI delete.** Deletes stay the v0.3.5 ingest-CLI path. Inline editing is about correcting live data, not removing it.
- **No multi-select / bulk edit.** One card at a time.
- **No rich-text editor for `body`.** The drawer's description stays a `<textarea>`. Body editing is in scope; rich formatting is not.
- **No "offer to open a terminal on transition" flow** (originally item #8 in the brainstorm). Explicitly descoped.
- **No push notifications / OS-level alerts / sound** for awaiting-input. In-UI badges + tab-title counter only.
- **No drag-to-reorder in the command palette.** Reordering stays on the board.
- **No new event types in the ingest schema for awaiting-input.** The existing `work_item.updated` envelope already covers `awaiting_input` via `updateWorkItem`; the only wiring needed is the client pass-through and a short-form ingest CLI helper.
- **No server WebSocket push for awaiting-input.** v0.0.9 established the websocket broadcast pattern; this plan *emits* on that channel but does not change the channel. If the current wiring already rebroadcasts `work_item.updated`, no server change is required beyond verifying it.

## Design

### 1. Inline editing

#### What becomes editable

| Surface | Field | Edit control | API |
| --- | --- | --- | --- |
| Card on board | `title` | `<input>` swap on click | `PATCH /api/work-items/:id { title }` |
| Drawer header | `title` | same as card | same |
| Drawer description | `body` | `<textarea>` swap on click | `PATCH /api/work-items/:id { body }` |
| Drawer tags | `tags` | chip editor (add/remove) | `PATCH /api/work-items/:id { tags }` |
| Card + drawer | `status` | status chip → popover with `validTransitions(current)` | `POST /api/work-items/:id/transition` |
| Drawer | `epic_id` | epic picker (dropdown over `useEpics()`) | `PATCH /api/work-items/:id { epic_id }` |
| Drawer | `assigned_agent_id` | agent picker | `PATCH /api/work-items/:id { assigned_agent_id }` |
| Drawer | `acceptance_criteria` | `<textarea>` | `PATCH /api/work-items/:id { acceptance_criteria }` |

Not editable inline (yet): `kind`, `parent_id`, `branch_name`, `sort_order`, `priority` (drag handles reorder; branch name edits via the CLI or terminal pane; kind is a creation-time decision).

#### Interaction model

- **Click to edit.** Single click on an editable field swaps to an input focused with the cursor at end-of-text. (Double-click is a common alternative but conflicts with drag-to-reorder — single click is fine because we'll guard against drag-in-progress using `@dnd-kit`'s `isSortableDragging`.)
- **Save on blur + Enter.** Tab-out or Enter commits; Escape cancels without saving.
- **Optimistic update.** `useMutation`'s `onMutate` sets the new value in the React Query cache; `onError` rolls back and shows a toast. The transition hook already invalidates `['work-items']` on success, so no manual refetch is needed.
- **Locking during drag.** When a card is being dragged (`activeId === item.id`), the title input is not mounted — dnd-kit's listeners own pointer events. Already naturally handled by stopping click propagation inside `SortableWorkItemCard`, which today calls `onCardClick` only when `!isSortableDragging`. Inline edit plugs into that same predicate.
- **Multi-line titles.** Keep titles single-line. A newline in the input submits (like Enter). The drawer description is the only multi-line field.

#### Component shape

New `InlineTextField` in `src/client/components/ui/InlineTextField.tsx`:

```tsx
<InlineTextField
  value={item.title}
  onSave={(next) => updateMutation.mutate({ id: item.id, title: next })}
  multiline={false}
  ariaLabel="Edit title"
  className="text-sm font-medium"
/>
```

Renders as a `<span>` in display mode, a `<textarea rows={1}>` (even for single-line — easier auto-resize than `<input>`) in edit mode. Keyboard: Enter commits (Shift+Enter inserts newline only when `multiline`), Escape reverts.

Also: `InlineTagEditor` for tag chips (typeahead against `useTags()`), `InlineStatusChip` for the status-popover, `InlineEpicPicker` over `useEpics()`. Each is ~40 lines.

Delete / resetting to empty: an empty title reverts with a toast "Title cannot be empty." Empty body / acceptance_criteria is allowed (persists as `null`).

### 2. Keyboard navigation

#### Focus model

A single `selectedCardId` lives in `BoardPage` state. When set:
- The card gets a 2px ring.
- The keyboard listener is active.
- The drawer is *not* auto-opened (selection ≠ open — `Enter` on a focused card opens the drawer; arrow keys alone just move focus).

Mouse interaction still works exactly as today. Clicking a card sets both `selectedCardId` and the drawer state (today's behavior preserved).

#### Shortcuts (all in document-level keydown handler in `BoardPage`, guarded by "is the user typing in an input?" check)

| Key | Action |
| --- | --- |
| `j` / `↓` | Select next card in current column |
| `k` / `↑` | Select previous card in current column |
| `h` / `←` | Select same-index card in column to the left (or last card if shorter) |
| `l` / `→` | Same, column to the right |
| `Enter` | If nothing selected: open first card in Triage. If selected and not editing: enter inline edit on the card's title. If editing: commit. |
| `Escape` | If editing: cancel edit. Else if drawer open: close drawer. Else: clear selection. |
| `Space` | Open drawer for selected card |
| `n` | Open command palette pre-seeded with "New task" |
| `e` | Open command palette pre-seeded with "New epic" |
| `/` | Focus the type filter (reuse existing filter UI) |
| `?` | Open a shortcut cheat-sheet modal |
| `⌘K` / `Ctrl+K` | Open command palette |

Guard: if `document.activeElement` matches `input, textarea, [contenteditable]`, *only* `Escape` and `⌘K` fire; everything else passes through. This is the standard approach and avoids stealing characters during inline edit.

#### Column-aware navigation math

The board already groups items into `COLUMNS` (`BoardPage.tsx:42`). A small helper `getAdjacent(selectedId, direction, grouped)` walks:

- `j/k`: same column, prev/next by current sort order.
- `h/l`: find the column index for `selectedId`, then the destination column, then clamp the row index to the destination column's length — 1. If the destination is empty, jump to the next non-empty column in that direction.

In epic-grouping mode, the grid is *rows of columns per epic*. `h/l` stays within the same epic row (left/right through columns within one epic); `j/k` walks down the column within the same epic, and wraps to the next epic's same column at the bottom. Wrapping behavior is a small call — we'll stop at the epic boundary on first release and revisit if it feels wrong.

### 3. Command palette

#### Where it lives

New top-right navbar button in `TopNav` (`App.tsx:28`), shaped like a VS Code command palette trigger: a `⌘K` badge + "Search or create…" placeholder text. Clicking it opens the palette. Also opens on `⌘K` / `Ctrl+K` from anywhere in the app (except when already in an input — then `⌘K` still works, because the guard above explicitly allows it).

Button markup lives in the existing navbar's right-side `flex-1` gutter; replace the empty spacer with a right-aligned block. Visually: rounded border, muted bg, mono font to match the logo label.

#### Palette shape

Full-screen `<Dialog>` (from `@radix-ui/react-dialog`, already in deps) with a top input and a scrollable result list.

```
┌────────────────────────────────────────────────────────────┐
│ >  fix login                              [Esc to close]   │
├────────────────────────────────────────────────────────────┤
│ ⚙  Create "fix login" as a new task                        │
│ ⚙  Create "fix login" as a new epic                        │
│ ─── Work items ──────────────────────────────────────────── │
│ 🐛 Fix login bug                           #a3f21c8   ready │
│ ✓  Fix login hover state                   #92ee110    done │
│ ─── Epics ────────────────────────────────────────────────── │
│ 📁 Online Poker Game                                        │
└────────────────────────────────────────────────────────────┘
```

Behavior:

- Input autofocuses on open.
- Results are a flat list of `Action` items. Each action has: `icon`, `label`, `group`, `shortcut?`, `onRun()`.
- Typing filters with substring match on `label` + `#<short-id>`. Scoring: exact short-id match > title-starts-with > title-contains > body-contains. Keep the implementation simple (sort-and-slice); no fuzzy-match library.
- `↑ / ↓` moves through results. `Enter` runs the highlighted action. `Escape` closes.
- First two rows are always "Create X as a new task / epic" when the input is non-empty — turns a failed search into a shortcut to create the thing you were looking for. These rows disappear when the input is empty.
- Groups: *Create* (top, conditional), *Work items*, *Epics*, *Pages* (Board / Tasks / Terminal / Activity — tiny navigational helper).

#### Creation form

Selecting "Create … as a new task" doesn't immediately POST; it swaps the palette into a **compact form** (still inside the same Dialog):

```
Create task
 Title        [ fix login                                    ]
 Epic         [ (none) ▾ ]
 Tags         [ frontend auth ×                              ]
 Kind         ( task ) ( bug )
                                      [ Cancel ] [ Create ]
```

`Enter` submits; `Escape` returns to the palette search view. Epic dropdown is populated from `useEpics()`. Tags is a comma-to-chip converter.

On submit:

- Task → `POST /api/work-items` with `{ kind, title, tags, epic_id?, status: 'triage' }`.
- Epic → `POST /api/epics` with `{ title, description? }`.

`useCreateWorkItem` already exists (`src/client/services/hooks.ts:110`); add `useCreateEpic` as a sibling — one-liner over the existing `POST /api/epics` route at `src/server/routes/epics.ts:23`.

After creation: toast "Created *fix login*"; close palette; optionally open the drawer for the new task if the user held Shift on Enter (nice-to-have, not MVP-blocking).

#### Why a palette and not a "+ New" button directly on the board

The user specifically asked for a palette-first design. Secondary benefit: the palette subsumes search, navigation, and creation in one surface. A `+ New` board button is a 10-minute addition later if anyone wants it, but it is redundant with the palette for the primary flow.

### 4. Awaiting-input notification

#### Data model

`work_items.awaiting_input` already exists (`src/server/db/schema.sql:63`). It's an `INTEGER NOT NULL DEFAULT 0` flag. No migration needed.

Currently no code writes to it and no UI reads it. This plan:
- **Client reads it** and renders a persistent dot.
- **Ingest CLI writes it** via a new tiny subcommand.
- **Claude Code hook** (downstream, documented only — not part of this plan's code) calls the CLI on `Stop` or `Notification` hook events.

#### Ingest CLI surface

```
npm run ingest -- set-awaiting --work-item-id <uuid> --awaiting true
npm run ingest -- set-awaiting --work-item-id <uuid> --awaiting false
```

Writes a `work_item.updated` envelope with `payload: { work_item_id, awaiting_input: true }`. `WorkItemUpdatedPayloadSchema` (in `src/shared/schemas.ts`) and `handleWorkItemUpdated` in `processor.ts` already handle arbitrary field updates — we just need to verify `awaiting_input` is in the allowed set. If it isn't, add it (it's one line — the schema is `.extend({ awaiting_input: z.boolean().optional() })`).

We use a dedicated subcommand rather than telling users to hand-author the envelope because:
- Claude Code hooks execute a literal shell command; short form is easier to embed.
- We can keep the primary `task` / `epic` create commands free of the awaiting flag. Set-awaiting is a different kind of operation (state toggle, not creation).

No client-side API for toggling the flag in this release — the signal is *from* Claude Code *to* the dashboard, one-way. A "mark as awaiting / cleared" UI button could come later but isn't needed for the loop.

#### Client rendering

**On the card:**

- A small pulsing amber dot at top-right of the card (next to the existing terminal icon) when `item.awaitingInput === true`.
- Tooltip: "Claude is waiting on input."
- If the card has a linked session, clicking the dot opens the terminal for that session (same as the existing terminal icon behavior), otherwise clicking opens the drawer.

**On the board header:**

- A small count chip next to the title, e.g. `Issues (2 awaiting)`, linking nowhere (purely informational). Hidden at zero.

**On the browser tab:**

- When any task has `awaiting_input = 1`, prefix the `document.title` with `(N) `. Clears when `N === 0`. Implementation: a `useEffect` in `BoardPage` keyed on the awaiting count.

**Auto-clear behavior:**

- Opening the task's drawer does **not** auto-clear. The signal is from Claude, not from user intent; only Claude should clear it (via another `set-awaiting --awaiting false` call from the hook on the next user-input event).
- Manual override: a "Clear awaiting" link appears inside the drawer when the flag is set. This is an escape hatch for when the Claude hook fails to clear. Hits the same ingest CLI path (surfaced as a client-side mutation that calls `PATCH /api/work-items/:id { awaiting_input: false }` — the PATCH route already accepts arbitrary fields).

#### Real-time delivery

Whether the badge appears instantly depends on the existing websocket/refetch wiring. `useWorkItems` has `refetchOnWindowFocus: false` and `staleTime: 5_000`, so polling alone would lag 5s. We'll verify whether the v0.0.9 WS rebroadcast already invalidates `['work-items']` on `work_item.updated`; if yes, nothing to do; if no, add the invalidation in the existing WS listener (out-of-scope code change, but worth a one-line audit during implementation). As a fallback, bump `useWorkItems` to `refetchInterval: 3000` *only when any item has `awaitingInput === true`* — a cheap way to get near-live without touching the WS layer.

#### Why a flag on the work item rather than on the session

`awaiting_input` already lives on `work_items`. Sessions have their own `state` column (`running`, `disconnected`, etc.), not an awaiting flag. Keeping the signal on the work item means:
- The board (which renders work items, not sessions) reads a local field.
- Tasks without a linked session can still be flagged (edge case: Claude is running in a detached terminal the dashboard never saw).
- Hooks can target `--work-item-id` without first resolving a session UUID.

If we later want a richer "which session is waiting" attribution, that's additive — we can add `awaiting_input_session_id` or similar without reworking the current surface.

        │
        ▼

        │
        ▼

## Risks

- **Click vs drag on cards.** The same region is both a drag handle and a click-to-edit target. The existing code already separates "click" from "drag" via `isSortableDragging`; inline edit plugs into the same guard. The risk is a brief flash of edit mode if the user starts an edit then drags — mitigated by blurring the input when a drag starts (listen on dnd-kit's `onDragStart` at the board level).
- **Keyboard shortcut conflicts.** `j/k/h/l` collide with some users' browser extensions (Vimium etc.). Mitigation: only fire when `document.activeElement === document.body` (or a known non-input container). Users who run Vimium on the board will get Vimium's behavior, not ours — acceptable since our arrow-key aliases still work.
- **Palette performance on large DBs.** With thousands of work items the in-memory filter might hitch. Not a near-term risk (current seed is ~dozens of items), but we keep the implementation simple so future paging / server-side search is additive.
- **Awaiting-input hook drift.** If Claude Code's hook fails to call `set-awaiting --awaiting false`, the dot stays stuck. Mitigations: the "Clear awaiting" link in the drawer; the ingest CLI is the user's explicit escape hatch; a future v0.3.x can add a TTL-based auto-clear.
- **Optimistic updates desync.** If `PATCH` 500s after we've shown the new value, the rollback on `onError` must restore exactly — React Query handles this as long as we pass the previous value via `onMutate`. Straightforward, but worth a targeted test (#3 and #4 above partially cover it).

## Out of scope / follow-ups

- "+ New task" / "+ New epic" buttons on the board header. Palette covers creation; buttons are additive.
- Rich-text or markdown preview in the description field.
- Multi-select and bulk operations (status change for N cards at once).
- A WebSocket-driven real-time push for awaiting-input state (if polling + existing WS isn't snappy enough).
- "Open terminal when transitioning to in_progress" — explicitly descoped by the user.
- Customizable keyboard shortcuts (config-driven).
- Command-palette plugins / arbitrary-action registry.

## Rollout

Single-version bump to 0.3.8. No DB migration (all columns already exist). No new dependencies. No breaking CLI changes — `set-awaiting` is additive. Client changes are purely additive surface on top of existing endpoints, so rolling back is a matter of reverting the bundle.
