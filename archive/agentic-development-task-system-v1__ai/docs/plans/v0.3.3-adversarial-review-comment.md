# v0.3.3 — Adversarial Review Comment on In-Review Transition

## Brief

When a work item transitions to the `in_review` status, the server auto-creates a system-authored comment on that work item containing a pre-filled `/codex:adversarial-review` prompt. The comment is rendered in the existing comment list with two extra actions: **Copy** (clipboard) and **Send to terminal** (pastes into the linked Claude session without pressing Enter). The user edits remaining placeholders and sends the prompt themselves.

### Motivation

- Moving a task to Review is exactly the moment where an adversarial review is most useful.
- Today the user has to hand-assemble the prompt, look up task body + acceptance criteria + branch, and paste into a terminal.
- This collapses the flow to 1–2 clicks from the board while preserving the review-before-submit behavior the user wants (no auto-Enter).

---

## Design

### User flow

1. User drags a task to the Review column (or transitions via drawer action / CLI / ingest).
2. The server applies the transition and, atomically, inserts a system comment with the adversarial review prompt.
3. The user opens the task drawer or detail page. The comment appears at the bottom of the comment list (which is ordered oldest-first) with **Copy** and (when a session is linked) **Send to terminal** buttons.
4. User clicks **Send to terminal** → the text is pasted into the task's Claude session at the cursor, **Enter is not pressed**. The UI navigates to the Terminal tab so the user can see it land.
5. User edits the `[risk area N]` / `[constraint N]` placeholders and the worktree path, then presses Enter themselves.

### Trigger point

In `POST /api/work-items/:id/transition` (`src/server/routes/work-items.ts`), after validating the transition, if `new_status === 'in_review'` **and** `previous_status !== 'in_review'`:

1. Load the work item.
2. Render the prompt via `renderAdversarialReviewPrompt` (new module).
3. Insert a `comments` row with `author_type: 'system'`, `author_id: 'adversarial-review-bot'`.
4. Insert a `comment.created` activity event mirroring the manual-comment path.

All four writes (status update, `status_changed` activity event, and conditionally the comment insert + `comment.created` activity event) run inside a single `better-sqlite3` `db.transaction(...)` — atomic, one fsync.

**Re-entry behavior:** Legitimate re-entries (Review → In Progress → Review) **do** produce a fresh comment — review context may differ between cycles. The `previousStatus !== 'in_review'` guard only prevents no-op self-transitions.

### Template module

**File:** `src/server/domain/review-prompts.ts`

**Export:**

```ts
export function renderAdversarialReviewPrompt(workItem: {
  id: string;
  title: string;
  body: string;
  acceptance_criteria: string | null;
  branch_name: string | null;
}): string
```

**Template (exact output):**

```
/codex:adversarial-review --base main challenge whether this was the right approach for <title>.

Task description:
<body or "(none)">

Acceptance criteria:
<acceptance_criteria or "(none)">

Working directory: <fill in worktree path>
Branch: <branch_name or "(none — uncommitted work)">

Focus on:
- correctness under edge cases
- [risk area 1]
- [risk area 2]
- [risk area 3]

Constraints:
- [constraint 1]
- [constraint 2]

Prefer:
- safer simpler alternatives
- ship-blocking issues first
- concrete examples of how the current approach could fail
```

**Rules:**

- `body`: trimmed; empty → `(none)`.
- `acceptance_criteria`: trimmed; null/empty → `(none)`.
- `branch_name`: literal value if set, else `(none — uncommitted work)`.
- `title`: newlines stripped before substitution (it goes on the first line).
- `--base main` is a literal string. No derivation from task data.
- `<fill in worktree path>` is a literal placeholder — the system does **not** inspect linked sessions or branches to guess a path.
- `[risk area N]` and `[constraint N]` are literal placeholders for the human to fill in.

### Paste endpoint

**New endpoint:** `POST /api/sessions/:id/paste`

**File:** `src/server/routes/sessions.ts`

- Request body: `{ text: string }`.
- Validates: session exists (404), `state === 'running'` (400), `tmux_session_name` is set (400), `text` non-empty (400).
- Calls `tmux.sendKeys(session.tmux_session_name, text, false)` — the existing helper's `false` flag means "no trailing Enter".
- Inserts an `activity_events` row with `event_type: 'session.text_pasted'`, `entity_type: 'session'`, `entity_id: session.id`, `payload_json: { char_count: text.length }`. The full text is not logged (already in the comment).
- Returns `{ ok: true }`.
- 500 on tmux failure (existing try/catch pattern).

### UI changes

**`src/client/components/CommentList.tsx`**

- Accept new prop `activeSessionId?: string | null`.
- In `CommentRow`, when `comment.authorType === 'system' && comment.authorId === ADVERSARIAL_REVIEW_BOT_ID`, render two additional buttons in the row header next to Edit/Delete:
  - **Copy** — `navigator.clipboard.writeText(comment.body)` + success toast.
  - **Send to terminal** — only rendered if `activeSessionId` is truthy. On click:
    1. POST `/api/sessions/:activeSessionId/paste` with `{ text: comment.body }`.
    2. On success: toast "Sent to terminal", then `navigate('/terminal?session=' + activeSessionId)`.
    3. On failure: toast the error message.

**`src/client/components/WorkItemDrawer.tsx`** and **`src/client/pages/WorkItemDetailPage.tsx`**

- Pass `activeSessionId={item.activeSessionId}` to `<CommentList>`.

**`src/client/services/hooks.ts`**

- Add `useSendToTerminal()` — a `useMutation` wrapping `POST /api/sessions/:id/paste`.

### Shared constants

`src/shared/constants.ts`:

- Add `export const ADVERSARIAL_REVIEW_BOT_ID = 'adversarial-review-bot'` so server and client share one source of truth.

### Data model

No schema changes. No migration.

### Error handling

- Transition succeeds but comment insert fails: impossible — single transaction; all-or-nothing.
- User clicks **Send to terminal** but the session exited between page load and click: endpoint returns 400, toast surfaces it, Copy still works.
- `tmux send-keys` fails (e.g. session killed): endpoint returns 500, toast surfaces it.
- Clipboard API denied: standard browser failure, toast surfaces it.

## Non-goals

- No change to the `reviews` table or adversarial review *result* tracking — this feature only generates the *invocation prompt*.
- No smart worktree detection — the template always emits a literal `<fill in worktree path>` placeholder.
- No automatic paste on status change — the user always initiates the paste.
- No edit lockout on system comments; standard edit/delete behavior is retained.

### Known issue — Send to terminal button rarely appears

Observed during browser verification: on the adversarial review system comment, **Copy** renders as expected but **Send to terminal** is hidden.

**Root cause:** the button is gated on `activeSessionId` being truthy, and `work_items.active_session_id` is only populated when a Claude session is started from the board via `POST /api/sessions/` (see `src/server/routes/sessions.ts` — `updateWorkItem(workItemId, { active_session_id: sessionId })`). Tasks that haven't been started that way — including most tasks moved to Review through normal DnD usage — never have a linked session, so the button never appears. In practice this means the button only shows up for tasks that were kicked off through the board's "start session" flow *and* still have that session running.

**Impact:** the feature's headline interaction (one-click paste to terminal) is unavailable for the common case of "I moved a task to Review; now I want to hand it off to the reviewer."

**Options to consider in a follow-up:**

- **A)** Keep current strict gating; document that users must start the session from the board.
- **B)** Show the button always; disable with a tooltip when no session is linked.
- **C)** Show the button always; open a session picker when the task has no linked session, letting the user pick from currently running terminals.

Deferred pending a decision on the preferred UX.
