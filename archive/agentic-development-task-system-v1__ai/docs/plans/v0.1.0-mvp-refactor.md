# v0.1.0 — MVP Refactor

## Brief

Strip the system down to what matters and build the four tabs into a usable tool. This is the first real release — a local dashboard for managing agentic development work with a working terminal emulator, live updates, and a clean data model.

## Data Model

### What stays
- **Initiatives** — top-level grouping (replaces themes + initiatives; themes are removed)
- **Epics** — groups of related work under an initiative
- **Work Items** (kind: `task` | `bug`) — the unit of work on the board
- **Sub-tasks** — work items with a `parent_id` pointing to another work item

### What gets removed
- **Themes** table — unnecessary layer; initiatives are the top grouping now
- `theme_id` FK on initiatives — dropped
- `story` kind on work items — only `task` and `bug`

### Status changes

| Old | New | Notes |
|-----|-----|-------|
| `backlog` | `triage` | Rename — new items land in triage |
| `ready` | `ready` | No change |
| `in_progress` | `in_progress` | No change |
| `blocked` | *(removed)* | Not a board column; use tags or a flag instead |
| `in_review` | `in_review` | No change |
| `done` | `done` | No change |
| `canceled` | `canceled` | Kept but not a board column |

### Status transitions

```
triage -> ready, canceled
ready -> in_progress, triage, canceled
in_progress -> in_review, done, triage, canceled
in_review -> in_progress, done, triage
done -> (terminal)
canceled -> triage
```

- `epic_id` — for grouping on board
- `status` — board column
- `awaiting_input` — boolean flag, true when agent is waiting for user input
- `active_session_id` — FK to terminal_sessions, set when a session is implementing this item

## Filesystem Storage (`data/task_data/`)

### Overview
All plan documents and markdown content live on the filesystem in a tree that mirrors the hierarchy. The `data/task_data/` directory is the single source of truth for markdown content — the Library tab reads directly from it, and edits write back to it. The database stores metadata (status, kind, category, etc.) but **not** long-form markdown content.

### Directory structure
```
data/task_data/
  <initiative-slug>/
    initiative.md              # initiative description
    <epic-slug>/
      epic.md                  # epic description
      <work-item-slug>/
        plan.md                # the plan for this task/bug
        notes.md               # optional working notes
        <subtask-slug>/
          plan.md
```

Example:
```
data/task_data/
  auth-overhaul/
    initiative.md
    login-flow/
      epic.md
      add-oauth-support/
        plan.md
      fix-session-timeout/
        plan.md
        investigate/
          plan.md
    signup-flow/
      epic.md
      email-verification/
        plan.md
```

### Slug generation
- Derived from the entity title: lowercase, spaces → hyphens, strip non-alphanumeric, truncate to 60 chars
- Stored on the DB row as `slug` column (new column on initiatives, epics, work_items)
- Must be unique within its parent directory
- On title rename, the folder is renamed (mv) and the slug column updated

### Auto-creation rules
1. On server startup: ensure `data/task_data/` exists; create if missing
2. On initiative create: create `data/task_data/<slug>/initiative.md` with title + description
3. On epic create: create `data/task_data/<initiative-slug>/<slug>/epic.md`
4. On work item create: create `data/task_data/<initiative-slug>/<epic-slug>/<slug>/plan.md`
5. On sub-task create: create `data/task_data/.../<parent-slug>/<slug>/plan.md`
6. On entity delete: archive (move to `data/task_data/.archive/`) rather than hard delete

### Filesystem service (`src/server/fs/task-data.ts`)
```typescript
// Core operations
ensureTaskDataRoot(): void             // create data/task_data/ if missing
getEntityPath(entity): string          // resolve full path from DB hierarchy
createEntityDir(entity): void          // mkdir -p + write initial .md
renameEntityDir(old, new): void        // mv on title change
readMarkdown(path): string             // read file content
writeMarkdown(path, content): void     // write file content
archiveEntityDir(entity): void         // mv to data/task_data/.archive/
listMarkdownFiles(dirPath): string[]   // list .md files in a directory
```

### How Library uses it
- The tree navigator is built from DB queries (for metadata: title, kind, status)
- When a node is selected, the right panel reads the markdown file from `data/task_data/` via a new API endpoint: `GET /api/fs/read?path=<relative-path>`
- Edits are saved via: `PUT /api/fs/write` with `{ path, content }`
- Plan artifacts are `.md` files inside the work item's directory

### How other tabs use it
- **Board** card preview drawer: fetches `plan.md` content to show a preview snippet
- **Work item detail page**: loads `plan.md` and any other `.md` files from the item's directory
- **Activity**: `artifact.attached` events reference the filesystem path

### Gitignore
`data/task_data/` is added to `.gitignore` — this is local working data, not source code.

## Tab 2: Terminal (`/terminal`)

### Overview
tmux-backed terminal emulator. When a work item transitions to `in_progress` and has an assigned agent, a terminal session opens here automatically. Each session is a tab.

### Layout
- **Tab bar** across top — one tab per active session
  - Tab label: work item title (truncated)
  - Tab color: matches the epic's `color` value
  - Session ID displayed above the terminal viewport
  - Close button per tab
- **Terminal viewport** — xterm.js rendering tmux session output via WebSocket

### Session lifecycle
1. Work item moves to `in_progress` → server creates tmux session → `terminal_sessions` row inserted → `active_session_id` set on work item
2. WebSocket connection established between client and tmux session via server relay
3. Agent works inside tmux session; output streams to xterm.js
4. When agent needs user input → server sets `awaiting_input = true` on work item → Board card shows warning badge
5. User clicks badge → navigated to Terminal tab with that session focused
6. Work item moves to `in_review` or `done` → session state updated to `exited` → tab remains but marked inactive

### Server components
- **tmux manager** (`src/server/terminal/tmux.ts`) — create/attach/kill tmux sessions, list sessions
- **WebSocket relay** (`src/server/terminal/ws-relay.ts`) — bridges xterm.js ↔ tmux session via stdin/stdout pipes
- **Session routes** (`src/server/routes/sessions.ts`) — CRUD for terminal_sessions, create session for work item

### Client components
- **TerminalPage** (`src/client/pages/TerminalPage.tsx`) — tab bar + xterm.js viewport
- **TerminalTab** (`src/client/components/TerminalTab.tsx`) — individual tab with xterm instance
- **useTerminalSession** hook — manages WebSocket connection lifecycle

### Dependencies
- `xterm` + `@xterm/addon-fit` + `@xterm/addon-web-links` (client)
- `ws` (server WebSocket)
- tmux installed on host (system dependency)

## Tab 3: Library (`/library`)

### Overview
Browse and edit all project content — reads directly from the `data/task_data/` filesystem. The tree mirrors the directory structure; the editor reads and writes `.md` files on disk.

### Layout
- **Left panel**: tree navigator
  - Built from DB hierarchy (initiative > epic > work item > sub-task) for metadata (title, kind, status)
  - Each node shows: icon (kind), title, status badge
  - Clicking a **work item** expands to show:
    - Sub-tasks (from DB)
    - Plan/markdown file names (from filesystem — lists `.md` files in the item's `data/task_data/` directory)
  - Clicking a **plan name** (e.g., `plan.md`, `notes.md`) opens it in the right panel
  - Clicking an **epic** shows `epic.md` in the right panel
  - Clicking an **initiative** shows `initiative.md` in the right panel
- **Right panel**: content viewer/editor
  - Reads `.md` file content from `data/task_data/` via `GET /api/fs/read?path=<relative-path>`
  - Markdown renderer with edit toggle (switch between rendered view and editor)
  - Save writes back to disk via `PUT /api/fs/write` with `{ path, content }`
  - File path shown as breadcrumb above the editor (e.g., `auth-overhaul / login-flow / add-oauth-support / plan.md`)

### Markdown editor
Use a simple split or toggle approach:
- **View mode**: rendered markdown (react-markdown or similar)
- **Edit mode**: textarea or Monaco editor with markdown preview
- Toggle button in top-right of content panel

### Data flow
```
DB (metadata: title, kind, status, slug)  →  Tree navigator (left panel)
Filesystem (data/task_data/**/*.md)            →  Content editor (right panel)
```

The Library never stores or reads markdown from the database. All long-form content lives in `data/task_data/`.

## Tab 4: Activity (`/activity`)

### Overview
Live feed of all system events plus a view of currently running agents.

### Layout
Two sections (split or tabbed):

#### Running Agents (top or left)
- Cards for each agent with `computed_status != 'idle'`
- Shows: agent name, kind badge, current work item title, session link, elapsed time
- Clicking agent card → Terminal tab focused on that agent's session

#### Event Stream (bottom or right)
- Chronological list of activity events (newest first)
- Each event shows: timestamp, event type icon, entity name, actor, description
- Color-coded by event type
- Auto-refreshes via WebSocket (not polling)

### Events that get recorded
Verify every mutation creates an activity event:

| Action | Event Type | Source |
|--------|-----------|--------|
| Work item created | `work_item.created` | `ui` or `ingest` |
| Work item status changed | `work_item.status_changed` | `ui` or `terminal` |
| Work item updated (title, body, etc.) | `work_item.updated` | `ui` |
| Work item assigned to agent | `work_item.assigned` | `ui` or `ingest` |
| Epic created | `epic.created` | `ui` or `ingest` |
| Epic updated | `epic.updated` | `ui` |
| Session started | `session.declared` | `terminal` |
| Session ended | `session.ended` | `terminal` |
| Review requested | `review.requested` | `terminal` or `system` |
| Review completed | `review.completed` | `terminal` or `system` |
| Artifact attached | `artifact.attached` | `terminal` or `ingest` |
| Agent needs input | `work_item.awaiting_input` | `terminal` |

### Missing events to add
- `epic.updated` — not currently emitted from PATCH /api/epics
- `session.ended` — not currently emitted
- `work_item.awaiting_input` — new event type
- Initiative CRUD events (if we want them)

### WebSocket for live updates
- Server broadcasts activity events over WebSocket as they're created
- Client subscribes on mount, appends to feed in real-time
- Replace the current 10s polling interval
