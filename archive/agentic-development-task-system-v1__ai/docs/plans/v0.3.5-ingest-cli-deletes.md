# v0.3.5 — Ingest CLI deletes (tasks, epics, comments, initiatives)

## Brief

The ingest CLI can currently create tasks, epics, and comments, but has no way to remove them. Today the only path to delete a bad row is raw `sqlite3` against `data/db/taskboard.sqlite`, which also requires manually sweeping dependent rows (tags, activity events, reviews, links) and the matching files in `data/ingest/processed/`. That happens often enough during task-entry mistakes (e.g. v0.3.4 broke when the shell ate a quoted multi-line `--acceptance-criteria` flag, leaving two broken work items) to be worth a proper CLI path.

v0.3.5 adds `delete` subcommands to the ingest CLI for every entity the CLI already creates, plus initiatives (which the CLI doesn't create but which appear in the DB). The deletes follow the same event-sourced pattern as every other mutation in this repo: the CLI writes a `*.deleted` envelope to `data/ingest/inbox/`, the watcher picks it up, and the processor deletes the row via the repository layer. No side-channel DB writes, no parallel code path.

### Motivation

- **Recoverability from input errors.** Pasted multi-line commands, typos in `--title`, duplicate runs — all produce garbage rows the user currently has to clean up by hand.
- **Symmetry with creation.** Every create event already emits an activity row and a processed ingest file; deletes should too, so the activity feed stays complete.
- **One surface.** Users should not need to learn two mental models (CLI for create, SQL for delete).
- **Unblocks later work.** The v0.3.4 bug report surfaced a related issue: the arg parser silently accepts a flag with no value by stealing the next flag's value. A tighter parser is listed as a non-goal here but called out in the follow-ups so it does not get lost.

### Non-goals

- No UI affordance for delete on the board. Deletes stay a CLI-only operation in this version — the board already hides `canceled` tasks, so archive-via-status covers the common "I don't want to see this" need. A trash/restore UI is a larger piece of work.
- No soft-delete / undo. A delete is a row-level DELETE through the repository. The activity row remains (so "what happened" is still auditable), but the entity itself is gone. Restoring requires re-creating from a prior envelope. This matches `deleteComment` today.
- No bulk-delete flags (`--all-in-epic`, `--all-by-tag`, etc.). One ID per invocation. Bulk operations can compose at the shell level (`xargs`) if needed.
- No cascading control flags (`--force`, `--dry-run`). Cascading behavior is whatever the existing FK constraints say — we are explicitly **not** inventing new cascade rules in this version. See "Cascade semantics" below for what that means per entity.
- No parser hardening (rejecting flag-eats-flag). Tracked as a follow-up, not in this plan.
- No delete for `session.declared`, `review.completed`, `artifact.attached`, `work_item.assigned`, `work_item.session_linked`, `work_item.status_changed`, or `work_item.updated`. Those are *event* records; deleting them would be rewriting history, not removing an entity.

## Design

### CLI shape

Four new subcommands, each mirroring its creation counterpart:

```
npm run ingest -- delete-task --work-item-id <uuid>
npm run ingest -- delete-epic --epic-id <uuid>
npm run ingest -- delete-comment --comment-id <uuid>
npm run ingest -- delete-initiative --initiative-id <uuid>
```

One required ID flag per subcommand. No other flags. Verb-first (`delete-task`) rather than sibling subcommands under a `delete` group, to keep the parser's one-token-subcommand shape unchanged (`parseArgs` in `src/cli/ingest.ts` today only reads `argv[0]` as the subcommand).

Rationale for the hyphenated-verb form over `delete task --id`:
- `parseArgs` currently treats anything at `argv[0]` that doesn't start with `--` as the full subcommand. Introducing a `verb + object` shape is a parser change with no user-facing benefit.
- `npm run ingest -- delete-task ...` reads cleanly in the shell history and matches the pattern Claude skills already use.

### Envelope shape

New `*.deleted` event types, mirroring the existing `comment.deleted` precedent:

```json
{
  "event_id": "<uuid>",
  "event_type": "work_item.deleted",
  "occurred_at": "<iso8601>",
  "source": "claude-skill",
  "actor": { "type": "agent", "id": "claude-code" },
  "payload": { "work_item_id": "<uuid>" }
}
```

Same pattern for `epic.deleted` (`payload.epic_id`), `initiative.deleted` (`payload.initiative_id`). `comment.deleted` already exists in `src/shared/schemas.ts` and needs no schema change — only a new CLI builder.

Payloads are intentionally minimal: just the ID. Any additional context (cascade counts, actor reason, etc.) is not needed now and can be added later without breaking existing envelopes because Zod's object schemas tolerate extra fields only if `.passthrough()` is used — we'll keep them strict for now to surface typos.

### Cascade semantics

What gets removed when you delete each entity is determined by the existing foreign-key constraints in `src/server/db/schema.sql` and `migrations/002_add_comments.sql`. This plan does **not** change those constraints. The CLI documents the current behavior; it does not invent new cascades.

| Entity deleted | Automatically removed via FK | Left behind (explicit) |
|---|---|---|
| `work_items` row | `work_item_tags` (CASCADE), `reviews` (CASCADE), `artifacts` (CASCADE), `task_session_links` (CASCADE), `comments` (CASCADE), child `work_items` via `parent_id` (CASCADE) | `activity_events` rows referencing this work item (entity FK is nullable/unenforced), `terminal_sessions.primary_work_item_id` (no ON DELETE clause — the FK will reject a raw DELETE if a session points at it; see "Open question" below) |
| `epics` row | `work_items.epic_id` set to NULL (SET NULL), `artifacts` where epic_id matches (CASCADE) | `activity_events` for this epic |
| `initiatives` row | `epics.initiative_id` set to NULL (SET NULL) | `activity_events` for this initiative |
| `comments` row | nothing (leaf table) | `activity_events` for the parent work item |

**`activity_events` are intentionally preserved** in every case. They are the audit trail; deleting them would lose the record of what happened. The `delete-*` operations *add* a new activity row (`*.deleted` event), they do not prune old ones.

#### Open question — `terminal_sessions.primary_work_item_id`

The `terminal_sessions` FK on `primary_work_item_id` has no `ON DELETE` clause, which in SQLite means `NO ACTION` (the DELETE will fail if any session references the work item). With `PRAGMA foreign_keys = ON` (which `schema.sql` sets), this will throw at DELETE time.

Options:

- **A (recommended for this version):** Detect the case in the processor and return a typed error (`work_item_still_referenced_by_session`), which moves the envelope to `rejected/` with a clear reason. Users can archive/close the session first, then retry the delete. No schema change.
- **B:** Migrate the FK to `ON DELETE SET NULL` (matches how `work_items.active_session_id` is declared). Changes behavior silently for anyone who had relied on the old reject — low risk here given single-user scope, but is a migration.
- **C:** Migrate to `ON DELETE CASCADE`. Too aggressive — deleting a task should not tear down the terminal session attached to it.

Proceeding with **A** unless instructed otherwise during implementation. The UX is: try `delete-task`, if it refuses, close the session, retry.

### Idempotency and "not found"

Each handler looks up the entity first (we already have getters: `getCommentById`, and we add `getWorkItemById` / `getEpicById` / `getInitiativeById` if the repo doesn't already expose them — spot-checking shows at least a `getByIdRaw` style in `work-items.ts`; we'll reuse or add one-liner helpers).

Behavior when the entity is absent:

- Return `{ success: false, error: "<entity> not found: <id>" }` from the processor. This matches the existing `handleCommentUpdated` / `handleCommentDeleted` paths. The envelope ends up in `data/ingest/rejected/` with a human-readable reason. This is the right call because a silent accept would hide real bugs (e.g., deleting the wrong UUID after a copy-paste error).

Duplicate envelopes (same sha256) are already rejected by `findBySha256` in `processor.ts`, so rerunning an identical delete command is a safe no-op.

### Processor handlers

Three new handlers in `src/server/ingest/processor.ts`, mirroring the existing `handleCommentDeleted`:

```ts
function handleWorkItemDeleted(envelope, payload, filePath, fileName, sha256): ProcessResult {
  const p = payload as { work_item_id: string };
  const existing = getWorkItemById(p.work_item_id);
  if (!existing) {
    return { success: false, event_type: envelope.event_type, error: `Work item not found: ${p.work_item_id}` };
  }

  try {
    deleteWorkItem(p.work_item_id);
  } catch (err) {
    // e.g., terminal_sessions.primary_work_item_id constraint
    return {
      success: false,
      event_type: envelope.event_type,
      error: err instanceof Error ? err.message : String(err),
    };
  }

  recordActivity(envelope, 'work_item', p.work_item_id);
  recordIngestFile(filePath, fileName, sha256, envelope.event_type);
  return { success: true, event_type: envelope.event_type, entity_id: p.work_item_id };
}
```

`handleEpicDeleted` and `handleInitiativeDeleted` are structurally identical. `handleCommentDeleted` already exists and needs no change.

### Repository additions

New one-liners (or reuse if present) — all in their respective files under `src/server/db/repositories/`:

- `work-items.ts`: add `getWorkItemById(id)` if not exposed, `deleteWorkItem(id)`.
- `epics.ts`: add `getEpicById(id)`, `deleteEpic(id)`.
- `initiatives.ts`: add `getInitiativeById(id)`, `deleteInitiative(id)`.

Each `delete*` is a single `DELETE FROM <table> WHERE id = ?` prepared statement. FK-triggered cascades handle the rest.

### Schema registration

In `src/shared/schemas.ts`:

- Add `WorkItemDeletedPayloadSchema = z.object({ work_item_id: z.string().uuid() })`.
- Add `EpicDeletedPayloadSchema = z.object({ epic_id: z.string().uuid() })`.
- Add `InitiativeDeletedPayloadSchema = z.object({ initiative_id: z.string().uuid() })`.
- Register them in `PayloadSchemaMap` under `"work_item.deleted"`, `"epic.deleted"`, `"initiative.deleted"`.

`CommentDeletedPayloadSchema` already exists and is already registered.

### CLI builders

In `src/cli/ingest.ts`, add three new builders (comment-delete also needs one, since the current `buildCommentEnvelope` is create-only):

```ts
export function buildWorkItemDeleteEnvelope(flags) {
  const workItemId = flags["work-item-id"];
  if (!workItemId) throw new Error("--work-item-id is required for delete-task subcommand");
  // …standard envelope with event_type: "work_item.deleted", payload: { work_item_id: workItemId }
  return { envelope, entityId: workItemId, slug: `deleted-${workItemId.slice(0, 8)}` };
}
```

Same shape for `buildEpicDeleteEnvelope`, `buildCommentDeleteEnvelope`, `buildInitiativeDeleteEnvelope`.

Then in `run()`, add four new cases (`delete-task`, `delete-epic`, `delete-comment`, `delete-initiative`) that call the appropriate builder and pass the right `entityType` to `writeToInbox` so the filename prefix reflects the entity being deleted (`task-deleted-…`, `epic-deleted-…`, etc.). Filename collisions are prevented by the short UUID suffix.

Update the usage string in `parseArgs`'s error path to list all subcommands.

### Processor dispatch

Add the three new entries to the `handlers` map in `src/server/ingest/processor.ts`:

```ts
'work_item.deleted': handleWorkItemDeleted,
'epic.deleted': handleEpicDeleted,
'initiative.deleted': handleInitiativeDeleted,
// 'comment.deleted' already registered
```

### Manual (end-to-end)

Run each through the actual watcher to confirm the envelope survives validation and the row is gone from SQLite.

Setup: `npm run dev` running; have at least one epic, one task with tags, one comment, one initiative in the DB.

1. **Delete a task.**
   - `EPIC_ID=<some epic>`; `npm run ingest -- task --title "Delete-test task" --epic-id $EPIC_ID --tags "scratch"`.
   - Note the returned `entity_id` as `TASK_ID`.
   - Wait ~1s for the watcher to process.
   - `sqlite3 data/db/taskboard.sqlite "SELECT COUNT(*) FROM work_items WHERE id = '$TASK_ID';"` → `1`.
   - `npm run ingest -- delete-task --work-item-id $TASK_ID`.
   - Wait ~1s.
   - `sqlite3 data/db/taskboard.sqlite "SELECT COUNT(*) FROM work_items WHERE id = '$TASK_ID';"` → `0`.
   - `sqlite3 data/db/taskboard.sqlite "SELECT COUNT(*) FROM work_item_tags WHERE work_item_id = '$TASK_ID';"` → `0` (tag cascaded).
   - `sqlite3 data/db/taskboard.sqlite "SELECT COUNT(*) FROM activity_events WHERE entity_id = '$TASK_ID';"` → ≥ 2 (create + delete rows both present).
   - Board in browser: task disappears from its column after the websocket broadcasts (or on refresh — whichever is the current behavior).

2. **Delete a task that has a session attached.**
   - Create a task, start a terminal session with `primary_work_item_id` pointing at it (via the existing session-creation UI).
   - `npm run ingest -- delete-task --work-item-id $TASK_ID`.
   - Expect: envelope moves to `data/ingest/rejected/` with an FK-constraint error; task stays in DB; error visible in the file's reason column.
   - Close the session (`DELETE /api/sessions/:id` via the UI).
   - Retry `delete-task` → succeeds.

3. **Delete an epic with child tasks.**
   - Create an epic, create a task under it.
   - `npm run ingest -- delete-epic --epic-id $EPIC_ID`.
   - After processing: epic gone, task still present with `epic_id = NULL`.

4. **Delete a comment.**
   - Create a task, add a comment via `npm run ingest -- comment --work-item-id $TASK_ID --body "Throwaway"`.
   - `npm run ingest -- delete-comment --comment-id $COMMENT_ID`.
   - Comment gone; `activity_events` gain a `comment.deleted` row.

5. **Delete an initiative.**
   - Seed an initiative with an epic under it, run `delete-initiative`, confirm initiative is gone and the epic's `initiative_id` is `NULL`.

6. **Idempotency / not-found.**
   - Run `delete-task` against a random UUID → envelope lands in `rejected/` with "Work item not found: …".
   - Re-run a previously successful `delete-task` → envelope lands in `rejected/` with the same "not found" reason (the first one already succeeded).

7. **Duplicate envelope dedupe.**
   - Copy a successful delete file from `processed/` back into `inbox/` → watcher detects `sha256` duplicate, moves to `rejected/` with "Duplicate file detected".

8. **Unrelated creates still work.**
   - After all of the above, create a fresh task/epic/comment to confirm no regression in the create paths.

## Risks

- **FK fallout.** The largest risk is that a `deleteWorkItem` call fails mid-flight because of an unexpected FK. Mitigation: the processor catches and rejects the envelope rather than crashing; the user sees a readable reason in `rejected/`. The manual-test matrix exercises the `terminal_sessions` case explicitly.
- **Activity feed noise.** Deletes now surface as activity rows. On a board with lots of scratch tasks this could feel spammy, but it is strictly an improvement over today's "row vanished with no trace." No mitigation needed.
- **Confusion with status-based archival.** Users already have `status: canceled` as a soft-hide. The CLI docs (README, if this repo has one — otherwise the skill prompt) should note when to pick delete vs. cancel:
  - *Delete* = "this entity should not have existed" (typo, duplicate, broken ingest).
  - *Cancel* = "we decided not to do this" (keeps history).
  Out of scope for the code change itself, but worth a line in the commit message / CHANGELOG.
- **CLI parser still flakey.** The v0.3.4 bug (flag with no value silently adopts the next flag's value) is *not* fixed in this plan. Users running the new delete commands with typos can still produce surprising behavior (e.g., `--work-item-id --comment-id <uuid>` would set `work-item-id = "true"`). Explicit follow-up below.

## Follow-ups (out of scope for v0.3.5)

- **Parser hardening.** In `parseArgs`, reject `arg.startsWith("--")` when the current flag expected a value (track which flags accept values via a per-subcommand allowlist). This fixes the root cause of the v0.3.4 multi-line paste fiasco.
- **Route-level deletes.** If the UI ever grows a delete affordance, add `DELETE /api/work-items/:id`, `DELETE /api/epics/:id`, `DELETE /api/initiatives/:id` that write the same envelopes (or call the repositories directly and emit the activity row — match whatever pattern the comment DELETE route settles on).
- **Bulk delete.** `delete-tasks --epic-id X` or `delete-tasks --status canceled` once there's a real use case.
- **Restore / undo.** A soft-delete table plus a `restore-*` subcommand. Only worth building if the hard-delete turns out to bite someone.
