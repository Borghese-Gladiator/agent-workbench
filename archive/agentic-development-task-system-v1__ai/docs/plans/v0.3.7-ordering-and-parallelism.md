# v0.3.7 — Ordering, batches, and parallelism lanes

## Brief

Today, after a bulk-create the board is a bucket. The `batch` subcommand promises "input-order writes" but that order is thrown away by the time rows land in the DB: `handleWorkItemCreated` hard-codes `sort_order: 0` for every row (`src/server/ingest/processor.ts:93`), `WorkItemCreatedPayloadSchema` doesn't carry a `sort_order` field (`src/shared/schemas.ts:25`), and the watcher emits `add` events in filesystem-discovery order, not write order (`src/server/ingest/watcher.ts:209`). The board then sorts by `(sortOrder ?? Infinity)` with no tiebreaker (`src/client/pages/BoardPage.tsx:80`), so 15 tasks from one batch all tie at 0 and render in undefined order.

Adjacent failures that compound the same pain:

- **No dependencies.** There is no `depends_on` / `blocks` anywhere in the schema, payload, or UI. An orchestrator looking at the board cannot answer "which tasks can run in parallel?" or "which task is ready next?"
- **No lane signal.** Tags exist as free-form strings, but there is no "group by tag" and no formal `lane` concept, so the frontend-vs-backend split is invisible.
- **No batch identity.** Once 15 envelopes are processed they have no shared marker — "what did the planner just create?" is impossible to query.
- **Epic ordering is alphabetical.** `epics.sort_order` exists in the schema but no ingest event sets it; `BoardPage.tsx:135` sorts epic groups by `title.localeCompare(...)`.

v0.3.7 addresses exactly these four problems, scoped tightly. The fixes share one piece of plumbing: a `sort_order`-carrying ingest payload plus a `batch_id` that ties a bulk-create together. Dependencies are scoped to a single FK column (`depends_on_id`) plus a blocked-status derivation — no full DAG, no cycle detection beyond a simple self/ancestor check.

Explicit non-goals (deferred to later):

- **No full dependency DAG.** One `depends_on_id` per task (many-to-one). Multi-prerequisite chains are expressed by chaining tasks; parallel siblings pointing at the same predecessor *is* supported and is the whole point.
- **No cycle detection beyond self-reference and an ancestor-walk up to N=50.** Anything deeper is user error; we return an error, we don't try to be clever.
- **No "group by tag" column on the board.** The data gets a `lane` derivation but the board UI addition is minimal — a colored left border and a lane filter chip. "Lanes as columns" is v0.3.8+ work.
- **No auto-scheduling** ("pick the next ready task for me"). Surfaces a `ready_to_start` derived flag; human / Claude still decides.
- **No undo for bulk-create.** `batch_id` makes it *queryable*; the actual "undo" CLI is a v0.3.8 follow-up.
- **No rollback on partial inbox write.** Pre-validation already catches schema errors. A mid-write disk failure remains fatal and logged, same as today.

### User stories

1. **As Claude running `bulk-create` for a phased breakdown**, I include a `sort_order` (or rely on array index) in the payload; the tasks appear on the board in that order, both within each column and after they move between columns.
2. **As a user asking "what can run in parallel?"**, I can see on the board which tasks have no incoming `depends_on_id` and no unfinished predecessor — those show a green `Ready` dot; blocked tasks show a grey `Waiting` dot with a hover showing the predecessor's title.
3. **As a user with a mix of frontend and backend work**, I set `lane: "frontend"` / `lane: "backend"` on the batch and the cards get a colored left border and a lane filter in the toolbar. I can toggle "only show frontend" without touching the tag filter.
4. **As a user who just bulk-created an epic's worth of tasks**, I can click the epic header and see a count "15 tasks from batch 7f3a…" and, if I want, filter the board to just that batch.
5. **As a user with a typo in row 3 of a bulk-create**, the `depends_on_index: 1` that row 4 was supposed to chain from still resolves correctly — the CLI translates batch-local indices to real UUIDs *before* writing, so there's no "inbox order" surprise.

## Design

### Shape of the fix in one sentence

Carry `sort_order` (and a tiny set of friends — `lane`, `depends_on_id`, `batch_id`) through the payload → processor → DB → UI. Derive the rest (`ready_to_start`, transitive-blocked) in SQL.

### 1. Ordering: pass `sort_order` through the ingest path end-to-end

#### Schema changes

No new columns on `work_items` for `sort_order` — the column already exists (`src/server/db/schema.sql:70`). The fix is that **every code path that writes a work item must set it from the payload instead of defaulting to 0**.

New migration `003_ordering_and_lanes.sql`:

```sql
ALTER TABLE work_items ADD COLUMN lane TEXT;                     -- free-form; nullable
ALTER TABLE work_items ADD COLUMN batch_id TEXT;                 -- uuid of the creating batch, nullable
ALTER TABLE work_items ADD COLUMN depends_on_id TEXT
  REFERENCES work_items(id) ON DELETE SET NULL;                  -- single predecessor
ALTER TABLE epics      ADD COLUMN batch_id TEXT;                 -- same

CREATE INDEX idx_work_items_batch   ON work_items(batch_id);
CREATE INDEX idx_work_items_lane    ON work_items(lane);
CREATE INDEX idx_work_items_depends ON work_items(depends_on_id);
```

`lane` is free-form text, not an enum. "Lanes" in real plans are ad-hoc groupings (frontend, backend, infra, db, docs) and baking them into a CHECK constraint is friction for one-off projects. A short recommended list is documented in the skill.

#### Payload changes (`src/shared/schemas.ts`)

Extend `WorkItemCreatedPayloadSchema`:

```ts
sort_order: z.number().int().optional(),
lane: z.string().max(40).nullable().optional(),
batch_id: z.string().uuid().nullable().optional(),
depends_on_id: z.string().uuid().nullable().optional(),
```

Extend `EpicCreatedPayloadSchema` with `sort_order` and `batch_id` only. No `lane` on epics — lanes are a work-item concept.

#### Processor changes (`src/server/ingest/processor.ts`)

`handleWorkItemCreated` currently hard-codes `sort_order: 0`. Replace with:

```ts
sort_order: p.sort_order ?? 0,
lane: p.lane ?? null,
batch_id: p.batch_id ?? null,
depends_on_id: p.depends_on_id ?? null,
```

`handleEpicCreated` likewise reads `sort_order` and `batch_id` from payload.

The `WorkItemRow` interface in `src/server/db/repositories/work-items.ts:4` gains the three new fields. `insertWorkItem` params expand accordingly. **No changes to `updateWorkItem`** — it already accepts arbitrary fields via the spread in the prepare/run call (`work-items.ts:116`); the whitelist lives in the route handler.

#### Route changes

`PATCH /api/work-items/:id` today calls `updateWorkItem(id, req.body)` wholesale. Add `lane`, `depends_on_id` to the allowed-field list (and reject the payload if unknown fields are present, if not already). **Do not** allow `batch_id` to be mutated via the API — it's immutable provenance, set only at creation.

### 2. Batch CLI: enforce order, propagate batch_id, support dependency chains

#### Payload schema (`src/cli/ingest.ts`)

`TaskInputSchema` gains:

```ts
sort_order: z.number().int().optional(),
lane: z.string().max(40).optional(),
depends_on: z.union([z.string().uuid(), z.number().int()]).optional(),
```

`depends_on` accepts either a real UUID (link to an existing work item) *or* an integer (batch-local index into `tasks[]`). The CLI resolves integer indices to the UUID of the N-th task being generated in the same run; unresolvable indices (negative, ≥ length, self, forward reference beyond batch) are validation errors.

`BatchPayloadSchema` top level gains:

```ts
lane: z.string().max(40).optional(),            // becomes defaults.lane
sort_start: z.number().int().optional(),        // first task's sort_order; defaults to 0
sort_step: z.number().int().positive().default(10),
```

`defaults` gains `lane`, `sort_order`, `depends_on` (all optional; row wins).

#### Deriving `sort_order` inside `runBatch`

Two passes, post-validation, pre-write (`src/cli/ingest.ts:461`):

1. Assign each task its `sort_order`:
   - If the row sets `sort_order` explicitly → use it.
   - Else if `defaults.sort_order` is set → use it for every row that didn't override (this is unusual; warn).
   - Else → `sort_start + index * sort_step` (default: `0, 10, 20, …`). Step of 10 leaves room for drag-to-reorder without renumbering the whole column.

2. Resolve `depends_on`:
   - If it's a string and looks like a UUID → pass through as `depends_on_id`.
   - If it's a number → look up `tasksBuilt[n].entityId`; error if out of range.
   - If it's a string but not a UUID → error (clear message: "use batch index or UUID").
   - After resolution, reject `depends_on_id === self.entity_id` (explicit self-reference) and run a single ancestor walk up the resolved chain to depth 50 looking for cycles. Deeper-than-50 or cycle → error. This is cheap (O(N) worst-case per task for O(N²) total, fine for typical batches ≤ 50).

3. Assign `batch_id`:
   - One UUID per `runBatch` invocation. Stamped on the epic (if present) and every task. Surfaced in the output so the skill / user can record it.

4. Epic ordering: if `epic.sort_order` is unset, leave as 0 — epics aren't typically batch-ordered against each other.

#### Output shape (additive)

```json
{
  "batch_id": "7f3a1c2d-…",
  "epic": { "file": "…", "entity_id": "…", "event_type": "epic.created", "sort_order": 0 },
  "tasks": [
    { "file": "…", "entity_id": "…", "event_type": "work_item.created",
      "sort_order": 0,  "lane": "backend",  "depends_on_id": null },
    { "file": "…", "entity_id": "…", "event_type": "work_item.created",
      "sort_order": 10, "lane": "frontend", "depends_on_id": "<row-0-uuid>" }
  ],
  "summary": { "epics": 1, "tasks": 15, "lanes": ["frontend", "backend"] }
}
```

Existing `batch` callers that only read `summary` / `epic.entity_id` / `tasks[].entity_id` keep working — the additions are additive fields.

### 3. Deterministic processing: serialize the watcher

The promise of "input-order writes" is empty unless the watcher consumes in order too. Today `handleNewFile` is `async` and fires per `add`, so two tasks' inserts can interleave.

Change (`src/server/ingest/watcher.ts:209`):

- Maintain a single in-memory `Promise` chain: `pending = pending.then(() => handleNewFile(path))`. Sequential, no concurrency. The handler is cheap (read file, parse, one insert); loss of parallelism is unmeasurable at realistic batch sizes.
- Rationale: chokidar's `awaitWriteFinish` already delays fires until writes settle, but it doesn't guarantee emit order across N files written in the same tick. Serializing the handler side is the simple fix.

This also resolves the "epic file arrives after its children" class of race — as long as the CLI writes the epic first (it does), the watcher can only process them in that order.

### 4. `ready_to_start` derivation

No new column. Compute in SQL, return in the work-item list:

```sql
-- A task is ready_to_start when:
--   status in ('triage','ready')
--   AND (depends_on_id IS NULL OR predecessor.status = 'done')
```

Implement as a view or inline in `listWorkItems`:

```ts
SELECT w.*,
  CASE
    WHEN w.status NOT IN ('triage','ready') THEN 0
    WHEN w.depends_on_id IS NULL THEN 1
    WHEN EXISTS (SELECT 1 FROM work_items p
                 WHERE p.id = w.depends_on_id AND p.status = 'done') THEN 1
    ELSE 0
  END AS ready_to_start,
  (SELECT title FROM work_items p WHERE p.id = w.depends_on_id) AS blocked_by_title
FROM work_items w
...
```

`WorkItem` (client type) gains `readyToStart: boolean` and `blockedByTitle: string | null`.

**No transitive closure.** If A depends on B and B depends on C, and C is done but B is in progress, A is "blocked" (predecessor not done). This is correct and matches the single-parent model.

### 5. Board UI — minimal surface changes

All changes to `src/client/pages/BoardPage.tsx` and `WorkItemCard`:

- Card renders a **left border color** from `lane` (simple hash-to-palette, stable across renders). `category` already owns the left border today (`BoardPage.tsx:360`); `lane` wins when set, `category` is the fallback.
- Card renders a small status dot top-right:
  - `readyToStart && depends_on_id === null` → nothing (default).
  - `readyToStart && depends_on_id !== null` → green dot, tooltip "Ready — predecessor done."
  - `!readyToStart && depends_on_id !== null` → grey dot, tooltip "Waiting on: {blockedByTitle}."
- Toolbar gains a **Lane filter** (reuses `FilterSelect`, populated from the distinct set of non-null lanes).
- The `epicGroups` alphabetical sort (`BoardPage.tsx:135`) is replaced with a two-key sort: `epic.sort_order` first, then title.

Within a column, sort becomes:

```
ORDER BY sort_order ASC, created_at ASC, id ASC
```

`id ASC` is a final tiebreaker that's deterministic across re-renders when `sort_order` and `created_at` tie (they shouldn't, but belt-and-suspenders).

### 6. Tag filter → lane filter wiring

Lane is a first-class field, so it gets its own filter dropdown. The existing tag filter stays. No cross-filtering magic — pick one at a time; the React Query filters object already supports additive filters, so combining them (`lane=backend, tag=auth`) is automatic.

```
Claude assembles JSON with array-order tasks (+ optional lane / depends_on)
                │
                ▼

                │
        (CLI, runBatch)
                │
        zod schema check
                │
        assign sort_order (index * step)
                │

                │
        self/cycle check (ancestor walk depth 50)
                │

                │

                │
                ▼

                │
                ▼

                │
                ▼
 listWorkItems returns ready_to_start + blocked_by_title (SQL-derived)
                │
                ▼
 BoardPage: column sort by sort_order; lane border; ready/blocked dot
```

## Risks

- **`depends_on_id = null` after predecessor delete.** `ON DELETE SET NULL` means deleting `a` while `b` points at it clears `b.depends_on_id`, and `b` silently becomes "ready." That's the right default for this scale — we prefer "predecessor gone ⇒ unblocked" over a hard FK violation. Documented in the skill.
- **Cycle check is O(depth)-per-task, O(N · depth) total.** Depth cap of 50 keeps it bounded. Batches of hundreds of tasks with deep chains might surprise-fail; surface the depth in the error.
- **Lane is free-form.** Typos (`fronend`) become separate lanes in the filter. Acceptable for a single-user tool; a future version can promote the common lanes to an enum or validation hint if this bites.
- **Watcher serialization hides real throughput issues.** If someone dumps 10k files into the inbox, sequential processing will lag. Not a real scenario today; flagged for v0.5+ work.
- **Sort-order collisions across batches.** Two batches in the same epic both starting at 0 will interleave: batch A gets 0,10,20,30 and batch B also gets 0,10,20,30 → six ties per batch. The skill recommends using `sort_start` (e.g. `100`, `200`) for follow-on batches to keep them visibly separate. Not a correctness bug, just a nudge.
- **`batch_id` on every row feels heavyweight** but it's a single string per row and makes "what did the planner just write" trivially queryable. The cost is ~36 bytes × N; negligible.

## Out of scope / follow-ups

- **Undo bulk-create CLI** (`npm run ingest -- delete-batch --batch-id <uuid>`). Straightforward once `batch_id` is persisted. Deferred to v0.3.8.
- **Transitive dependency closure** (A depends on B depends on C; render A as "blocked on C" when that's more useful than "blocked on B"). Single-parent covers 95% of cases; punt.
- **Lanes as swim-lane columns** on the board (horizontal split by lane). v0.3.8 UI work.
- **Auto-pick-next-task** for an agent. Needs `ready_to_start` + some ownership / claim mechanic we don't have.
- **Priority** separate from `sort_order`. One axis is enough for now.
- **Drag-to-reorder across columns while preserving dependency validity.** Today reorder is within-column only; cross-column is a status change. Nothing new here.
- **Enum-promoting the common lanes** once usage data suggests a stable vocabulary.

## Addendum — Auto `/color` and `/rename` on session start

### Brief

When the orchestrator opens a new terminal tab for a task, it spawns `claude` inside tmux and (after a 2s wait) pastes the assembled ticket prompt (`src/server/routes/sessions.ts:121,127`). Claude then sits there with the default tab name and the default color. Hand-running `/color` and `/rename` every time is friction; pushing this out to a `SessionStart` hook would force *every* session in this repo to do the same dance even when the user opens `claude` outside the orchestrator. The clean place for this is exactly where we already programmatically start Claude.

This addendum wires deterministic `/color` (from `epics.color`, which is already constrained to the 8 supported palette values at `src/server/db/schema.sql:27`) and `/rename` (from the work item's title) into the session-creation flow. No randomness; no global hook.

### Design

#### Where it goes

`src/server/routes/sessions.ts`, in the `POST /` handler, right after `tmux.sendKeys(tmuxName, "claude", true)` and before the existing 2s `setTimeout` that pastes the prompt:

1. Wait the same 2s for Claude to be ready for input.
2. Send `/color <color>` + Enter.
3. Send `/rename <title>` + Enter.
4. *Then* paste the ticket body (current behavior).

A single `setTimeout(2000)` already exists for the prompt paste. We extend that callback rather than adding a second timer — keeps the order strict and avoids a race between `/color` and the prompt paste.

#### Color resolution

```
session.workItem.epic_id ──► epics.color  (one of red|blue|green|yellow|purple|orange|pink|cyan)
                       └── no epic ──► "blue"  (matches the schema default)
```

`epics.color` is already a CHECK-constrained enum, so no validation is needed at send time. A task with no epic falls back to `blue` — same default the schema uses. Not random; predictable.

#### Rename string

The work item's `title`, trimmed and capped to 60 characters (Claude's `/rename` doesn't enforce a hard limit but anything longer wraps poorly in the tab bar). No prefix, no suffix — the title alone reads cleanest in the tab list.

#### tmux helper

`tmux.sendKeys` already supports the "Enter-terminated command" variant via `pressEnter=true` (`src/server/terminal/tmux.ts:55`). Reuse it directly. No new helper needed.

#### Resume path

`POST /:id/resume` (`src/server/routes/sessions.ts:167`) sends `claude --resume <id>`. On resume, Claude restores its in-session state — the prior `/color` and `/rename` do **not** persist across `--resume` because they're tab/terminal-level. We re-send them on resume too, using the same lookup (re-read the work item + epic).

### Changes

1. **`src/server/routes/sessions.ts`** — extract a small helper `applySessionAdornments(tmuxName, workItem)` that:
   - Looks up the epic (if any) and reads `color`.
   - Sends `/color <color>` Enter.
   - Sends `/rename <title-truncated-60>` Enter.
2. Call it inside the existing `setTimeout` callback in `POST /`, **before** the `sendKeys(prompt)` call.
3. Call it inside `POST /:id/resume`, after the `claude --resume …` send-keys, gated behind a fresh `setTimeout(2000)` (Claude takes ~the same time to come up on resume).
4. No DB schema change. `epics.color` is the source.
5. No payload schema change. Color is server-derived from epic.
6. No CLI change.

### Risks

- **Slash-command timing.** Claude needs to be at the input prompt before `/color` is sent or it'll be eaten by whatever is on screen. The existing 2s wait is empirically enough; if Claude ever ships a startup screen that intercepts keystrokes, this breaks silently. Mitigation: keep the order `claude` → wait → `/color` → `/rename` → prompt; if `/color` ever fails in practice, bump the wait or look for an idle-prompt sentinel.
- **`/rename` quoting.** Titles with single quotes pass through `shellEscape` (`tmux.ts:68`), which already wraps in `'...'` and escapes inner quotes. Safe.
- **Resume re-applies even if the user manually changed it.** Acceptable — the source of truth is the task; re-applying on resume is a feature, not a bug.
- **`/color` and `/rename` are Claude Code-specific slash commands.** If a session ever launches a non-Claude REPL (it doesn't today, but `tmux.sendKeys "claude"` is hardcoded), the slash commands would land in the wrong shell. Tied to the `claude` launch; if that changes, this changes with it.
