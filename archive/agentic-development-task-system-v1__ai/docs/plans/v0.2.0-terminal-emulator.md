# v0.2.0 — Terminal Emulator (tmux-backed, Claude Code sessions)

## Brief

Build the terminal tab into a real tmux-backed terminal emulator where each ticket being implemented gets its own terminal session running Claude Code. Clicking a ticket anywhere in the UI navigates to the Terminal tab and focuses that ticket's session. The terminal tab bar is color-coded by epic. Sessions persist across browser refreshes via tmux, and each work item stores its Claude Code session ID so sessions can be resumed with `claude --resume <session_id>`.

---

## Design

### Architecture

```
Browser (xterm.js)  ←—WebSocket—→  Express (ws)  ←—node-pty—→  tmux session (claude CLI)
```

- **xterm.js** renders terminal output in the browser
- **node-pty** spawns a shell attached to a specific tmux session
- **WebSocket** (`/ws/terminal/:sessionId`) bridges stdin/stdout between xterm.js and the pty
- **tmux** provides session persistence — survives server restarts, browser closes, etc.

### Key concepts

| Concept | Description |
|---------|-------------|
| `terminal_sessions` row | DB record linking a work item to a tmux session name + Claude session ID |
| tmux session | OS-level tmux session, named `task-<short-id>` |
| Claude session ID | The `--resume` ID printed when Claude Code exits — stored in `metadata_json` |
| Tab color | Derived from the work item's epic color |

### Why NOT SpecKit

Claude Code running inside the tmux session doesn't need SpecKit or any external integration
to access ticket info. The ticket data is local (SQLite DB), the server already knows the
work item details at session creation time, and the server can assemble the prompt and paste
it directly into the terminal. SpecKit would only matter for pulling from external systems
(Linear, Jira). Everything here is local.

### Session lifecycle — new session (no prior Claude session)

```
1. User clicks "Start Session" on a ticket
     ↓
2. Server creates tmux session: `tmux new-session -d -s task-<shortId> -x 200 -y 50`
     ↓
3. Server inserts terminal_sessions row (state: 'running', tmux_session_name, primary_work_item_id)
     ↓
4. Server sets work_item.active_session_id = session.id
     ↓
5. Server launches Claude inside tmux: `tmux send-keys -t task-<shortId> 'claude' Enter`
     ↓
6. Server waits ~2s for Claude to start (the human> prompt to appear)
     ↓
7. Server assembles ticket prompt from DB (title, body, acceptance criteria, epic context, subtasks)
     ↓
8. Server pastes ticket content into tmux WITHOUT pressing Enter:
     `tmux send-keys -t task-<shortId> -l '<assembled prompt>'`
     (-l flag = literal, no Enter at the end)
     ↓
9. Client opens Terminal tab → tab appears with epic color → xterm.js connects via WebSocket
     ↓
10. User sees Claude open with ticket content pre-filled in the input area
     ↓
11. User reviews/edits the prompt, then presses Enter when ready
```

### Session lifecycle — resuming a session (has Claude session ID)

```
1. User clicks "Resume" on a session that has a stored claude_session_id
     ↓
2. If tmux session is dead, server recreates it
     ↓
3. Server sends: `tmux send-keys -t task-<shortId> 'claude --resume <id>' Enter`
     ↓
4. Claude resumes with full conversation history — user picks up where they left off
```

### Ticket prompt assembly

When creating a new session, the server assembles the prompt from the work item's DB fields:

```
Implement: <title>

## Description
<body>

## Acceptance Criteria
<acceptance_criteria>

## Context
- Epic: <epic.title>
- Kind: <kind>
- Status: <status>
<if subtasks>
## Subtasks
- [ ] <subtask 1 title>
- [ ] <subtask 2 title>
</if>
```

This is built server-side in the session creation route (`POST /api/sessions`), not by the
client. The server has direct DB access to the work item, its epic, and its subtasks.

The user sees this in the Claude input line and can edit it before pressing Enter.
This avoids any need for SpecKit, CLAUDE.md injection, or external tool integration.

### Claude session ID capture

When `claude` exits inside a tmux session, it prints:
```
To resume this conversation, run: claude --resume <session_id>
```

The server's stdout stream watcher regex-matches this line and stores the session ID
in `terminal_sessions.claude_session_id` (dedicated column, not JSON).

When a session tab is re-opened or a "Resume" button is clicked, the server sends
`claude --resume <session_id>\n` to the tmux session via send-keys.

### Tab coloring

Each terminal tab's left border / accent color matches the epic color of its linked work item:
- Work item → `epic_id` → epic → `color` (red/blue/green/yellow/purple/orange/pink/cyan)
- The `epicColorToCss()` utility (already exists in `EpicDetailPage.tsx`) maps color names to hex values
- Extract this utility to a shared location (`src/client/lib/colors.ts`)

### Phase 3: Server — tmux manager

**New file: `src/server/terminal/tmux.ts`**

Manages tmux session lifecycle via child_process.execSync:

```typescript
// Core functions
createSession(name: string, cwd?: string): void
  // tmux new-session -d -s <name> -x 200 -y 50 [-c <cwd>]

sessionExists(name: string): boolean
  // tmux has-session -t <name>  (exit code 0 = exists)

listSessions(): TmuxSessionInfo[]
  // tmux list-sessions -F "#{session_name}:#{session_width}:#{session_height}"

killSession(name: string): void
  // tmux kill-session -t <name>

sendKeys(name: string, keys: string, pressEnter?: boolean): void
  // tmux send-keys -t <name> [-l] <keys> [Enter]
  // pressEnter=true:  `tmux send-keys -t <name> <keys> Enter`  (for commands like `claude`)
  // pressEnter=false: `tmux send-keys -t <name> -l <keys>`     (for pasting prompt text without executing)
  // Used for: launching claude, resuming sessions, and pasting ticket prompts
```

### Phase 4: Server — WebSocket relay

**New file: `src/server/terminal/ws-relay.ts`**

Handles WebSocket upgrade for terminal I/O:

```typescript
// Mounted at: /ws/terminal/:sessionId
// On connection:
//   1. Look up terminal_sessions row by sessionId
//   2. Verify tmux session exists (tmux has-session -t <name>)
//   3. Spawn node-pty: pty.spawn('tmux', ['attach', '-t', <name>])
//   4. Wire: pty.onData → ws.send, ws.onMessage → pty.write
//   5. Handle resize: ws.onMessage({type:'resize', cols, rows}) → pty.resize(cols, rows)
//   6. On pty data: scan for "claude --resume <id>" pattern, store in DB
//   7. On ws close: dispose pty (tmux session stays alive)
//   8. On pty exit: update terminal_sessions.state, notify client
```

**WebSocket message protocol:**

```typescript
// Client → Server
type ClientMessage =
  | { type: 'data'; data: string }      // stdin keystrokes
  | { type: 'resize'; cols: number; rows: number }

// Server → Client  
type ServerMessage =
  | { type: 'data'; data: string }      // stdout output
  | { type: 'session_update'; state: SessionState; claudeSessionId?: string }
  | { type: 'error'; message: string }
```

### Phase 5: Server — session routes

**New file: `src/server/routes/sessions.ts`**

```
GET    /api/sessions                — list sessions (optional ?state=running&workItemId=...)
GET    /api/sessions/:id            — get session by ID (includes work item + epic data)
POST   /api/sessions                — create NEW session for a work item (launches claude + pastes ticket)
  body: { workItemId: string, title?: string }
  1. Generate tmux name: `task-<workItemId first 8 chars>`
  2. Create tmux session
  3. Insert terminal_sessions row (state: 'running')
  4. Set work_item.active_session_id = new session ID
  5. Launch claude: `tmux send-keys -t <name> 'claude' Enter`
  6. Wait ~2s for claude to start
  7. Assemble ticket prompt from DB:
       - Fetch work item (title, body, acceptance_criteria, kind, status)
       - Fetch epic (title, color)
       - Fetch subtasks (title, status)
       - Build markdown prompt string (see "Ticket prompt assembly" above)
  8. Paste prompt WITHOUT pressing Enter:
       `tmux send-keys -t <name> -l '<prompt>'`
  9. Return session object (client navigates to Terminal tab)
  NOTE: User sees Claude open with the ticket prompt pre-filled. They review/edit, then Enter.

POST   /api/sessions/:id/resume     — resume a session with its stored Claude session ID
  1. Look up session → get claude_session_id
  2. If tmux session dead, recreate it
  3. Send `claude --resume <id>` Enter to tmux session
  4. Update state to 'running'

DELETE /api/sessions/:id             — close/archive a session
  1. Kill tmux session (if exists)
  2. Update state to 'archived'
  3. Clear work_item.active_session_id
```

**Mount in `src/server/index.ts`:**
```typescript
import sessionRoutes from "./routes/sessions.js";
app.use("/api/sessions", sessionRoutes);
```

**WebSocket mount — also in `src/server/index.ts`:**
```typescript
import { createServer } from "http";
import { setupTerminalWebSocket } from "./terminal/ws-relay.js";

// Change from app.listen() to http.createServer() so ws can share the port
const httpServer = createServer(app);
setupTerminalWebSocket(httpServer);
httpServer.listen(PORT, ...);
```

## Data flow summary

```
Work Item (epicId → epic.color, activeSessionId → terminal_sessions)
    ↓
Terminal Session (tmux_session_name, claude_session_id, state)
    ↓
tmux (OS-level session, survives everything)
    ↓
node-pty (attaches to tmux, bridges to WebSocket)
    ↓
WebSocket (/ws/terminal/:sessionId)
    ↓
xterm.js (renders in browser, tab colored by epic)
```

**Navigating to a session from anywhere:**
1. Work item has `activeSessionId`
2. Navigate to `/terminal?session=<activeSessionId>`
3. TerminalPage reads query param, finds matching tab, focuses it
4. If no WebSocket yet for that session, creates one
5. xterm.js renders the tmux session output

## Claude session ID storage

The `terminal_sessions` table gets a new column:

```sql
ALTER TABLE terminal_sessions ADD COLUMN claude_session_id TEXT;
```

**Capture mechanism:**
- The WebSocket relay scans all pty stdout for the pattern:
  ```regex
  /claude --resume ([a-f0-9-]+)/
  ```
- On match: `UPDATE terminal_sessions SET claude_session_id = ? WHERE id = ?`
- The client is notified via a `session_update` WebSocket message

**Resume mechanism:**
- `POST /api/sessions/:id/resume`
- Server checks `claude_session_id` exists
- If tmux session is dead, recreates it
- Sends `claude --resume <id>\n` as tmux send-keys
- Updates state to `running`
