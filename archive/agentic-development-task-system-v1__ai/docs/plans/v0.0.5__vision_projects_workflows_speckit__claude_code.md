# Agentic Development Task System — Expanded Vision Plan (v0.0.5)

This plan captures capabilities NOT covered (or only partially covered) in v0/v0 phases. It is organized by gap area with implementation notes.

---

## Terminology: "Session" Means Three Things

The word "session" is overloaded in this plan. These are distinct concepts:

| Concept | What it is | Identity | Restartable? |
|---------|-----------|----------|-------------|
| **Workflow run** | The full conversation-to-PR pipeline (specify → plan → tasks → execute → review → PR) | `workflow_id` on the prompt | Yes — retry from failed step |
| **Agent session** | A single Claude Code CLI invocation | `claude_session_id` | Yes — `claude --resume <id>` |
| **Terminal session** | The tmux container that hosts agent sessions | tmux session name (`task-<id>`) | Survives agent crashes/restarts |

Key relationships:
- A **terminal session** can host multiple **agent sessions** over time (e.g., if the first agent crashes and you launch another)
- A **workflow run** orchestrates when to create terminal sessions and launch agent sessions
- The `sessions` table tracks agent sessions, with a reference to the terminal session (tmux name) and workflow run

## Spec-Kit as the Workflow Engine

**Key architectural decision:** Instead of building a custom workflow sequencer, we use [GitHub Spec-Kit](https://github.com/github/spec-kit) as the core workflow engine. Spec-kit already implements the spec → plan → tasks → implement pipeline. Our system becomes an **orchestration and dashboard layer** on top of spec-kit.

### What spec-kit provides (we DON'T build)
- **Constitution** — project principles and guidelines (replaces custom skills for brainstorm/clarify)
- **Specification** — natural language → structured spec (replaces custom intent extraction)
- **Planning** — spec → architecture/tech decisions (replaces custom plan generation)
- **Task breakdown** — plan → actionable tasks (replaces custom task materialization)
- **Implementation** — execute tasks via AI agents (replaces custom agent launch orchestration)

### What we build ON TOP of spec-kit
- **Conversational UI** — chat interface that feeds into spec-kit's phases
- **Dashboard** — kanban board, task detail, progress tracking, artifact browsing
- **tmux/terminal management** — session persistence, Agent Teams integration
- **Git worktree isolation** — per-task worktrees with branch management
- **Adversarial review** — fresh-session review not covered by spec-kit
- **Playwright MCP verification** — automated UI testing
- **Real-time agent status** — what each agent is currently doing

### Architecture
```
Conversational UI (chat)
    ↓
Our orchestrator (thin layer)
    ↓ invokes spec-kit phases via CLI or slash commands
Spec-Kit: /speckit.specify → /speckit.plan → /speckit.tasks → /speckit.implement
    ↓ we intercept between phases for:
    ├── Dashboard updates (progress, status)
    ├── Approval gates (user approves plan before tasks)
    ├── Worktree creation (before implementation)
    ├── tmux session management (for implementation)
    └── Adversarial review (after implementation, before PR)
    ↓
Draft PR via `gh`
```

## New Capabilities to Add (by Priority)

### 1. Ticket-to-PR Workflow (Core UX Loop) — Powered by Spec-Kit

**The #1 gap.** The user wants to describe what they want in conversation and get back a code-complete PR.

#### Design
```
User Conversation → natural language description
    ↓
[Spec-Kit: Constitution] — project principles already defined in repo
    ↓
[Spec-Kit: Specify] — conversation → structured specification
    ↓
[Spec-Kit: Plan] — spec → architecture + tech decisions → USER APPROVAL GATE
    ↓
[Spec-Kit: Tasks] — plan → task breakdown → ingested into our task board
    ↓
[Our Layer: Execute] — for each task:
    1. Create git worktree
    2. Start tmux session
    3. Run /speckit.implement inside tmux (or claude with spec context)
    4. Agent implements, creates markdown artifacts
    5. Agent pushes branch
    ↓
[Our Layer: Review] — fresh session adversarial review
    ↓
[Our Layer: Submit] — create Draft PR, run CI
    ↓
Dashboard shows status throughout
```

#### Implementation
- **New table: `projects`** — groups tasks, has repo_path, name, description
- **New table: `workflow_runs`** — tracks the overall pipeline state
- **API: `POST /api/workflows`** — accepts conversation context, kicks off spec-kit pipeline
- **Orchestrator** (`src/server/domain/workflow.ts`) — thin layer that:
  - Invokes spec-kit phases (via `specify` CLI or agent slash commands)
  - Intercepts between phases for approval gates and dashboard updates
  - Creates worktrees + tmux sessions for the execute phase
  - Triggers adversarial review after implementation
  - Creates Draft PR on review pass
- **Spec-kit integration** (`src/server/domain/speckit.ts`) — wrapper around spec-kit CLI:
  - `runConstitution(projectPath)` — ensure constitution exists
  - `runSpecify(projectPath, userInput)` — generate spec from conversation
  - `runPlan(projectPath)` — generate plan from spec
  - `runTasks(projectPath)` — break plan into tasks
  - `runImplement(projectPath, taskId)` — implement a single task

#### Error Handling & Recovery

The orchestrator must handle failures at every step. Without this, you get orphaned worktrees, zombie tmux sessions, and tasks stuck in intermediate states.

**Workflow step tracking:**
- Each workflow run records its current step: `specifying` → `planning` → `awaiting_approval` → `tasking` → `executing` → `reviewing` → `submitting`
- On failure: mark the workflow run as `failed` with the step name + error message
- User can **retry from the failed step** (not restart the whole pipeline)

**Failure scenarios:**

| Step | Failure | Recovery |
|------|---------|----------|
| Specify | Spec-kit fails to parse input | Mark failed, user retries with clarified input |
| Plan | Spec-kit generates invalid plan | Mark failed, user retries → re-runs specify output through planner |
| Approval | User rejects plan | Workflow paused at `awaiting_approval`, user can edit spec and re-plan |
| Tasks | Task breakdown fails | Mark failed, user retries → re-runs plan through task breaker |
| Execute | Agent crashes mid-implementation | Detect via `tmux has-session` health check → mark failed → user retries → new agent session on **same worktree/branch** picks up where code left off |
| Execute | Worktree creation fails (branch exists, dirty state) | Abort with clear error, user resolves manually |
| Review | Adversarial review rejects code | Create a new Execute cycle on the same branch (loop back, don't restart) |
| Submit | `gh pr create` fails (no remote, auth expired) | Mark failed with error, user retries after fixing auth |

**Health checks:**
- Terminal sessions: poll `tmux has-session -t <name>` periodically (or on workflow step timeout)
- Agent sessions: check if tmux pane is still running a process
- Stale detection: if a workflow step has been in-progress for >N minutes with no activity events, flag for user attention

#### Files
- `src/server/domain/speckit.ts` (spec-kit CLI wrapper)
- `src/server/domain/workflow.ts` (thin orchestrator, NOT a DAG engine)
- `src/server/routes/workflows.ts`

### 2. Agent Teams + tmux Terminal Integration

**v0 has xterm.js but the user wants tmux-backed Agent Teams.**

#### Design
- Each task execution spawns a tmux session (not raw PTY)
- tmux sessions are named: `task-<task-id>`
- Multiple panes/windows per tmux session
- Agent Teams (`claude --agent-teams`) runs inside tmux
- xterm.js in browser attaches to tmux via WebSocket
- Session identity = tmux session name = task linkage

#### Implementation
- Replace raw `node-pty` with tmux spawn + attach
- `tmux new-session -d -s task-<id> -c <worktree-path>`
- `claude --agent-teams` launched inside the tmux session
- WebSocket bridges tmux → browser via `tmux capture-pane` or direct PTY attach
- Session state derived from tmux: `tmux has-session -t <name>`

#### Changes to Phase 5
- `src/server/terminal/tmux-manager.ts` (replaces pty-manager.ts)
- `src/server/terminal/ws-handler.ts` (attach to tmux instead of raw PTY)

### 3. Git Worktree Management

**Agents should work in isolated worktrees, and worktrees are session identity.**

#### Design
- On task execution start, create a worktree:
  ```
  git worktree add .worktrees/<task-slug> -b <branch-name>
  ```
- Worktree path stored on task AND session
- Session resume = reattach to existing worktree's tmux session
- On task completion, worktree can be cleaned up or kept for review

#### Implementation
- `src/server/domain/worktrees.ts`
  - `createWorktree(repoPath, taskId, branchName)`
  - `removeWorktree(worktreePath)`
  - `listWorktrees(repoPath)`
- Task status transition to `running` triggers worktree creation
- Worktree path propagated to terminal session

### 7. Conversational Interface (Primary Entry Point)

**The user wants to have a natural conversation and have the system create the right objects (tickets, workflows, sessions, tasks) from that conversation.**

This is NOT a structured form or command input. It's a chat where you describe what you want — the system interprets intent and materializes the appropriate entities. The conversation feeds directly into spec-kit's pipeline when the intent is to build something.

#### Design
- Full conversational UI on the dashboard home page
- User types naturally: "I want to build a notification system that sends emails when tasks are overdue"
- The system (backed by Claude) interprets the conversation and:
  1. **Extracts intent** — is this a new project? A task on an existing project? A bug report? A status query?
  2. **Creates the right entities** — ticket, task, workflow run, project — without the user having to pick a form
  3. **Asks clarifying questions** inline if needed ("Which project should this go under?")
  4. **Shows what it created** — inline confirmation with links to the created entities
  5. **Kicks off spec-kit pipeline** — if the conversation leads to an actionable idea:
     - Conversation content becomes the input to `speckit.specify`
     - Plan output is shown inline for approval
     - On approval, tasks are created and execution begins
     - Progress updates appear in the conversation thread
- Conversation history is persisted and browsable
- A conversation can create multiple entities over its lifetime (e.g., start by describing a feature, end up with 3 tasks and a workflow run)

#### Examples of natural input → system action
| User says | System does |
|-----------|------------|
| "I want to add dark mode to the dashboard" | Creates project → runs `speckit.specify` with conversation → shows spec for confirmation → on approval, runs `speckit.plan` → `speckit.tasks` → executes |
| "PROJ-123 needs to handle edge case X" | Fetches Jira ticket via Atlassian MCP → feeds ticket + user input to `speckit.specify` → pipeline continues |
| "What's the status of the notification work?" | No entity created — queries existing tasks/workflows and responds inline |
| "Let's break down the auth rewrite into smaller pieces" | Runs `speckit.specify` + `speckit.plan` + `speckit.tasks` → shows task list for approval |
| "Review the PR for task 42" | Triggers adversarial review skill (not spec-kit — this is our custom layer) |
| "Actually, change the approach — use WebSockets instead of polling" | Updates the spec → re-runs `speckit.plan` → shows revised plan for approval |

#### Implementation
- `src/client/pages/Home.tsx` — chat UI with message history + inline entity cards + spec-kit progress indicators
- `src/server/routes/chat.ts` — handles message send, calls Claude for intent extraction
- `src/server/domain/chat-interpreter.ts` — maps conversation intent to:
  - Entity creation (task, workflow, project, review) for direct actions
  - Spec-kit pipeline invocation for "build something" intents
  - Query resolution for status/info questions
- New table: `conversations` — `id, title, project_id?, workflow_run_id?, created_at, updated_at`
- New table: `conversation_messages` — `id, conversation_id, role (user|assistant), content, entities_created (JSON), speckit_phase?, created_at`
- Conversation links to its workflow run, so progress is trackable from the chat thread

## Open Questions

1. **tmux vs raw PTY**: tmux gives session persistence + Agent Teams but adds a dependency. Raw PTY is simpler. **Recommendation: tmux** — it's already on macOS and gives you Agent Teams for free.

2. **Agent Teams opt-in**: How to ensure agents use Agent Teams? → Launch `claude` with `--agent-teams` flag inside tmux. The system controls how agents are launched.

3. **Git worktree lifecycle**: When to clean up worktrees? **Recommendation**: keep until task archived, then offer cleanup.

4. **Chat vs Prompt**: ~~Full conversational chat or just a command input?~~ **RESOLVED**: v0.0.5 builds a **full conversational interface**. The user types naturally, and the system (backed by Claude) extracts intent and creates the right entities (tasks, workflows, projects, reviews). This is the primary entry point — no structured forms required. See Section 7.

5. **Jira integration**: Should ticket-to-PR actually fetch from Jira? → Yes, use Atlassian MCP (per CLAUDE.md rules).

6. **Spec-kit invocation method**: Should the orchestrator call spec-kit via the `specify` CLI, or via slash commands inside a Claude agent session? **Recommendation**: CLI (`specify plan`, `specify tasks`, etc.) for phases that don't need interactivity. Slash commands (`/speckit.implement`) for the implementation phase where an agent needs to run inside a tmux session.

7. **Spec-kit constitution**: Should we maintain a single constitution for the whole system, or per-project constitutions? **Recommendation**: Start with a single repo-level constitution, allow project-level overrides later.

8. **Spec-kit extensions**: Should adversarial review and Playwright validation be packaged as spec-kit extensions? **Recommendation**: Keep as standalone skills for v0.0.5, evaluate extension packaging for v1.

### Data Migration Plan

Adding new tables (`projects`, `workflow_runs`, `conversations`, `conversation_messages`) should be **additive migrations** — never rebuild the existing schema. Each phase that adds tables should:
1. Include a migration SQL file in `src/server/db/migrations/`
2. Use `CREATE TABLE IF NOT EXISTS` for safety
3. Add foreign keys to existing tables via `ALTER TABLE` (SQLite supports this with limitations — may need to recreate table if adding FK constraints)
