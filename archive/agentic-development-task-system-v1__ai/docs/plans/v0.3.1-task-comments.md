# v0.3.1 — Task Comments

## Brief

Add editable comments to work items. Comments appear at the bottom of the task detail page (`WorkItemDetailPage`) and inside the Board-page task preview drawer (`WorkItemDrawer`). Users can create, edit, and delete comments from either surface.

### User stories

1. **As a user on a task detail page**, I see a list of comments at the bottom and can add a new comment, edit an existing one, or delete one.
2. **As a user on the Board page**, when I open a task preview (drawer), I see the same comments list at the bottom and have the same edit/delete/create capabilities.
3. **As an agent (Claude Code, scripts)**, I can drop a `comment.created` ingest envelope into `.taskboard/inbox/` and the comment shows up in both UI surfaces.

## Design

### Architecture

```
UI (WorkItemDetailPage, WorkItemDrawer)
        │
        ▼
CommentList.tsx ──hooks──> /api/work-items/:id/comments (REST)
                                     │
                                     ▼
                         comments.ts route ──> comments repository ──> SQLite
                                     │
                                     └──> activity_events (comment.created/updated/deleted)

Ingest path (parity with existing events):
  JSON envelope → validator.ts → processor.ts → handleCommentCreated → comments repo
```

Comments are a first-class entity with their own table and route module. Activity events are emitted so the Activity page reflects comment changes like every other mutation.

### DB

**New migration: `src/server/db/migrations/002_add_comments.sql`**

```sql
CREATE TABLE comments (
  id TEXT PRIMARY KEY,
  work_item_id TEXT NOT NULL REFERENCES work_items(id) ON DELETE CASCADE,
  body TEXT NOT NULL,
  author_type TEXT NOT NULL CHECK (author_type IN ('user', 'agent', 'system')),
  author_id TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  edited_at TEXT
);

CREATE INDEX idx_comments_work_item ON comments(work_item_id, created_at);
```

- `edited_at` stays NULL until the first edit; drives a `(edited)` label in the UI.
- `ON DELETE CASCADE` so comments disappear when a task is deleted.
- Update `EXPECTED_TABLES` in `migrate.ts` to include `comments`.

### Shared

**`src/shared/types.ts`** — add:

```ts
export type Comment = {

  workItemId: string;
  body: string;
  authorType: ActorType;

  createdAt: string;
```

**`src/shared/schemas.ts`** — add payload schemas and wire them into `PayloadSchemaMap`:

```ts
export const CommentCreatedPayloadSchema = z.object({
  comment_id: z.string().uuid(),
  work_item_id: z.string().uuid(),
  body: z.string().min(1),
});

export const CommentUpdatedPayloadSchema = z.object({
  comment_id: z.string().uuid(),
  body: z.string().min(1),

export const CommentDeletedPayloadSchema = z.object({
  comment_id: z.string().uuid(),
});
```

### Server

**`src/server/db/repositories/comments.ts`** (new file) — prepared statements:

- `listCommentsForWorkItem(workItemId)` → oldest→newest
- `getCommentById(id)`
- `insertComment({ id, workItemId, body, authorType, authorId, createdAt, updatedAt })`
- `updateComment(id, body, editedAt)` → also bumps `updated_at`
- `deleteComment(id)`

Row mapping mirrors existing repos: snake_case rows → camelCase domain type.

**`src/server/routes/comments.ts`** (new file):

- `GET  /api/work-items/:id/comments` → list
- `POST /api/work-items/:id/comments` → `{ body }` → insert + log `comment.created` activity event
- `PATCH /api/comments/:commentId` → `{ body }` → update + set `edited_at` + log `comment.updated`
- `DELETE /api/comments/:commentId` → delete + log `comment.deleted`

Mount both groups in `src/server/index.ts` under their respective prefixes. (Two sub-routers since the PATCH/DELETE paths don't nest under `/work-items/:id/`.)

**Ingest handlers** — extend `src/server/ingest/processor.ts` with `handleCommentCreated`, `handleCommentUpdated`, `handleCommentDeleted`. Route via the existing switch on `event_type`.

### Client

**`src/client/services/hooks.ts`** — add:

- `useComments(workItemId)` → `useQuery<Comment[]>({ queryKey: ['comments', workItemId] })`
- `useCreateComment(workItemId)` → POST `/work-items/:id/comments`
- `useUpdateComment(workItemId)` → PATCH `/comments/:commentId`
- `useDeleteComment(workItemId)` → DELETE `/comments/:commentId`

All mutations invalidate `['comments', workItemId]` on success.

**`src/client/components/CommentList.tsx`** (new file):

- Props: `{ workItemId: string; compact?: boolean }`
- Composer: Textarea + "Post" button. Enter submits (Shift+Enter = newline). Clears on success.
- Row: author label (`authorId` or author type), `timeAgo(updatedAt)`, `(edited)` if `editedAt`, body (`whitespace-pre-wrap`), inline "Edit" / "Delete" actions.
- Inline edit: clicking "Edit" swaps the body for a Textarea + Save / Cancel (Escape cancels). Pattern matches `InlineEditTitle` on `WorkItemDetailPage`.
- `compact`: tighter padding, smaller font; used inside the drawer.

Since this is a single-user local dashboard, edit/delete actions are available on every comment (no per-user gating).

**Page wiring:**

- `WorkItemDetailPage`: add `<Separator />` + `<CommentList workItemId={item.id} />` at the bottom of the scroll region.
- `WorkItemDrawer`: add `<Separator />` + `<CommentList workItemId={itemId} compact />` at the bottom.

## Post-implementation fix — migration regression

**Symptom:** first boot after implementation crashed with `SqliteError: table initiatives already exists`; Vite dev server logged ECONNREFUSED for every `/api/*` call because Express never listened on `:3001`.

**Root cause:** `EXPECTED_TABLES` in `src/server/db/migrate.ts` represents "tables the base `schema.sql` creates" — it is the gate `tablesExist()` uses to decide whether to re-run the base schema. During implementation, `"comments"` was added to `EXPECTED_TABLES` **and** a `comments` block was added to `schema.sql`. On an existing DB, `tablesExist()` returned `false` (no `comments` row yet), which triggered a full replay of `schema.sql` — and the first statement (`CREATE TABLE initiatives`) failed immediately.

**Fix (already applied):**

- Removed `"comments"` from `EXPECTED_TABLES` in `src/server/db/migrate.ts`.
- Removed the `comments` table block from `src/server/db/schema.sql`.
- `comments` is now created solely by incremental migration `002_add_comments.sql`, which applies correctly on both existing and fresh DBs.

**Rule of thumb for future incremental migrations:** do **not** add the new table to `EXPECTED_TABLES`, and do **not** append it to `schema.sql`. Keep the new table exclusively inside the incremental migration file.

## Addendum — Comments accessible to Claude Code

### Problem

As shipped, comments are fully visible in the UI but **invisible to agents**:

1. `GET /api/work-items/:id` does not include `comments` in its response payload, so `useWorkItem` and any agent-side fetch of a work item misses them.
2. There is no CLI command or Claude skill to **read** comments — agents would have to know about `/api/work-items/:id/comments` and hit it over HTTP (which the existing skills avoid).
3. There is no CLI subcommand to **post** a comment from an agent — the only on-disk ingest path requires an agent to hand-roll a `comment.created` envelope.
4. UI-originated comments never produce a JSON file in `.taskboard/processed/`, so the on-disk audit trail is partial.

Goal: agents reading or editing a task can see its comments, and agents can post comments via the same CLI/skill pattern used for tasks and epics.

### Design

Two changes, both small extensions of existing patterns.

**1. Enrich `GET /api/work-items/:id` with comments**

In `src/server/routes/work-items.ts`, add `listCommentsForWorkItem` to the enrichment block so the detail payload returns `{ ...item, tags, reviews, subItems, artifacts, epic, parent, comments }`. Update the `WorkItemDetail` client type in `src/client/services/hooks.ts` to include `comments: Comment[]` — existing callers keep working, and `CommentList` can opt to seed its cache from the detail payload (optional; not required for this addendum).

This is the **primary** change that makes comments discoverable: anyone reading a task via the standard detail endpoint now gets its comments inline.

**2. Add `comment` subcommand to `scripts/ingest.ts` + a `taskboard-comment` skill**

CLI:

```
npx tsx src/cli/ingest.main.ts comment --work-item-id <uuid> --body "<text>"
  [--actor-id <string>]   (default: "claude-code")
  [--actor-type <string>] (default: "agent")
  [--source <string>]     (default: "claude-skill")
```

Builds a `comment.created` envelope, validates with `CommentCreatedPayloadSchema`, writes JSON to `.taskboard/inbox/comment-<workitem-short>-<short-uuid>.json`. The existing watcher/processor already handle `comment.created` (shipped in this plan) — no new server code.

Skill: `.claude/skills/taskboard-comment.md`, thin wrapper that invokes the CLI. Description lines up with the existing `taskboard-create-task` / `taskboard-create-epic` skills.

**Why add a CLI + skill instead of telling agents to call the API:** consistency with the existing ingest-CLI pattern documented in v0.3.0 (ingest JSON is the canonical on-disk audit trail; skills are thin wrappers that shell out to the CLI). This also fills the gap where UI-created comments don't produce a JSON file — agent-created ones will.

### Non-goals for this addendum

- Mirroring UI-created comments out to `.taskboard/processed/`. The processed folder is the audit trail for **ingested** files; duplicating every UI mutation there is out of scope (same as we don't mirror UI-created tasks). The `activity_events` table is the canonical mutation log for both paths.
- A skill or CLI for editing/deleting comments. Agents overwhelmingly want to **read** and **append**; edit/delete remain UI-only.

### Changes

1. `src/server/routes/work-items.ts` — import `listCommentsForWorkItem`, add `comments` to the `GET /:id` response.
2. `src/client/services/hooks.ts` — add `comments: Comment[]` to `WorkItemDetail`.
3. `src/cli/ingest.ts` — add `comment` subcommand that builds the `comment.created` envelope.
4. `src/cli/ingest.main.ts` — wire the subcommand into the CLI dispatcher.
5. `src/cli/ingest.test.ts` — add tests for comment envelope generation, filename slugification, missing `--work-item-id`, missing `--body`.
6. `.claude/skills/taskboard-comment.md` — new skill wrapping the CLI.

### Tests

**Unit:**

- `GET /api/work-items/:id` returns `comments` array ordered oldest → newest.
- `GET /api/work-items/:id` on a work item with zero comments returns `comments: []`.
- `scripts/ingest.ts comment` subcommand: validates required flags, builds an envelope that passes `IngestEnvelopeSchema` + `CommentCreatedPayloadSchema`, writes JSON to `.taskboard/inbox/`.
- CLI exits 1 when `--work-item-id` or `--body` is missing.

**Manual:**

- [ ] `curl /api/work-items/<id>` → response includes `comments` array matching what the UI shows.
- [ ] `npx tsx src/cli/ingest.main.ts comment --work-item-id <uuid> --body "Hello from CLI"` → file appears in `.taskboard/inbox/`, gets processed, and the comment shows up in both the task detail page and the drawer.
- [ ] Invoke the new `taskboard-comment` skill in Claude Code → comment posted.
