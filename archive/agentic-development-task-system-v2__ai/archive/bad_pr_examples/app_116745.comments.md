## PR Description

Replaces the management command from PR [#116708](https://github.com/klaviyo/app/pull/116708) with a Django data migration that inserts `(FUNNEL_SUMMARY, BY_CHANNEL)` widget rows for every dashboard that currently has at least one per-channel funnel summary widget (`EMAIL`/`SMS`/`PUSH`).

The new widget is positioned at `min(order)` of the source rows so it lands in the same UI slot as the legacy widgets it replaces. The legacy rows are removed in a follow-on PR (`0039_core587_delete_funnel_summary_per_channel`).

This is the **insert** half of the two-PR pair tracked in the [CORE-587 test plan](https://klaviyo.atlassian.net/wiki/spaces/RP/pages/PerformanceDashboardMigration).

# Risk Impact

- **Downstream impact / datastores:** Inserts at most one new row per existing performance dashboard into `app_widget` (custom_analytics_reports DB). Test plan estimate: ~2730 dashboards have email + sms funnel summary widgets, so the insert touches at most that many rows. Idempotent — re-running on a partially migrated set is safe.
- **Performance:** `iterator(chunk_size=2000)` over the source query keeps memory bounded. Each insert is one row; total runtime is dominated by INSERT latency (~2730 inserts).
- **Environment flags:** None. The fender Statsig gate (`reporting_enable_multi_channel_funnel_widget`) controls *visibility*, not migration behavior — inserts run unconditionally so the BY_CHANNEL widget exists when the gate flips on.
- **Forward compatibility:** Yes. New rows match the existing `Widget` model schema.
- **Rollback:** `RunPython` reverse deletes BY_CHANNEL rows on dashboards that still have legacy per-channel rows. Once the follow-on delete migration runs, this reverse becomes incomplete by design (deleted legacy rows are not snapshotted) — but the insert reverse is sufficient if rollback happens before the delete migration.

This loop does one `Widget.objects.create()` per dashboard. For a large number of dashboards, that's one INSERT statement and one round trip per row.

Consider using `bulk_create` instead:

```python
widgets_to_create = []
for (company_id, dashboard_id), min_order in min_order_by_dashboard.items():
    if dashboard_id in already_migrated:
        skipped_existing += 1
        continue
    widgets_to_create.append(
        Widget(
            company_id=company_id,
            performance_dashboard_id=dashboard_id,
            name=_DEFAULT_NAME,
            type=_TYPE_FUNNEL_SUMMARY,
            subtype=_SUBTYPE_BY_CHANNEL,
            order=min_order,
            status=_STATUS_LOADING,
            details={},
        )
    )

Widget.objects.bulk_create(widgets_to_create, batch_size=1000)
inserted = len(widgets_to_create)
```

This batches 1000 rows per INSERT statement instead of one per row — significantly faster for large datasets since you avoid the per-row round trip overhead.

nit: This could be simplified to a single database query using Django's `annotate` + `Min`:

```python
from django.db.models import Min

min_order_by_dashboard = {
    (row["company_id"], row["performance_dashboard_id"]): row["min_order"]
    for row in Widget.objects.filter(
        type=_TYPE_FUNNEL_SUMMARY,
        subtype__in=_PER_CHANNEL_SUBTYPES,
    )
    .values("company_id", "performance_dashboard_id")
    .annotate(min_order=Min("order"))
}
```

This translates to a single SQL query with `GROUP BY company_id, performance_dashboard_id` and `MIN(order)`, so the database computes the minimum for each group rather than streaming all matching rows into Python and computing it in the loop. For a migration touching many rows it's a nice efficiency win — the DB engine is much faster at aggregation than Python iteration.

### User story

As a Klaviyo customer, I want my Performance Dashboard to show a single unified funnel summary widget covering all send channels instead of separate per-channel widgets, so that I can see all my funnel data in one place.

### Background

Today, dashboards contain separate Email, SMS, and Push funnel summary widgets. **Widget ordering**

We need the BY_CHANNEL widget to appear in the same position the user's existing funnel widgets occupied — not appended to the end.
