### Keyset pagination drops rows at batch boundaries

**Medium Severity**

<!-- DESCRIPTION START -->
The keyset pagination uses `performance_dashboard_id__gt` as the cursor, but a single dashboard can have up to 3 rows (EMAIL, SMS, PUSH). When rows for the same dashboard span a batch boundary, the next batch's `__gt` filter skips the remaining rows for that dashboard. For example, if batch N ends with `dashB/EMAIL`, `last_dashboard_id` is set to `"dashB"`, and the `dashB/SMS` and `dashB/PUSH` rows are silently lost. This causes an incorrect `min_order` for affected dashboards, positioning the new `BY_CHANNEL` widget at the wrong order. The pagination test only seeds one widget per dashboard so it doesn't catch this.
<!-- DESCRIPTION END -->

### Dead exception handler masks unhandled operational errors

**Medium Severity**

<!-- DESCRIPTION START -->
The `except UnableToObtainConcurrencyLockException` handler can never fire because `trigger_widget_update_task` is called with `ignore_concurrency_lock=True`, which skips the lock-acquisition path entirely — the only place that exception is raised. If an actual operational error occurs inside `trigger_widget_update_task` (e.g., Celery is down or a DB write fails), the internal `except Exception` re-raises the original exception, which won't match `UnableToObtainConcurrencyLockException`, so it propagates unhandled up to the `retrieve` view and results in a 500. Since this runs on every non-stale dashboard load with `NOT_RUN` widgets, a transient infrastructure issue would block users from viewing their dashboard until the `NOT_RUN` widgets are successfully processed.
